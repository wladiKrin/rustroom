## What this is

**Rustroom** is an open-source alternative to Adobe Lightroom (Classic model): a non-destructive RAW photo editor. **Linux first**, then Windows/macOS from one codebase.

- Ambition: a **serious, usable** tool on a focused feature set — not a toy, not a full LR clone.
- Focus order: **Develop (editing) first, Library (catalog/DAM) later.**
- **Reuse proven libraries** (libraw, LittleCMS, lensfun) rather than reimplementing decoding/color science.

## Stack

| Concern | Choice |
|---|---|
| Language | **Rust** (Cargo workspace) |
| RAW decode | **libraw** via bindings (swappable; `rawler` is the pure-Rust alt) |
| Color management | **LittleCMS** (`lcms2`) |
| Lens corrections | **lensfun** (later phase) |
| CPU parallelism | **`rayon`** |
| Image export I/O | **`image`** + jpeg/tiff/png crates |
| GUI | **`egui` + `wgpu`** (Slint reconsidered later) |
| Catalog DB (later) | **SQLite** via `rusqlite` |
| Edit persistence | sidecar **JSON** now → catalog DB later |

**Why Rust over C++/Qt:** cross-platform single codebase, native perf w/o GC, memory/thread safety, and — the deciding factor — `wgpu` is one GPU compute API across Vulkan/Metal/DX12/GL, making the later CPU→GPU port share one abstraction.

## Core architecture (the load-bearing decisions)

1. **Non-destructive.** Originals are never modified. An edit = a parameterized entry in an ordered **op-list**. Rendering replays the op-list. This gives history, virtual copies, and presets almost for free.
2. **Scene-referred, linear, float32 working space.** Math in linear light; display/output transform applied only at the end.
3. **Staged pipeline behind a `PipelineStage` trait.** Each stage is an independent, unit-testable `apply(image, params) -> image`. A stage's CPU impl can later be swapped for a `wgpu` compute shader **without changing callers.**
4. **Interactivity via previews.** Edit downscaled previews for instant feedback; render full-res only on export / 1:1 zoom.

Pipeline order:
```
decode → linearize/black-white → white balance → demosaic →
input color profile → working space (linear f32) →
geometry (crop/straighten) → noise reduction → exposure →
tone (highlights/shadows/curve) → color (HSL/grading) →
vignette → sharpen → output transform → encode
```

**Geometry runs first**, not last, so every adjustment acts on the final cropped pixels —
which is also what makes the vignette post-crop for free, with no separate mode. (Lens
corrections will join it there when `lensfun` lands.)

**NR early, sharpening late** — the two halves of "detail" belong at opposite ends. Denoising
the source is far easier than denoising after Exposure/Shadows/the tone curve have amplified
the grain, and it prevents HSL chroma speckle instead of smoothing it after the fact.
Sharpening is last because it must not amplify anything a later stage would then stretch.

## Conventions & engineering discipline

- **CI on Linux from day one:** `cargo build`, `cargo test`, `cargo clippy`, `cargo fmt --check` must stay green.
- **Golden-image regression tests** (established at plan milestone M1.2): render a fixed RAW with a fixed op-list, assert output matches a checked-in reference within tolerance. Never abandon these — they make the GPU port safe.
- **Keep crates small and single-purpose.** A file growing large signals it's doing too much.
- **Color correctness is first-class** — validate against references early.
- **Design the GPU seam now, build it later.** Don't leak CPU-specific types into the pipeline interface.
- Avoid platform-specific assumptions (paths, file dialogs, GPU backend) so Win/macOS stay cheap.

**A photo's undo stack now survives a switch away and back, and Ctrl+Z is scoped to the photo on screen.** `History<Edits>` still lives on `Session`; what changed is that it no longer dies with it, and that `ActionLog` entries can now say *which* photo they belong to.

- **⚠ The storage was the easy half; the log was the feature.** A per-path history alone does nothing, because `ActionKind::PhotoEdit` was **anonymous** — it meant "pop whatever history is current", which after a switch is a different photo's, which is exactly why `forget_photo_edits()` had to delete every one of them on every switch. Restore A's stack without touching the log and Ctrl+Z is still dead. The variant carries a `PathBuf` now.
- **Undo is scoped to the open photo, not chronological across photos.** Lightroom's own answer is the other one — strict order, jumping back to the photo an undo belongs to — and it was rejected because a keystroke whose whole promise is "put it back" should not yank the view elsewhere and start a decode. Reverting a closed photo's sidecar in the background was rejected outright: it changes a photo the user cannot see. Global actions (`PresetDelete`, `Sync`) still interleave chronologically with whichever photo is open.
- **⚠ `ActionLog` is now one `Vec<Entry>` with an `undone` flag, not two stacks.** Filtering two stacks by reachability means removing an entry from the *middle* of one and pushing it back on the *top* of the other, which scrambles chronological order across photos — observable as a wrong undo order the next time you switch, and repairable only by putting a sequence number on every entry. The flag makes the ordering intrinsic. `undo` takes the **last** reachable entry in force; `redo` takes the **first** reachable undone one, and *first* is what makes them exact inverses: within one photo's subsequence the in-force entries form a prefix and the undone ones a suffix, so the first undone entry **is** the one undone most recently. With a single photo open throughout, this is behaviourally identical to the old two stacks, which is the regression argument — all 13 pre-existing tests passed with their assertions unchanged.
- **⚠ `reachable()` is where the semantics live.** Global actions are reachable from anywhere; a `PhotoEdit` only from its own photo; a **`Batch` only when every member is**, so one Ctrl+V stays one Ctrl+Z.
- **⚠ That fixes a wart rather than extending one.** The old sweep tore the `PhotoEdit` member out of every batch on every switch, **permanently** stranding the sidecar half of a paste with no way to undo it. Now the batch simply waits, intact, and becomes undoable again on return. `a_batch_survives_a_visit_to_another_photo_intact` pins it.
- **⚠ One rule invalidates a stale stack, checked at one moment.** A sync or paste rewrites the sidecars of photos that are *not open*, so their stashed histories describe a state no longer on disk. Rather than oblige every writer — `sync::apply`, `apply_to_selection`, a preset click, a `Sync` undo *and* redo, and anything added later — to remember to invalidate, `HistoryStash::take_matching(path, on_disk)` hands a history back **only if `stashed.get() == on_disk`** and drops it otherwise. That single check subsumes all of them. `Edits` is `PartialEq` over `f32`, so a `NaN` compares unequal and it fails toward "start fresh" — the safe direction, as `PrefixKey` fails toward a cache miss.
- **`app::edit_history::HistoryStash` is a stash, not a store.** `Session` keeps owning the authoritative history, so all ~10 `s.history.*` call sites were untouched. Making the stash authoritative would force every `s.history.push` — each already inside a closure holding `&mut self` through `self.session` — to take a second simultaneous `&mut self` borrow, which is the egui borrow shape this codebase has already paid compile errors for twice. Putting histories in `BufferCache` was rejected too: capped at 3 for memory, `Arc`-immutable, and a history should outlive its buffer.
- **`finalize_session` is the only place `self.session` is ever assigned**, so it is the only choke point needed — it stashes the outgoing history and takes the incoming one, covering both the cache-hit and finished-decode paths with one edit.
- **⚠ `forget_photo_edits()` became `forget_edits_of(path)`**, called only where a history was *actually* discarded: `reload_if_affected`, and `finalize_session` when `take_matching` refuses. Not on every switch any more — that is the whole point.
- **Unbounded map, deliberately.** `BUFFER_CACHE_CAP` is 3 because a decoded buffer is 78–313 MB; a `History<Edits>` is a `Vec` of a few-hundred-byte struct, so 500 photos at 20 steps each is ~4 MB. A cap here would be a constant nobody could justify from a measurement. Histories with nothing to undo are not stashed at all, so the map grows per photo *edited*, not per photo visited.
- **⚠ Redo is per photo too.** A new action clears only the redo entries **it can reach** — the open photo's and global ones. Editing B does not invalidate A's pending redo, because nothing about B makes it wrong; the blanket clear would have reintroduced "your stack is gone" one level down.
- **Tests: 22 in `action_log` (13 pre-existing, unchanged), 7 in `edit_history`.** The reachability tests were **watched failing** — sabotaging `reachable`'s `PhotoEdit` arm to `true` failed seven of them.
- **⚠ The plan missed two sites and the compiler caught them**: `undo_one` and `redo_one` *pattern-match* `ActionKind::PhotoEdit`, not just construct it. Worth remembering when changing a variant's shape — grep for the name, do not enumerate call sites from memory.
- **Accepted caveats:** (1) session-only — closing the app loses every stack, since persisting to the sidecar would change the file format, inflate every sidecar by its whole history and raise a migration question; (2) the map is unbounded; (3) a sync to a *closed* photo discards that photo's stack, detected lazily on reopen — the sync itself stays undoable globally; (4) **Ctrl+Z on B can never reach A's edit**, which is the point of the scoping, not a gap; (5) the stash is keyed by path, so moving or renaming a file between visits loses its stack — the same assumption sidecars already make.

**1:1 region rendering done — zoom now re-renders instead of magnifying.**

- **Two render modes.** Fit (`max_dim` = `PREVIEW_MAX_DIM` 1600) and Native (`max_dim` = the editing buffer's long edge, 3123 for the X-T4), switching at **`fit · zoom > 1.0`** — the point where the fit texture is magnified past its own pixels. Quantized to two modes on purpose: a continuously-varying `max_dim` would rebuild the cache on every scroll tick. **Fit mode is byte-for-byte the old behaviour** (`region = None`, same code path).
- **The crop sits between prefix and tail.** The prefix (geometry + NR) runs whole-buffer and is cached; the visible region is cropped out of *its output*, and only the tail runs on it. Two properties made this the right cut: the prefix output **is** the post-geometry image, so screen→region is a plain scale and offset with **no inverse geometry**; and NR having run whole-buffer means **no region boundary can ever produce a seam**, however you pan. That was the deciding argument against cropping first and giving each spatial stage a margin.
- **The cache key does not include the region** — panning re-runs only the tail and never invalidates anything. `CacheKey` stays `(PrefixKey, max_dim)`.
- **Two cache entries** (`PrefixCache::CAP = 2`), one per render mode, so zooming in and out is instant rather than recomputing a 141 ms prefix each way. ~20 MB (fit) + ~78 MB (native).
- **`Region` is optional and additive**: `build_pipeline_split_in_region` / `VignetteStage::new_in_region`, with the existing functions delegating with `None`. **Zero call-site churn** — the CLI, export and all 20 goldens compiled untouched. Rejected alternatives and why: moving vignette into the prefix would run it *before* the tone curve (which would re-map it) and break its "+100 = exactly white" endpoint, besides making every vignette slider invalidate NR; `ImageBuf` carrying `origin`/`full_size` needs no API change but puts a rendering concern in the core type, obliges every future buffer-producing op to maintain it or be silently wrong, and changes `ImageBuf`'s `PartialEq` (which tests compare on); a full `RenderContext` is the cleanest long-term shape but churns every call site for something only zoom uses.
- **⚠ Only `VignetteStage` is position-dependent**, and it is in the tail — so it is the one stage a crop would break. Its `Shape::new` must receive the **frame's** dimensions, not the crop's, or roundness silently reshapes. `a_region_render_matches_the_whole_frame_cropped` and `the_region_sets_the_aspect_not_the_crop` pin both halves.
- **`every_cached_frame_matches_a_cold_render`'s big brother**: `a_region_render_matches_the_whole_render_cropped` asserts `render_region == crop(render_whole)` **bit-identically**, with a vignette, a geometry angle and NR all active. One property validating the region maths, the vignette correction and the cache at once.
- **`app::view_region`** holds the viewport maths as pure, `egui`-free functions (`needs_native`, `visible_rect`, `with_margin`, `contains`) **specifically** so clamping and off-by-one errors are testable rather than only visible as a wrong image. `REGION_MARGIN = 128` px means small pans reuse the existing texture; a re-render is requested only when the visible rect escapes the rendered one.
- **Measured** (X-T4, release, best of 5): native prefix **141.4 ms** one-off; **region tail 1400×900 in 6.9 ms** (plus ~3 ms RGBA pack). Compare the fit-mode cached hit at 13.4 ms.
- **Caveats:** (1) and (2) below are **superseded for RAW** by the full-resolution 1:1 work — see that section. They still describe the **NativeHalf** tier, i.e. zoom between 1.0× and ~1.95× fit, and the whole of a session before the full decode lands. (1) buffer-native is **half** of true full-res, so detail judged there corresponds to ~2× the radius it will have in the export; (2) the half-size decode **skips demosaic entirely** (2×2 binning) while export runs a real algorithm, so that tier differs from the export in *kind*, not only resolution; (3) +78 MB while zoomed; (4) the before/after baseline stays preview-resolution, so toggling it while zoomed shows a softer image; (5) native mode renders slightly more than displayed between 0.51× and 1.0× on-screen scale.

**⚠ Demosaic: we never set `user_qual`, so every decode inherits libraw's slowest.** Measured full-res on the X-T4 (unpack a flat ~850 ms in all cases): bilinear 405 ms → VNG 2,310 → PPG 6,782 → **AHD 10,148** (the default). So ~93% of an 11 s full-res decode is demosaic, chosen by a default nobody made. Two conclusions: **full-res is reachable in ~1.3 s, not 11.4** — which makes a future background full-res upgrade for true 1:1 far more tractable than it looked — and **the planned Phase 5 `wgpu` port would not fix it**, because that time is inside libraw's `dcraw_process`, entirely upstream of the `PipelineStage`s wgpu would touch. GPU demosaic means replacing libraw's, and on X-Trans that is Markesteijn/AMaZE-class work whose errors surface as exactly the fine-detail artifacts one zooms in to inspect. Every export also pays this ~11 s. Tracked as a separate task.

**The fit view now fills the window — and a progressive-sharpen feature was built and then removed.** The visible symptom was a soft fit view on a HiDPI display. The diagnosis took four rounds and three bugs, and the durable lessons are about *diagnosis*, not resolution.

- **⚠ The cause was one line, and not the one I measured.** `let fit = (…).min(1.0)` meant "never magnify past 100%" — but 100% of an arbitrary 1600 px preview, not of the image. On a 2302-point-wide canvas the photo was drawn at **1600 points: letterboxed at 70% of the window**, then upscaled 2× by the display. Removing the clamp fills the window *and* makes the existing zoom ladder climb to the 3200 rung on its own, closing most of the gap with **no new machinery**.
- **⚠ Two things were conflated, and separating them is what made the clamp removal safe.** "Render a region" had meant "the rung is above the fit cap", equivalent to "zoomed in" only *because* `fit` was clamped. Unclamped, the whole image can be visible at a higher rung — and rendering that as a region would starve `fit_image_size`, which is only taken from whole-image frames, leaving it stale after any crop applied outside Geometry mode. Now decided by `view_region::covers_whole_image`.
- **`fit_image_size` is derived from any whole-image frame** by the ratio `fit_cap / frame.max_dim`. Both are *pre-geometry caps*, so the crop factor cancels exactly and neither term comes from a rendered size — it cannot feed back. This replaced an equality test that would silently have rejected the higher-rung frames the clamp fix introduced.
- **⚠⚠ The progressive sharpen was built, shipped, debugged three times, and removed.** Measured: simply raising the cap takes a tail slider **14.6 ms → 45.9 ms (3.1×)** at 2800 px, so it rendered at 1600 while interacting and re-rendered 200 ms after. It never once worked in use:
  1. **It oscillated.** `wants_sharpen` required "the showing resolution is not yet sharp", which goes false the frame the sharp render lands — so the canvas reverted, counted that as interaction, and reset its own timer. Visible as nothing happening.
  2. **It sharpened the *wrong buffer*.** `sharp_cap` clamps to `buffer_long`, which before the full-res upgrade is the **half-size, binned** buffer. Rendering at its native size shows binning artifacts 1:1 that downscaling had been averaging away — no detail gained, ~4× the pixels spent. That was the "slower Exposure slider".
  3. **The clamp fix made its gate unreachable.** It tested "at the base rung", true only while `fit` was clamped.
  With the gate finally right the residual was 1.44× → 1:1 sampling for ~2× the render, and **the user could not see it on or off**. Removed: `sharpen.rs`, the interaction tracking, the `FINALS_CAP` bump, the debug print.
- **⚠ The lesson: one print settled what four rounds of reasoning had not.** The opening measurement was real but measured a *consequence*. Nobody checked what the fit view was actually doing on that display until an env-gated `eprintln` went in, and its first line (`native=true` — the user was never at the fit rung) reframed the problem. Reach for instrumentation earlier when the code reads correctly but the behaviour disagrees.
- The design doc survives as `2026-08-13-progressive-fit-resolution-design.md`, marked **built, then removed**, carrying the measurements and the post-mortem.

**Rotate and flip done — the Crop panel is now the Geometry panel.** Quarter turns and mirroring, the eight rigid transforms of a rectangle. Not in any milestone: the capability inventory lists "rotate" but the P0–P4 table never scheduled it.

- **Two fields, eight states, no redundancy.** `Orientation { rotate: Quarter, mirror: bool }` — mirror about the vertical axis, *then* turn. ⚠ **`mirror` is one flag, not two**: a vertical flip *is* a horizontal flip plus a half turn, so separate `flip_h`/`flip_v` fields would make four states representable two ways. **Flip-vertical is a derived action**, so the UI has four buttons over two fields.
- **⚠ Composition is non-abelian, and this is where it silently breaks.** Rotating composes trivially, but flipping *after* a rotation does not: `flip_h` is `rotate = -rotate; mirror = !mirror`, because `M ∘ rot_r = rot_{-r} ∘ M`. Get it wrong and every button is right in isolation and wrong in sequence.
- **⚠⚠ The obvious property test does not catch that — verified, not assumed.** "The generators reach exactly 8 states" *passes* with the wrong abelian rule, because it still reaches all eight, just as a direct product rather than a dihedral group. The count cannot distinguish the two groups. The real guard is **`each_button_matches_its_geometric_action`**, which checks each button against an **independent corner model** — where the unit square's corners land — from all eight starting states. Sabotaged `flip_h` and watched: the count test passed, the geometric test failed. *A property test is only as good as the property.*
- **⚠ The crop follows the rotation.** `CropRect::rotated_cw` / `flipped_h`, applied alongside every orientation button — without them, rotating a cropped photo leaves the crop on entirely different pixels. In the unit square a clockwise turn is `(x, y) → (1 − y, x)`. ⚠ Round trips are exact only to `f32`: `1.0 - (1.0 - 0.1)` is 0.100000024, so the four-turn test uses a 1e-6 tolerance — a millionth of the frame, sub-pixel on any image.
- **Lossless.** An index permutation, no resampling; `orient()` inverse-maps each output pixel. The mirror is undone in *source* space after un-rotating, so `w` is the source width whatever the turn.
- **⚠ The dimension swap needed no work elsewhere**, which is worth recording because it looks like it should have: `fit_cap` uses the *buffer's* long edge (a swap does not change `max(w,h)`), `k` compares two caps, the vignette's `Region` comes from the prefix output's real dimensions, and `fit_image_size` is already derived from the returned frame.
- **Goldens 29 → 31**, and ⚠ **verified numerically against `neutral.png`, not by squinting**: `orient_cw90` *is* a quarter turn clockwise, and `orient_mirror` (180° + mirror) nets to a **vertical** flip and is *not* a horizontal one — the non-abelian composition confirmed end to end on real pixels. The 29 existing stayed byte-identical.
- **The rename:** `crop_mode` → `geometry_mode` and both labels. ⚠ `preview_edits` still resets the crop so the whole frame shows under the overlay, and must **not** reset the orientation — the preview would otherwise be oriented differently from the image being edited.
- **Accepted caveats:** (1) rotating requires entering Geometry mode, as Straighten already did; (2) it lives inside `GeometryStage` rather than earning its own prefix checkpoint — 313 MB at full resolution to avoid re-running a cheap, rarely-changed transform; (3) a *flip* mirrors the crop with the frame, so a deliberately asymmetric crop ends up on the other side; (4) older sidecars load with the identity orientation via `#[serde(default)]`.

**Library format filter done — a RAW+JPEG folder can be browsed one format at a time.** A chip per extension actually present, in the top toolbar.

- **A derived index list, not a filtered `entries`.** `Library`'s `entries`, `thumbs`, `Selection` and `ThumbLoader` are all **index-parallel**, so filtering the list itself would mean rebuilding `thumbs`, remapping every stored index and restarting the loader — on every toggle. Instead `entries` stays whole and `visible: Vec<usize>` is derived; toggling is a few hundred `usize` and no thumbnail reload. The cost is that the grid, filmstrip and both arrow-nav sites iterate `visible` rather than `0..len`.
- **⚠ The feature's real content is the selection, not the display.** Select twenty photos, hide their format, and the selection still holds them — a sync or paste then writes to photos that are not on screen. Silent, and discovered as data loss rather than as a bug. `Library::refilter` therefore always does **both** halves: recompute `visible` *and* `Selection::retain_visible`.
- **⚠ `retain_visible` follows `clamp`'s rule rather than inventing a second one.** If the active photo is pruned, the whole selection goes. Two rules for "the active index went away" is a smell, and silently *moving* the active photo changes which photo a sync copies **from**, with nothing on screen to announce it. The design doc originally said "move to a survivor"; reading `clamp` corrected it.
- **⚠ Ctrl+A is the deliberate exception**, and `select_all(n)` became `select_indices(&[usize])` because "all" now means "all visible" and the visible list is *sparse*. It adopts a new active photo when the current one is outside the set — defensible because Ctrl+A is an explicit "select these" from the user, where a filter change is a side effect. Both behaviours are pinned by tests that name the distinction.
- **⚠ It stores what is *hidden*, not what is shown.** With a shown-set, a format appearing after a folder reload would be absent from the set and therefore silently invisible. Hidden-by-exception makes "everything visible" the default and needs no maintenance.
- **⚠ The grid's row break must count the cell's *position*, not the entry index** — found in use, one toggle later. `egui::Grid` broke rows on `(i + 1) % cols`, which is right only while `i` is dense; with a filter on it fires after the wrong cells, giving gaps and rows that overflow the window. This is the **third** sparse-vs-dense index bug in this lineage (after the crop feedback loop and `render_max_dim`), so it has a test: `the_grid_breaks_rows_by_position_not_by_entry_index` lays out a sparse list both ways and asserts the index-counted one is *wrong*. ⚠ Like `cell_widths` beside it, that test reimplements the loop rather than driving the real one — it pins the rule, not the call site.
- **⚠ …and a second, pre-existing layout bug the filter merely made visible: the column count ignored egui's inter-column gaps.** `n` cells need `n*CELL + (n-1)*spacing`, not `n*CELL`. ⚠ **The failure rate rises with window width** — the gap total grows with the column count while the leftover width stays uniform in `[0, CELL)` — which is why it showed on a large monitor and not a small one, and why it had gone unnoticed. `grid_columns(avail, cell, spacing)` is pure and swept over widths by `grid_columns_leaves_room_for_the_gaps`, which asserts both that the chosen count fits *and* that one more would not.
- **⚠ `format_filter::step` exists because Develop keeps the open photo when its format is hidden** — so arrow navigation must cope with a `cur` that is *not* in the visible list, taking the nearest visible index in the direction of travel. Clamped at both ends rather than wrapping.
- **Three UI calls:** chips appear only at **≥2 formats** (a lone toggle can only blank the grid); the **filmstrip is filtered too**, since it is the same list and the same intent; the filter **resets on folder load** rather than persisting — a `Settings` field is an obvious follow-up if "always RAW only" turns out to be wanted.
- Extensions compare lowercased, so `.JPG` and `.jpg` are one chip; an extensionless file is always visible, since no control exists for it.
- **Accepted caveats:** (1) the filter is per-session; (2) hidden photos stay in `BufferCache` if visited — it is a view, not an eviction; (3) thumbnails for hidden entries still load, which is what keeps toggling instant.

**Three bugs from the first hour of real use (2026-08-12), and the two interesting ones are mine.** Recorded together because the lessons are about *inference vs. fact*, not about the individual symptoms.

- **⚠ "Reset all" did not stick across a photo switch.** `persist_current_session` wrote the sidecar only when `edits != default`, so a reset wrote nothing and **left the old file on disk** to be loaded straight back. `sidecar::remove` already existed and was simply never called. Fixed by `sidecar::persist`, which deletes on neutral. This had been documented as a "minor edge" caveat for weeks — it is a reminder that a caveat nobody has hit is just a bug nobody has hit *yet*.
- **⚠⚠ One photo opened shrinking to a few pixels, unrecoverably. The cause was a feedback loop I built, and the crop is why only one photo showed it.** The render ladder's base rung was `fit_long`, derived from `fit_image_size` — but that is the **post-geometry** size, while `downscale_to`'s cap is **pre-geometry**. Geometry crops *after* the downscale, so with a 0.588 crop: render at cap 1600 → frame 941 → that becomes the next cap → 553 → 325 → 191 → … one step per frame. **Uncropped photos have a crop factor of 1 and sit at a fixed point**, so the bug was invisible on 400 files and total on the one cropped one. `view_region::fit_cap(buffer_long, preview_max)` is now the base and depends only on the buffer.
  - **⚠ The same confusion had a second, older instance:** `k` compared a pre-geometry cap against a post-geometry size, so native-zoom placement was off by `1/crop_factor` on any cropped photo — a pre-existing bug this fix also closed. Both sides are caps now, so the crop cancels.
  - **⚠ The user's phrasing was the diagnosis.** "Zooms out *rapidly*" means a loop, not a bad value; "one frame at the right size, then snaps small again" identified the forced post-upgrade render at a fixed cap feeding the loop's next iteration. Symptom sequences are evidence — read them literally.
- **⚠ `render_max_dim` must be *derived* from `requested_region`, never stored beside it.** It began as a method and I turned it into a field during the trigger rework; two facts that can disagree then did, when `pump_full_res` cleared the region while the canvas had left a native rung. A panel edit then issued a whole-image render at a native rung, which poisoned the cached fit size. Deriving one from the other makes the disagreement **unrepresentable** — better than testing for it.
- **⚠ `RenderedFrame` now carries its `max_dim`, because "whole image ⟹ fit render" is an inference that a crop can falsify.** A native rung times a small crop factor lands *below* the preview cap, so a size-based guard fails open exactly in the case that caused the bug. Twice bitten by this inference; it is a field now. Every whole-image request uses `Session::fit_cap()` so the comparison is exact — normalising that also exposed an inconsistency for images smaller than the preview cap.
- **⚠ A found-in-passing bug: the full-resolution upgrade was not re-rendering at fit zoom at all.** The rung was unchanged and the region already covered, so the canvas requested nothing and the old buffer's texture stayed on screen — the upgrade was invisible unless you happened to be zoomed in. `pump_full_res` now issues an explicit request.

**`downscale_to` is 3.2× faster — the last sequential hot loop in the render path is gone.** Parallel across **output rows**: each output pixel averages its own source rectangle and reads nothing else, so the result is bit-identical.

- **Measured** (X-T4, release, best of 9): `downscale_to(1600)` from the half buffer **9.1 → 2.8 ms**; from a full-resolution buffer **27.3 → 8.6 ms**; `downscale_to(3123)` from full is 10.8 ms.
- **⚠ Consequence for the pending trigger rework:** sourcing the *fit* tier from the full-resolution buffer now costs **8.6 ms, less than today's 9.1 ms** from the half one. The +18 ms regression that rework was going to pay simply does not exist any more — do it before, not after.
- **Rows, not the fixed blocks `to_rgba8` uses**, and that is a deliberate difference: a 1600-wide output row already averages tens of thousands of source pixels, so there is none of the per-item dispatch overhead that made a per-pixel split of the 8-bit pack *slower than not threading at all*. The granularity was checked rather than assumed, which is the lesson that work left behind.
- **⚠ It found a pre-existing bug on the way in.** `dw`/`dh` are clamped up to 1, so a 0×5 source produced a **1×2 image of `NaN`** — the averaging loop found no source pixels and divided by zero. The empty-dimension guard fixes that *and* is what makes the row chunk width provably non-zero, which `par_chunks_exact_mut` requires. `downscale_handles_the_degenerate_sizes` pins both.
- **Bit-identity is proven against a sequential reference written inline in the tests**, over five source/output ratios chosen to be non-integral in both axes with more rows than any plausible thread count. Watched to fail by perturbing the row index.

**True full resolution done — every zoom now shows the real pixels.** What Rustroom called "100%" was a **half-size** decode that *skips demosaic entirely* (2×2 binning) while export runs a real algorithm. A full decode now starts in the background ~0.8 s after a photo settles, and every rung of the render ladder uses it. ⚠ This section describes the **reworked** version; it shipped zoom-triggered with two engines first, and the rework is the most instructive part.

- **Measured** (X-T4 `.RAF`, release, `Demosaic::Fast`):

  | | value |
  |---|---|
  | half decode (unchanged) | 985 ms → 3123×2085, 78 MB |
  | **full decode** | **3026 ms** → 6246×4170, **313 MB** |
  | `downscale_to(1600)` from half / from full | 9.1 ms / **27.3 ms** — *now 2.8 / 8.6, see below* |
  | geometry (angle) whole-buffer at full res | 203 ms |
  | noise reduction 50/50 at full res | 504 ms |
  | dehaze 60 at full res | 562 ms |
  | **region tail 1400×900 at full res** | **13.4 ms** |

- **⚠ The trigger was zoom-based first, and using it proved that wrong.** Shipped that way, measured after, reworked the same day. Compared against a properly demosaiced render: **Fit differs in 5.5% of samples (mean 0.91/255), NativeHalf in 22.6% (mean 1.69, max 211)**. So the gap is *not* at fit — it is at 1.0–1.95× zoom, an ordinary editing zoom that never crosses a 1.95× threshold. The decode is now **eager, once the session settles**. For reference: Lightroom's Develop module always works from a full decode; its Library previews are a separate browsing cache, and Smart Previews (2560 px lossy DNG) are its one opt-in downgrade.
- **⚠ A ladder, not an enum — the first version was three fixed tiers and it did not generalise.** `tier_max_dim(fit_long, buffer_long, fit, zoom)` walks rungs that **double** from fit resolution up to the buffer's own. A 3123 buffer yields two rungs (exactly the pre-feature behaviour), a 6246 one yields three, any sensor, with nothing to extend when the buffer is upgraded underneath it. Rungs double so on-screen scale cannot fall below ~0.5; they are quantized so `max_dim` does not vary continuously with zoom, which would rebuild the prefix cache on every scroll tick.
- **⚠ Why the ladder exists at all, and it is not obvious.** The tempting design — "native mode just uses the full-res buffer" — is quietly disastrous. Native mode's `max_dim` was one value keeping scale in (0.51, 1.0]; doubling the buffer **halves** that to ~0.26, and the region is derived from the viewport **in rendered pixels**, so a 1400×900 viewport would need a **5385×3462** region — 18.6 Mpx instead of 1.26, turning the 13.4 ms tail into **~180 ms**. The feature would have made slider response *worse* across most of its own zoom range.
- **⚠ State the invariant precisely or a test written from it fails.** "Scale stays in (0.5, 1.0]" is false twice over: at the fit rung there is no lower bound (zoomed out, fit is arbitrarily small), and at the *top* rung scale exceeds 1.0 because the file holds no more data. Testable form: **for a rung above fit and below the buffer, scale ∈ (0.5, 1.0]**. `a_rung_below_the_buffer_never_magnifies` sweeps both buffer sizes.
- **One engine, whose buffer is replaced.** The two-engine version (half buffer for fit, full for 1:1) was right only while fit kept using the half buffer; once every rung renders from the full one, the half engine is dead weight. Dropping the old engine disconnects its channel so its worker returns on its own. ⚠ **Its prefix cache goes too** — a one-off cost at the moment of upgrade. The rework removed **87 lines net**.
- **⚠ The dwell is not redundant with the 180 ms open debounce.** There is already an implicit ~1.2 s before a `Session` exists (debounce plus a ~1 s half decode) — but a **`BufferCache` hit creates a `Session` instantly**, so arrowing *back* through recently viewed photos would fire a 3 s, 313 MB decode each. `full_res::SETTLE` is 800 ms of session age.
- **⚠ The trigger must schedule its own repaint.** egui does not redraw an idle window, so without `request_repaint_after` the dwell could expire with nothing to notice it and the decode would start only when the user next moved the mouse.
- **⚠ Handover clears `rendered_region` and `requested_region`.** Region rects are in *rendered* pixels, and those coordinates change with the buffer; reusing one would describe the wrong part of the image.
- **Reuses `DecodeWorker`** (second instance, `max_concurrent: 1`, `DecodeOptions::linear_scene()` injected) — abandon-don't-abort, sequence numbers and all four of its tests, for one constructor call. The baseline it renders is discarded so before/after does not change under the user. A failed decode leaves the ladder topping out at the half-size buffer, i.e. the pre-feature behaviour.
- **Cache: `MID_BUDGET_BYTES` 256 → 512 MiB, plus a new `MIDS_CAP = 6`.** 512 clears one full-res checkpoint (~313 MB) but not two — deliberate, since a second buys ~200 ms on a rare interaction for double the memory. ⚠ **512 rather than 320 because 320 covers only 28.0 Mpx**, and Fuji's current 40.2 Mpx bodies (X-T5, X-H2) would get *zero* native checkpoints; 512 covers 44.7 Mpx. The sizing is a **compile-time assertion**, not a comment. ⚠ **The count cap fixes a pre-existing leak**: dragging Straighten mints a new post-geometry key every frame, so the mids tier filled with stale checkpoints bounded only by bytes — a bigger budget would simply have retained more garbage. A chain needs at most 3 mids, so 6 keeps it plus one previous state.
- **Memory: ~1.32 GB worst case** for one photo zoomed in with all three prefix stages active (78 half buffer + 156 other cache entries + 313 full buffer + 147 fit cache + 626 native cache).
- **Accepted caveats:** (1) **~3 s of background CPU and 313 MB per photo you stop on**, whether or not you zoom — the price of being correct by default; (2) ~1.32 GB worst case, now reached on any photo you dwell on rather than only zoomed ones; (3) **between opening and the upgrade landing (~4 s) every rung is still the binned half-size decode** — better than "until you zoom past 1.95×", but not instant; (4) the prefix cache is lost at the moment of upgrade, so the first render after it is cold; (5) prefix sliders cost ~0.2–0.6 s per frame at the top rung — one checkpoint softens it, the rest is the price of a whole-buffer prefix, and tail sliders stay at 13.4 ms; (6) **⚠ the view uses `Demosaic::Fast`, not the export preset's setting** — matching it means plumbing a parameter through `DecodeWorker`'s injected decode fn, and the measured Fast-vs-Best gap is small, so it is a contained follow-up; (7) switching photos and back re-decodes, since the full-res buffer is not cached across sessions; (8) the before/after baseline stays preview-resolution.

**The 8-bit pack is 10× faster — and the task's own name was wrong about why.** `render_engine::pack` was the largest slice of a cached preview frame; it is now the smallest.

- **Measured** (X-T4 `.RAF`, release, best of 9, 8 threads). **Two independent multipliers**, kept as separate commits so the credit goes where it is due:

  | | fit 1600×1068 | native 3123×2085 |
  |---|---|---|
  | `Vec::push` loop (the original) | 4.59 ms | 17.81 ms |
  | preallocate + sequential fill | **1.16 ms** | 4.42 ms |
  | + parallel in 8192-px blocks | **0.46 ms** | 2.21 ms |

- **⚠ Most of the win was not parallelism.** The task was named "parallelise the RGBA8 pack", but the measurement that started it showed `export::to_rgb8` doing ¾ as many output bytes on the same buffer in ⅕ the time — **3.7× cheaper per byte, with no thread involved**. `Vec::push` carries a capacity check per byte and does not vectorise; `.collect()` over an exact-size iterator allocates once. Dropping the push was a 4.0× win on its own, threading a further 2.5×.
- **⚠ The obvious parallel spelling is *slower than not threading at all*.** `par_chunks_exact_mut(4)` — one pixel per rayon task — measured **1.64 ms against 1.13 ms sequential**, because per-item dispatch stops the inner work vectorising. Coarse blocks with a plain sequential loop inside get both: **0.46 ms**. `PACK_BLOCK_PX = 8192`, and the plateau is flat from ~1024 up (52.8 / 58.9 / 61.3 GB/s at 1024 / 8192 / 65536), so it sits mid-plateau rather than on a tuned peak. **This also disproves the tempting explanation** that the operation is memory-bandwidth-bound and untreadable — 61 GB/s against 24 says otherwise. Both wrong shapes are recorded in the `PACK_BLOCK_PX` doc comment so nobody re-derives them.
- **One quantizer, on `ImageBuf`.** `to_rgb8` / `to_rgba8` share a private `quantize`. `export::to_rgb8` keeps its name and signature and delegates, so no call site churned and its existing `to_rgb8_quantizes_and_clamps` became the guard that delegation preserved behaviour. **Every export got faster for free** — it was the same sequential code. **`app` still has no `rayon` dependency**, preserving the separation recorded for `ThumbLoader`.
- **⚠ The golden harness keeps its own private copy, deliberately.** A golden that quantizes through production code cannot witness a change to production code. That third copy is confined to a test, where drift is a visible failure rather than wrong pixels — and it is precisely what let the 29 checked-in PNGs act as an independent check on this change.
- **⚠ No zero-size guard here, unlike `map_pixels_xy` — and that is correct.** The block widths are non-zero constants, so a zero-width image just yields an empty `Vec`. `map_pixels_xy` chunks by *row*, which is 0 for a zero-width image, and `par_chunks_exact_mut(0)` panics. Chunking by a fixed block rather than a row is what buys the difference. Pinned by `the_conversions_handle_an_empty_image`.
- **⚠ Bit-identity could not be proven by the existing tests.** `every_cached_frame_matches_a_cold_render` compares two frames that would *both* go through the new pack. So `core-image`'s tests carry **sequential reference loops written inline**, deliberately not shared with production, on a fixture with negative, >1, `NaN` and exact-rounding-boundary samples. Watched to fail (both reference tests) with `dst[3] = 254`.
- **⚠ `NaN` reaches 0 via the `as u8` cast, not the clamp.** `f32::clamp` returns `NaN` for `NaN`; Rust's float→int casts saturate. Noted in `quantize`'s doc because "clamp handles NaN" is the obvious wrong reading.
- **Accepted caveats:** (1) a third copy of the quantization lives in the golden harness, on purpose; (2) `vec![0u8; n]` writes every byte twice — 0.09 ms at fit, measured and accepted rather than fixed with unsafe; (3) the pack now competes for the global rayon pool, but it runs on the render worker where the pipeline stages already do; (4) gains shrink on small images where rayon's overhead is a larger fraction, which only affects tests.

**Per-stage prefix checkpoints done — a Dehaze drag is ~1.9× faster.** The prefix is no longer cached as one lump; every stage boundary is its own checkpoint, so a change re-runs only what is downstream of it.

- **Measured first, and the measurement corrected the plan twice** (X-T4 `.RAF`, release, best of 5). Fit = 1600 px / 21 MB per buffer; native = 3123 px / 78 MB.

  | step | fit | native |
  |---|---|---|
  | `downscale_to` | 9.0 ms | **2.2 ms** (already small enough — it is a clone) |
  | geometry, angle 3° | **13.6 ms** | **52.2 ms** |
  | geometry, crop only | 1.0 ms | 3.9 ms |
  | noise reduction 50/50 | 31.4 ms | 117.4 ms |
  | dehaze 60 | 32.3 ms | 115.6 ms |
  | deep clone of one checkpoint | 0.5 ms | 2.1 ms |

  And the resume points, with all three prefix stages active:

  | what you drag | resumes at | cost |
  |---|---|---|
  | geometry / Straighten | the downscale | 101.2 ms |
  | noise reduction | after geometry | 87.5 ms |
  | **Dehaze** | **after NR** | **49.7 ms** (was 95.4) |
  | any tail slider | the final | 14.4 ms |

  Reproduce with `cargo run --release -p app --example bench_preview <raw>`.
- **⚠ Correcting this file, again — the post-geometry checkpoint is worth far more than the old RESUME block claimed.** That note said a second checkpoint's only win was the ~9 ms downscale, reasoning about *changing* Straighten (where it is right: geometry is first, so changing it invalidates everything by definition). But the checkpoint's real job is the other direction — with an angle set, every NR or Dehaze drag was re-running a **13.6 ms / 52.2 ms** rotation. Note the asymmetry inside geometry: a crop alone is ~1 ms, so essentially all of that is the rotation.
- **⚠ The post-downscale checkpoint is free at native, and would have been a terrible deal otherwise.** `downscale_to` returns a *clone* when the image is already small enough, so caching checkpoint 0 natively would cost 78 MB to save 2.2 ms. The engine already holds the buffer as `Arc<ImageBuf>`, so the chain seeds from that Arc and stores nothing. At fit it is a real 21 MB / 9.0 ms checkpoint and is cached normally. `the_native_seed_shares_the_buffer_rather_than_copying_it` pins both halves by counting mid entries (2 at native, 3 at fit).
- **⚠ A missing cache key is now a compile error, not a test failure.** `build_prefix_steps(edits, scale) -> Vec<PrefixStep>` returns `(key, stage)` pairs, and `PrefixKey` is **defined through it** — `PrefixKey::new` is `upto(&build_prefix_steps(..), len, scale)`. A prefix stage with no `PrefixStepKey` variant does not compile. Same upgrade `Edits::merge_from`'s exhaustive destructure made over a test. `build_pipeline_split_in_region`'s prefix half is likewise `build_prefix_steps(..).map(|s| s.stage)`, so the pipeline and the keys are one list with two consumers. The old tripwire (`the_prefix_holds_geometry_noise_reduction_and_dehaze`) is **kept**: it pins composition and order, which the compiler cannot.
- **An inactive stage costs nothing, with no special-casing.** It produces no step, so the cumulative key after it *equals* the key before it — the checkpoints coincide rather than duplicating a buffer. Chain length is `active prefix stages + 1`.
- **Two cache tiers that cannot evict each other.** `finals` holds complete prefix outputs, cap 2 — byte for byte the old policy, so the zoom guarantee (fit and native both warm) is preserved unconditionally and a native render can never evict the fit final for its own intermediates. `mids` holds the intermediates under `MID_BUDGET_BYTES = 256 MB`, plain LRU. **Deepest-first retention needs no rule of its own**: within a render checkpoints are inserted shallow→deep, so the deepest is the MRU and the shallowest is evicted first, which is the order that saves the most upstream work.
- **⚠ Be honest about what the budget buys: on an X-T4 it never bites.** Worst case the mids come to 219 MB, under the ceiling, so memory goes **~99 MB → ~318 MB** — the same as an unbudgeted chain. The budget earns its place as a ceiling for larger sensors (a 100 Mpx file's native mid is ~300 MB, so zero survive and native degrades to today's behaviour) and as a guarantee that the degradation is *designed*. **If ~318 MB proves too much in use, that constant is the one thing to turn down.**
- **⚠ A shrinking prefix would have broken the zoom guarantee, and the test is what found it.** Turn Dehaze off and the post-NR checkpoint becomes the *final* one — but it is sitting in the budgeted tier, where a large render can evict the very thing zooming back relies on. `render_cached` promotes it when it resumes at the final without running anything; `a_shrinking_prefix_does_not_serve_the_wrong_checkpoint` pins it.
- **⚠ The correctness tests would all pass with the cache deleted.** So `render_cached` returns the frame **and how many prefix stages actually ran** (the worker discards it), and `a_change_reruns_only_what_is_downstream_of_it` asserts 0 / 1 / 2 / 3 for a tail / dehaze / NR / geometry change. Watched to fail (`left: 3, right: 0`) with both cache capacities zeroed. `every_cached_frame_matches_a_cold_render` stays the master and its sequence now visits every checkpoint and returns, with the `assert_ne!` guards extended.
- **⚠ A compile-time guard has to be a free-standing `const _`, not an associated one.** `const _BUDGET_IS_USABLE: () = assert!(Self::MID_BUDGET_BYTES > 0)` inside `impl PrefixCache` compiles happily with a budget of 0 — associated consts are only evaluated where they are used, so it is a guard that does not guard. Moved to a module-level `const _: () = assert!(..)` and **verified by setting the budget to 0 and watching it fail**. Worth remembering for any future compile-time invariant.
- **⚠ `PipelineStage` does *not* need importing to call `stage.apply(..)` on a `Box<dyn PipelineStage>`** — trait-object methods resolve without the trait in scope. The plan said otherwise and clippy caught the unused import.
- **⚠ Restoring a file with `mv file.bak file` fools cargo.** `mv` preserves the backup's older mtime, so the fingerprint looks unchanged and cargo reuses the artifact built from the *sabotaged* source — which showed up as seven tests failing against correct code. `touch` after any such restore.
- **Cost paid:** `PrefixKey` is no longer `Copy` and allocates a ≤3-element `Vec` per render; a cold chain pays one deep clone per active stage instead of one total (+1.0 ms fit, +4.2 ms native, against 13–117 ms per avoided stage).
- **All 29 goldens stayed byte-identical** through every commit, which is the proof this is a caching change and nothing else. The four pre-existing key/cache tests passed **unchanged** after `PrefixKey` was redefined, which is the proof its meaning was preserved.
- **Accepted caveats:** (1) ~318 MB of prefix cache against ~99 MB before; (2) Straighten still costs full price when you drag *it* — structural, geometry is first; (3) a crop-only geometry checkpoint buys ~1 ms and costs a whole buffer, cached anyway because keying on "is this stage expensive" would make cache contents depend on a cost heuristic rather than on correctness; (4) more clones per cold render; (5) nothing here helps the first render after opening a photo — the cache is cold on open.

**Preview prefix cache done — editing with NR on is 3.5× faster.**

- **The measurement redirected the design.** The original scope (recorded here) was "cache the downscaled preview". Decomposing a neutral 21.1 ms render first — `downscale_to` **9.0** / pipeline 7.5 / RGBA8 pack 4.4 — showed the downscale is 43% of a *neutral* render but only 18% of an NR-on one (46–50 ms). The real waste was that **NR runs first, so moving Exposure re-ran ~29 ms of denoising whose parameters never changed.** So the checkpoint went *after* NR, which subsumes the downscale win. It also corrected the stale ~14 ms figure for `downscale_to`.
- **`build_pipeline_split(edits, scale) -> (prefix, tail)`** — prefix = `geometry` → `noise_reduction`; tail = everything else, ending in the output transform. **`build_pipeline` is now defined as `prefix ++ tail`** (via `Pipeline::into_stages`), so the two constructions *cannot* drift. Add a stage to the split, never to `build_pipeline`.
- **`PrefixKey`** (co-located with the split, on purpose) = `{ geometry, noise_reduction, scale }`, compared by `==` not hashed. `scale` is in it because it sets the NR radii. An `f32` in a `PartialEq` is safe here: `NaN` compares unequal to itself, failing toward a cache *miss*.
- **⚠ The failure mode this guards is silent staleness** — someone adds a stage to the prefix, forgets the key, and the cache serves wrong pixels with nothing failing. Two tests block it: `the_prefix_holds_only_geometry_and_noise_reduction` (tripwire on composition) and `prefix_key_ignores_every_downstream_field` (proves every other field is downstream). `all_edits()` in those tests lists every `Edits` field **explicitly** rather than using `..Default::default()`, so adding a field breaks compilation and forces a decision about which half it belongs to.
- **The scale must be predicted, not measured.** `render_once` derives it from the *downscaled* image's dimensions — which does not exist on a cache hit. `rendered_long_edge(buffer_long, max_dim)` computes it from `max_dim` instead, asserted against `downscale_to`'s real output for both the scaling-down and already-small-enough cases.
- Cache lives in the `RenderEngine` worker thread — sole renderer, so no locking. One entry, replaced on miss; a new photo builds a new engine, so it is per-session with no invalidation logic of its own. `render_once` stays pure and **uncached**, serving as the reference the cached path is tested against.
- **A 0.6 ms deep clone is paid every frame**: `PipelineStage::apply` consumes its input (the ownership that keeps the GPU-port seam clean), so a cached image must be copied before the tail runs. Kept deliberately — 15× cheaper than the 9 ms it avoids — rather than reshaping the trait.
- **Measured** (X-T4, 1600 px preview, release, best of 5): NR both 50 cold **46.0 ms** → **13.1 ms** on a hit. Reproduce with `cargo run --release -p app --example bench_preview <raw>`.
- **`every_cached_frame_matches_a_cold_render`** is the test that matters: it pushes a sequence (hit / downstream change / NR change / return / geometry change) through one engine and asserts every frame equals a cold `render_once`. Three `assert_ne!` guards up front stop it passing trivially. All **20 goldens stayed byte-identical** through the whole feature, which is the proof `build_pipeline`'s behaviour never changed.
- **Caveats:** cold on open (this speeds up *editing*, not opening); **Straighten is still full cost** since geometry is upstream, but **dragging the crop rectangle hits the cache** because `preview_edits` resets the crop in crop mode, so the pipeline never sees it change; one entry, so alternating between two heavy NR settings misses every time; and the RGBA8 pack (4.4 ms, still a sequential `Vec::push` loop) is now ~35% of a cached frame — the obvious next target.

**Batch export done.** The last of the *selection* work, and the one that could not borrow sync's shortcuts. (It does **not** finish Phase 2 — see the milestone status at the top.)

- **One `Export…` button, not two.** The count decides: one selected photo exports that photo, several export all of them — **through the same worker**. The old single-photo path (its own `rfd` save-file dialog, its own inline decode+render+encode) is **gone**, which removes a second implementation of the render that could have diverged from `export_one`. Consequence, accepted: a single export now picks a destination *folder* rather than a filename, and in exchange gains the quality and long-edge controls it never had.
- **⚠ Unlike sync, this decodes.** Sync is 200 sidecar writes; batch export is 200 full-resolution decodes at ~11 s each. That one difference is what forced a worker thread, a progress line and cancellation — none of which sync needed.
- **`app::batch_export` is sequential on purpose.** The pipeline stages are already rayon-parallel *internally*, so exporting several photos at once would contend for the same cores while multiplying peak memory — a 26 Mpx decode is ~312 MB as f32 RGB. One at a time keeps the ceiling at roughly one image.
- **The decode fn is injected**, the `DecodeWorker` pattern, so the entire loop — naming, collisions, cancellation, progress, the failure path — is unit-tested **with no image fixtures**. Only the decode itself is untestable, and it is one line. 17 tests.
- **⚠ The resize happens *before* the pipeline, not after.** Rendering at full resolution and shrinking the result would resample **sRGB-encoded** pixels, which is gamma-incorrect; `downscale_to` runs on the linear decode instead, where averaging is meaningful. It is also the path the preview already takes, so it reuses `downscale_to` and the `RenderScale` seam **with no change to `pipeline` at all**, and it is faster. Consequence: sharpening and NR radii scale with the output, preserving the *look* rather than the pixel radius, so a resized export is not a downsampled full-res export and there is no output-sharpening pass.
- **⚠ A collision can happen in an empty folder.** `a.RAF` and `a.jpg` both map to `a.jpg`, so the worker tracks the names it has **claimed this run**, not just what is on disk.
- **⚠ `Decision::Cancel` carries no `apply_to_all`.** Ticking "apply to all" and then cancelling must arm nothing — and here that is *unrepresentable* rather than enforced by a rule, which is strictly better than `Settings::apply_delete_confirm`, where the flag and the outcome are separate values held together only by a test. It also means one fewer test, because there is no state left to assert about.
- **⚠ Cancel drops the photo in flight — "abandon, don't abort".** libraw's `unpack` still cannot be interrupted, so that decode runs to completion on its thread; but the flag is checked **again after the decode**, so its result is discarded rather than written, and the UI drops the `ExportWorker` immediately instead of waiting. From the user's side the cancel is instant and the photo being worked on is *not* exported — the same trade `DecodeWorker` makes for superseded previews, with no unsafe FFI. Dropping the worker also drops the decision channel, so a worker blocked on a collision prompt sees `Err` and exits rather than hanging.
- **The worker blocks on a collision**, sending `ExportEvent::Collision` and waiting on a second channel, so the UI must drain `events()` every frame. `pump_export` also calls `request_repaint_after(100ms)` while a run is live — nothing else would wake the app, since the work is off the UI thread.
- **A pre-existing bug fixed on the way in:** `export_dialog` wrote a sidecar next to the *exported* file. `sidecar::path` appends `.json`, producing `export.jpg.json` — and JPEG is a supported **input** format, so reopening an exported file loaded those edits and applied them **a second time** to pixels that already had them baked in. `persist_current_session` already writes the source's sidecar, so the line was redundant as well as wrong.
- **Accepted caveats:** (1) a cancelled photo's decode still runs to completion in the background, wasting up to ~11 s of CPU, though nothing is written; (2) a resized export is not a downsampled full-res export; (3) JPEG only — TIFF and PNG are a separate feature; (4) no filename templating or per-file naming, just `<stem>.jpg` into a chosen folder; (5) no undo — export creates rather than destroys, and overwriting is guarded by the prompt; (6) export options are not persisted between runs; (7) sequential, so 47 photos is ~47 × 11 s — the `user_qual` demosaic finding is the lever that would move that, tracked separately.

**Multi-selection & sync done.** App-layer only; the 23 goldens stayed byte-identical.

- **`app::selection`** — `Selection { active, set, anchor }` replaces `Library.selected: Option<usize>`. **⚠ The invariant is the whole design:** `active == Some(i)` implies `i` is selected, `active == None` implies nothing is. A sync would otherwise have a source outside its own selection, or none at all. A `check()` helper asserts it after every operation in the tests.
- **⚠ Cmd-click and Shift-click never move the active photo** — only a plain click or arrow navigation does. Lightroom moves it on shift-click, but here that would fire a RAW decode mid-range-select, and it fights the order of the task: pick the source, *then* extend the targets. Two consequences, both accepted: Cmd-clicking the active photo is a no-op, and `extend_to` re-inserts the active index because a preceding Cmd-click can have moved the anchor away from it.
- **`app::sync` decodes nothing.** Every target's edits live in a JSON sidecar, so a sync is `load → merge_from → save` — 200 photos is 200 tiny file writes, not 200 × ~11 s of RAW decoding. That single fact is why there is no progress bar, no worker thread and no cancellation. A failed write is collected and reported rather than aborting the batch. **Batch export will not have this luxury.**
- **`app::sidecar`** was extracted from `main.rs` so `sync` could reach it and so it could be tested at all. Its tests need **no image fixtures**: `path` only appends `.json`, so a sync touches nothing but sidecars and the photo files never have to exist.
- **⚠ `prior: Vec<(PathBuf, Option<Edits>)>` — the `Option` is load-bearing.** `None` records "this photo had no sidecar", so undo *deletes* the file the sync created instead of writing a neutral one and littering the folder.
- **⚠ `ActionKind` lost its `Eq` derive** when it gained an `Edits` (`f32` is `PartialEq` only), and the payload is **boxed** as `Sync(Box<SyncAction>)` — clippy's `large_enum_variant` caught that an inline `Edits` would make *every* entry in the undo/redo stacks a few hundred bytes, including the zero-sized `PhotoEdit`, which is by far the most common. `Sync` entries are global like `PresetDelete`, so `forget_photo_edits` leaves them be.
- **⚠ The live-session hazard.** The active photo is never a sync target, so a sync cannot make the open session stale — but you can sync, *switch* to a synced photo, then Ctrl+Z, which rewrites its sidecar underneath an open session. `reload_if_affected` reloads the edits and resets that session's history; without it the canvas silently disagrees with disk until you switch away and back.
- **`EditGroups` is now doing its third job** — copy/paste, presets and sync all share one partition and one checkbox dialog. `sync_groups` is kept separate from `paste_groups` so the dialogs do not reconfigure each other.
- **Ctrl+V — and clicking a preset — apply to the whole selection**, syncing directly: copy or pick a preset, select several in the grid *or* the filmstrip, apply. Both go through one `apply_to_selection`, which returns `(changed, failed)` and lets the caller word the status line, because "pasted" and "applied preset" describe the same work differently. Each spans two mechanisms (the open photo through its session, the rest through their sidecars), so the resulting actions are wrapped in **`ActionKind::Batch`**: one Ctrl+V, or one preset click, must stay one Ctrl+Z. A lone action is never wrapped. `handle_clipboard_keys` moved from `develop_body` into `ui()` so the keys reach a Library-grid selection too, and `sync_targets` keys on the open *path* rather than the active index — in Develop they are the same photo, but a paste from the grid may have a selection that excludes whatever is open.
- **⚠ `forget_photo_edits` reaches inside a batch.** A nested `PhotoEdit` belongs to a session that is gone and would pop a *different* photo's history — but dropping the whole batch would strand the sidecar half of a paste with no way to undo it. So the member is removed and the rest kept; a batch left empty is not an undo step and goes. Caught by writing the test, not by review.
- **All five dialogs use `egui::Modal`, not `egui::Window`.** A Window opens at the **top-left** and is genuinely easy to miss; a Modal centres on the viewport, dims the backdrop and blocks clicks behind it. Clicking outside cancels — which for the delete confirm also discards the "don't ask again" tick, exactly like the Cancel button.
- **Accepted caveats:** (1) Cmd-clicking the active photo does nothing. (2) No Auto-Sync. (3) Sync only from Develop — the source must be the open photo. (4) No progress UI or cancellation, justified above. (5) One undo step for the whole batch, not per photo. (6) Selection resets on plain navigation and on folder reload. (7) Sync writes sidecars for photos that had none, which is visible in the folder.

**Presets & copy/paste done — moving an `Edits` around.** App-layer only: no pipeline stage was touched, and all 23 goldens stayed byte-identical, which is the proof.

- **`EditGroups` (`edit-model`) partitions `Edits` into six groups** — White Balance / Tone / Color / Detail / Effects / Geometry — and drives `Edits::merge_from(&src, groups)`. One type serves both consumers, which is why presets and copy/paste are one feature and not two. `EDIT_GROUP_NAMES` + `get`/`get_mut`/`only(i)` mirror the `HSL_BAND_NAMES` pattern, so the checkbox UI and the tests index the same table.
- **`Default` is everything except Geometry**, deliberately: a crop framed for one composition reframes another, and a preset built on a 3:2 crop would reshape every photo it touches. `version` is a schema marker, not an edit, and never transfers.
- **⚠ `merge_from` destructures `Edits` exhaustively.** Adding a field is then a **compile error** until someone gives it a group — without that, a new field would silently never transfer and nothing would fail. Same class of bug as `PrefixKey`, but the guard is in production code rather than a test fixture.
- **The partition is tested as a partition, generically — no field lists.** Coverage: `merge(ALL) == src`, which alone catches an ungrouped field. Disjointness: clear group `g` from a fully non-neutral `Edits`, then check that what every *other* group transfers is unchanged — a field in two groups fails this without any test needing to know field names. Plus a clear-then-restore round trip per group. **Verified by deliberately putting `sharpening` in two groups**, which failed with "clearing Detail changed what Effects transfers".
- **`app::presets`** — **one JSON file per preset** (`{ name, groups, edits }`), not one file holding all of them: a preset is then a shareable artifact, add/delete are plain file ops with no read-modify-write race, and one corrupt preset cannot take the rest down. **The preset stores its own group mask**, chosen at creation, so a "punchy tone" preset never disturbs white balance; copy/paste picks groups at *paste* time instead.
- **⚠ Filename sanitizing is load-bearing, not cosmetic** — the name is free text from the UI and becomes a path, so `../../evil` must not escape the directory. It is the one place in this feature where user input reaches the filesystem, and it has its own test. The display name is stored *inside* the file so it survives sanitizing. **Known limitation, tested rather than hidden:** sanitizing is many-to-one, so `a/b` and `a_b` share a file and the later save wins. Hashing would fix it at the cost of a directory nobody can read by hand, which is most of the point of one file per preset. Only a name that sanitizes to *empty* is rejected — `"///"` becomes `___.json` and is fine.
- **Deleting a preset trashes it rather than unlinking it, and Ctrl+Z restores it.** `<config>/rustroom/trash/`, a **sibling** of `presets/` — nesting it would oblige every present and future globber of the presets dir to exclude it, a standing trap. Filenames are `<13-digit unix millis>-<name>.json`, and that prefix does **two** jobs: it orders eviction and undo without trusting file mtime (rsync and backup restores rewrite mtime, which is not a fact about when anyone deleted anything), *and* it stops a re-created, re-deleted preset from clobbering its own earlier trashed copy. **⚠ Two deletions inside one millisecond** — trivial to produce; any test doing two in a row does it — bump the timestamp rather than overwrite.
- **`TRASH_CAP = 20`, evicted at delete time.** A cap on *entries*, not bytes, chosen from a measurement: a worst-case preset is **2809 bytes**, so 20 is ~56 KB and disk space is never the binding constraint — what degrades is the directory's comprehensibility. An **age cap was rejected**: the entry you want back is precisely the one that just silently expired, and it would make correctness depend on the system clock.
- **`app::action_log` — one chronological undo stack across photo edits *and* preset deletions.** Ctrl+Z walks back through both in the order they happened, so "delete a preset, change a setting, Ctrl+Z twice" brings the preset back, and several deletions restore in a row. **`ActionLog` stores only *which* stack the next undo should pop** (`PhotoEdit` / `PresetDelete { name }`); the payloads stay where they already live — snapshots in `Session::history`, deleted presets in the trash — so nothing is duplicated and both existing mechanisms work unchanged. The toolbar's Undo/Redo buttons drive it too, and the Undo label reads "Undo delete '<name>'" when that is what it would do, so it never silently does the surprising one.
- **⚠ `History::push` now returns `bool`.** It is a no-op when the value is unchanged, and recording a step in the log that the history silently dropped would desynchronize the two — the next Ctrl+Z would pop the wrong stack. Every caller must honour the return.
- **⚠ `forget_photo_edits()` on every session change.** `Session::history` dies with its session, so a `PhotoEdit` entry that outlived it would make an undo pop *this* photo's history and revert an edit the user never made here. Preset deletions are global and survive. Both the undo *and* redo stacks are swept.
- **Restoring is by name (`PresetStore::restore(name)`), not "newest".** An undo must target its own deletion however the trash was reordered by others in between. `Ok(None)` when it has been evicted past the cap, which the status line reports rather than failing silently.
- **The two photo-edit sites sit inside closures already holding `&mut self` through `self.session`**, so they set a local `photo_edited` flag that `develop_body` records after the panels close; `draw_crop_overlay` returns `bool` for the same reason. There is no trash browser and no "Empty trash" button, by choice.
- **⚠ Where these files actually live is platform-specific, and it is *not* `~/.config` on this machine.** `dirs::config_dir()` follows each platform's own convention, so on **macOS it is `~/Library/Application Support/rustroom/`**, on Linux `$XDG_CONFIG_HOME` (usually `~/.config/rustroom/`), on Windows `%APPDATA%`. Worth stating flatly because the first draft of this section said `~/.config` and sent a check looking in a directory that does not exist on macOS.
- **`app::settings`** — Rustroom had **no settings system at all** before this; nothing survived a restart, not even `show_filmstrip`. Now `<config dir>/rustroom/settings.json` holds one flag (`confirm_preset_delete`). **`load()` is infallible**: a missing *or malformed* file yields the defaults, because a corrupt settings file must never brick the app — the same forgiving posture the sidecars take. Saved on change, not on quit. Deliberately one field; others move in when actually wanted.
- **⚠ "Don't ask again" must only apply on Delete.** Tick it, think better of the deletion, hit Cancel — and the guard you just declined to use must still be armed. The rule lives in `Settings::apply_delete_confirm(ConfirmOutcome)`, a pure function separated from the egui code precisely so it is testable; `cancelling_never_suppresses_the_confirmation` pins it, and the dialog keeps the tick as *scratch* state until Delete is clicked.
- **Both stores take their path by injection**, so tests run against temp directories and never touch the real home directory — the same pattern `DecodeWorker` uses for its decode fn. A local `TempDir`/`TempFile` guard with a `Drop` impl avoids adding a `tempfile` dependency.
- **⚠ Cmd/Ctrl+C and +V must be read as `egui::Event::Copy` / `Event::Paste`, never as key presses.** `egui-winit` matches the clipboard chords first, pushes the semantic event and **returns without emitting a `Key` event at all** (`egui-winit/src/lib.rs:1005`), so `key_pressed(Key::C)` can never fire — which is exactly how the first version silently did nothing on macOS. Worse, `Event::Paste` is only pushed **when the system clipboard already holds non-empty text**, so a copy that does not write there leaves Ctrl+V dead on a freshly booted machine.
- **`app::edit_clipboard`** therefore puts a **tagged envelope** on the system clipboard, which also makes copy/paste work between two running instances. **⚠ The tag is load-bearing:** every `Edits` field is `#[serde(default)]`, so a bare `Edits` deserializes happily from **any** JSON object — `{}` included — and a stray paste would silently reset the photo to neutral. `decode` refuses anything without the marker; `an_empty_json_object_is_refused` pins it.
- **UI:** a collapsible **left** panel (Lightroom's placement, and the right panel already scrolls through six sections). Unlike the Filmstrip toggle, **Presets shows without a `Library`** — it is just as useful on a single-file open. Ctrl+C copies; **Ctrl+V pastes with the last-used groups, no dialog**; "Paste…" opens the chooser. Both keys are gated on `ctx.memory(|m| m.focused())`, the way arrow-nav already is, so Ctrl+C in the name field is not hijacked. Applying anything is one `history.push` → **one undo step, for free**, because `History<Edits>` is snapshot-based. One `Modal` enum, so two dialogs cannot contradict.
- **Two egui borrow shapes worth remembering** (both cost a compile error before they were fixed): `if let Some(s) = &self.session { self.clipboard = … }` holds an immutable borrow across a mutable one — use `self.session.as_ref().map(|s| …)` instead; and `match self.modal { … => self.some_modal(ctx) }` keeps the scrutinee borrowed across a `&mut self` call — decide *which* modal into a local enum first, then dispatch.
- **New dependency:** `dirs` (cross-platform config dir). CLAUDE.md's "avoid platform-specific assumptions" rules out hand-rolling `$HOME`.
- **Accepted caveats:** (1) **a preset resets, it does not merge** — a preset whose Tone group is on but whose tone values are neutral will *reset* the target's tone. Correct (the preset asserts "tone is this"), matches Lightroom, and surprises people once. (2) No shipped presets; the panel starts empty. (3) Flat list, no folders or tags. (4) Not Lightroom compatible — no `.xmp`/`.lrtemplate`; presets are plain JSON copied by hand. (5) No rename — save under the new name and delete the old. (6) The clipboard payload rides the **system** clipboard, so it survives between instances but is plain text anyone can read or hand-edit. (7) A preset now applies to the whole selection, like a paste. (8) The trash has no browser and no manual empty — an entry is recoverable via undo, or by hand from the trash directory, until 20 further deletions push it out.

**PNG/TIFF export done, with sRGB profiles everywhere.** JPEG was the only output; now five.

- **`ExportFormat { Jpeg, Png8, Png16, Tiff8, Tiff16 }` is flat, not `format` + `bit_depth`.** There is no 16-bit JPEG, and a separate depth field would need a rule saying so — flattening makes the invalid state **unrepresentable**, the same reasoning behind `Decision::Cancel` carrying no `apply_to_all`. It lives in `export` (which owns encoding) and gained serde there, exactly as `Demosaic` lives in `raw-decode`.
- **One `save(image, path, format, quality)` dispatcher replaced `save_jpeg`**, so no caller can branch on format by accident. `quality` stays a plain parameter rather than `Option<u8>`: the UI keeps its value while PNG is selected, and an `Option` would put "is this lossy" in a second place that could disagree with `is_lossy()`.
- **⚠ 16-bit precision is real, not interpolated.** The pipeline is `f32` end to end and libraw hands us 16-bit, so a 16-bit file carries what an 8-bit one discards. Pinned by `sixteen_bit_output_really_carries_more_than_eight`, which writes `1/512` — a value 8 bits cannot represent — and asserts it reads back as **128** in the 16-bit formats and **0** in the 8-bit ones. **Without that test a silent 8-bit downgrade passes everything else**: right dimensions, opens fine, looks correct.
- **lcms2 landed, for exactly one job**: `srgb_icc()` emits a static sRGB profile (588 bytes) once behind a `OnceLock`, attached to every format via `ImageEncoder::set_icc_profile`. **JPEG got tagged too** — it had been shipping untagged all along, and an inconsistency nobody can explain is worse than either choice. ⚠ **Colour management is still deferred**: input profiles, conversions and a working-space policy are untouched.
- **⚠ Verifying the profile needed two instruments, and finding out why was the interesting part.** PNG stores `iCCP` **zlib-compressed**, so the bytes are not literally in the file and its decoder must be asked. **`image`'s TIFF decoder cannot read back the ICC tag it just wrote** (`get_tag_u8_vec` does not match the type `write_tag` emits) — a round-trip gap in the crate, **not** a failure to embed. Confirmed externally: `sips` reports `profile: sRGB built-in` for all four, and `bitsPerSample: 16` for the 16-bit TIFF. **Asking the decoder everywhere would have reported a bug that does not exist.**
- **⚠ `dest_for` now takes the format, which moves *which files collide*.** The collision logic keys on the produced filename: `a.RAF` + `a.jpg` collide when exporting JPEG, but not when exporting PNG — where `a.RAF` + `a.png` collide instead. `two_sources_with_the_same_stem_collide_in_an_empty_folder` is **parameterised by format** rather than edited until it passed again; the property is format-independent, only the triggering pair moves.
- `ExportOptions` carries the format, so **export presets save it**, alongside `demosaic`. The quality slider is `add_enabled(format.is_lossy())` — greyed out rather than hidden, so its value survives switching to PNG and back.
- **⚠ The build setup line grew.** lcms2 is installed but off the default pkg-config path, exactly like libraw. Both copies in this file are updated; CI installs `liblcms2-dev`.
- **Accepted caveats:** (1) no alpha — the pipeline is RGB; (2) compression is not exposed (PNG level, TIFF compression use `image`'s defaults), so a 16-bit TIFF is large; (3) JPEG stays 8-bit by definition; (4) **the CLI's `render` still writes JPEG only** — it takes an explicit output path, so a `--format` flag is an easy follow-up rather than a gap; (5) sRGB only, since that is the pipeline's working space.

**Demosaic backend selection done.** First item past Phase 2, and the largest measured win available.

- **⚠ We were inheriting libraw's own default (AHD, its slowest) because nobody ever set `user_qual`.** That was ~93% of an 11 s export. Now an explicit choice, defaulting to **`Fast`**.
- **Measured before designing** (X-T4 `.RAF`, full resolution, release). `unpack` is a flat ~845 ms on top of each, which is why the process-only ratios overstate the win — **quote the end-to-end column**:

  | tier | `user_qual` | process | end to end | vs `Best` |
  |---|---|---|---|---|
  | `Fastest` | 0 | 400 ms | 1.25 s | **9.2×** |
  | **`Fast`** (default) | 1 | 2,049 ms | 2.89 s | **3.9×** |
  | `Better` | 2 | 6,888 ms | 6.9 s | 1.5× |
  | `Best` | 3 | 10,575 ms | 11.42 s | 1× |

  Reproduce with `cargo run --release -p raw-decode --example demosaic_probe <raw> <out-dir>`, which is kept for exactly that.
- **⚠ On X-Trans, `user_qual ≥ 3` collapses.** `3` (AHD) and `4` (DCB) produce **byte-identical** output at identical cost, because libraw routes X-Trans through Markesteijn variants rather than the Bayer algorithms those names denote. So there are **four** distinct outcomes on this camera, not seven.
- **⚠ Hence the labels are tiers — Fastest / Fast / Better / Best — not algorithm names.** Selecting "DCB" on a Fuji gets you Markesteijn; a label that is false on the user's own camera is worse than no label. The `user_qual` value and its Bayer meaning live in the doc comments, where they are accurate as implementation detail.
- **⚠ It is an *export* setting by structure, not by preference.** The editing preview decodes `half_size`, and libraw **skips demosaic entirely** there (2×2 binning), so this can only ever affect a full-resolution decode. Two gated tests (`RAW_FIXTURE`, run with `--release`) pin both halves: `a_half_size_decode_ignores_the_demosaic_setting` proves it cannot be previewed, and `a_full_size_decode_honours_the_demosaic_setting` proves the param actually reaches libraw — without the second, a typo would leave an inert dropdown that looks like it works.
- **`Demosaic` lives in `raw-decode`** so the `user_qual` mapping exists once, which cost `serde` as a dependency there. A mirror enum in `app` would have meant a second copy of the mapping, and a mapping that exists twice is one that will disagree.
- Carried by `ExportOptions`, so **export presets save it**. `PrefixKey` and `BufferCache` are untouched: export decodes are never cached.
- The CLI gained `--demosaic` (it silently inherited AHD too). Measured end to end including pipeline and JPEG encode: **6.4 s at `fastest` against 13.3 s at `best`.**
- **Validated at 1:1 on real full-resolution exports** (2026-08-11): `Best` has marginally crisper hair-strand separation, `Fastest` is slightly softer. The gap is **small** — which is the entire justification for defaulting to `Fast` rather than `Best`, and it was checked rather than assumed.
- **Accepted caveats:** (1) **⚠ the choice cannot be previewed** — judging it means exporting a frame at two settings and comparing crops, which is why the dialog says so in a hint rather than leaving it to be discovered; (2) on X-Trans the tiers describe speed, not algorithm; (3) **the new default changes output** relative to anything exported before today — the previous value was never chosen, and this is early development; (4) `unpack` is unavoidable, so the floor is ~1.2 s per photo, not 0.4.

Persistence was useful alone and did not wait for the preset UI.

The draft is reset from `settings.export` each time the dialog opens and only `start_export` commits, so cancelling discards **by construction** rather than by remembering to undo. Same scratch-state shape `ConfirmDeletePreset`'s `dont_ask_again` uses. Note the lesson: "there is only one write site" was true and still insufficient, because a *second* piece of committed state existed.

- **⚠ Deleting an export preset has a confirmation with "Don't ask again", but no trash** — deliberately unlike develop presets. A develop preset can encode an hour of grading and goes to a 20-entry trash restorable by Ctrl+Z; an export preset is three fields, deleted outright. **The confirmation folds into its own `confirm_export_preset_delete` flag, not the develop one**: disarming the guard on the *recoverable* deletion must not disarm it on the *irrecoverable* one, and `the_two_delete_guards_are_independent` pins that. The shared rule — suppress only on `Confirmed`, never on `Cancel` — has one implementation behind both folds.
- **Storage mirrors `PresetStore` (one JSON file per preset) but on a weaker argument**, stated rather than assumed: that store's main reason was "a preset is a shareable artifact", and an export preset holds an absolute path so it is not shareable. What carries: no read-modify-write race, one corrupt file cannot take the rest down, one pattern rather than two.
- **Accepted caveats:** presets are machine-specific; no import/export of presets; no folder organisation; JPEG only and `<stem>.jpg` naming (**being addressed next — see the next action**); a non-UTF-8 destination path will not serialise, degrading to "not persisted" rather than a crash.

**Dehaze done — M2.3 is closed.** Fourteen stages. The Develop feature set is complete.

- **⚠ The feature was expected to need new architecture and did not.** The handoff note said dehaze would force a "global stats computed upstream" seam, because a frame-global airlight cannot be computed from a cropped region. True only for a *tail* stage. `render_cached` builds `mid = prefix.run(...)` **whole-buffer** and crops *afterwards*, so putting dehaze in the **prefix** dissolved it: no seam, no `Region` plumbing, no `REGION_MARGIN` growth, and `a_region_render_matches_the_whole_render_cropped` untouched. **Read the actual plumbing before believing a note about it — including one you wrote.**
- **Placement: `geometry → noise_reduction → dehaze`.** After NR because dehaze is a contrast stretch that amplifies noise hard. `PrefixKey` gains `dehaze`; the renamed tripwire `the_prefix_holds_geometry_noise_reduction_and_dehaze` is what forces that.
- **Model:** dark-channel prior on `I = J·t + A·(1−t)`. **Linear light is *more* correct here, not less** — the model is radiometric, so it holds exactly in our working space and only approximately in the gamma-encoded space most published implementations use. (The *prior* is an empirical statistic gathered on gamma images; that asymmetry is inherited, not proven here.)
- **One slider, one expression, both directions.** With `k = amount/100` and `t_k = 1 − |k|·(1 − t)`: positive **inverts** the model, negative **applies** it. At `k = 0` both collapse to `J = I` exactly, which is what lets all 27 existing goldens stay byte-identical. Because `t` encodes depth, **negative dehaze is depth-aware for free** — distant things get hazier.
- **⚠ Airlight is estimated on a fixed 256 px downscale, never at the render resolution.** An order statistic over the brightest pixels moves when you downscale, so a render-scale estimate would give the fit preview, the 1:1 view and the export three different airlights and the image would shift on zoom. Fixed sample size makes it render-scale-independent *by construction*. Taken as the **mean** of the haziest 0.1%, not the paper's single brightest pixel, so one hot pixel cannot set it. `A_MIN` floors it because `I_c / A_c` divides by it.
- **`spatial` now has five primitives.** New **`min_filter`** (monotonic deque, O(1) amortised in `r`; a deque rather than van Herk/Gil-Werman specifically because the window *clamps* at borders). And **`guided_filter(p, guide, …)`**, generalised out of `noise_reduction`'s private `guided_self_filter` — NR calls it with `p == guide`. `offset` changed from `(1−s)·m` to `m − s·m`, which can differ in the last f32 ulp; a test pins the two to 1e-6 and **all three NR goldens came out byte-identical**, so the refactor is verified, not hoped.
- **⚠ Three dehaze tests failed first, and all three were the *fixtures*, not the code — but finding out why taught the model.** (1) A real bug: `airlight`'s patch radius was derived from the *input* size, so a small image asked for a patch wider than itself. (2) The test scene's darkest channel reached ~0.175, **violating the dark-channel prior the test was checking** — it measured how DCP degrades, not whether we implemented it; fixed with periodic dark cells on a 40 px pitch so every 41 px patch contains one. (3) **The airlight can only be *observed* where transmission approaches zero.** The fixture's haze topped out at `t = 0.3`, so the far edge was never near-pure airlight and the estimate was necessarily low. Real haze has a horizon; the fixture now reaches `t = 0.05`. **Any future dehaze fixture needs all three properties.**
- **⚠ A fourth lesson, on measurement.** `negative_dehaze_is_depth_aware` first measured how far each pixel *moved*, which is `|J−A|·t·(1−t)` — confounded by scene colour and not even monotonic in `t`. It read backwards. The right invariant is the **retention ratio** `|out − Â| / |in − Â|`, which *is* `t_k` — and normalised against the airlight the stage **estimated**, not the one the fixture imposed.
- **Measured** (X-T4 `.RAF`, 3123×2085 half-size buffer → 1600 px preview, release, best of 5):

  | preview pipeline | ms |
  |---|---|
  | neutral | 22.2 |
  | clarity 70 | 30.1 |
  | **dehaze 60** | **55.3** |
  | NR both 50 | 55.3 |
  | **dehaze 60 + NR both 50** | **87.6** |
  | HSL only | 62.7 |
  | cached tail (any other slider) | 13.7 |

  Dehaze costs about what NR does. Reproduce with `cargo run --release -p app --example bench_preview <raw>`.
- **Goldens 27 → 29** (`dehaze_plus`, `dehaze_minus`) on a `hazy_chart()` built by *applying* the haze model to a synthetic scene, so the reference encodes a known correct answer. The 27 existing stayed byte-identical.
- **Validated on real photographs** (user, 2026-08-11): a hazy landscape and the white-wall kitten frame both read correctly at **+60**.
- **Accepted caveats:** (1) **⚠ Bright achromatic objects violate the prior** — snow, white walls, a white cat read as haze and get over-corrected. *The* classic DCP artifact, inherent to the model. Confirmed acceptable at +60 on a white-wall frame; a real fix needs large-bright-region detection and is its own feature. (2) **At ±100 a visible separation appears between depth regions.** Inherent, not a tuning failure: the transmission map has genuine edges because depth is discontinuous, so at full inversion the `1/t` gain differs sharply across them and a depth edge becomes a tonal edge. Lightroom does the same at Dehaze 100. Softening it would trade edge fidelity for a different artifact. (3) **Dragging Dehaze re-runs noise reduction** — 87.6 ms with both on, against 13.7 ms for every other slider. The price of needing no new architecture; a second cache checkpoint (a standing perf item) would remove it. (4) `A` is estimated per photo, so a synced or pasted Dehaze value can look different elsewhere — inherent to a content-adaptive correction. (5) A single global `A`, so sun-and-shade scenes get one compromise value.

**Filmstrip fixes (2026-08-10) — a layout bug and a loading bug, reported together, unrelated underneath.** Both surfaced by picking a photo near the *end* of an 822-entry folder.

- **⚠ `Ui::allocate_ui` allocates the space its content *actually used*, not the space requested.** egui's own doc says so, and it was the root cause of two thirds of the report. The filmstrip's placeholder branch allocated `box_size` (132 px at the default height) while the loaded branch drew `Image::max_size(..)` — which for a **portrait** thumbnail is only **58.6 px**. Every thumbnail that arrived collapsed its cell by 73 px and shifted every cell to its right. Measured on the test folder: **−12.8 px mean per cell, ~10,500 px of cumulative reflow.**
- **That is also why the centred photo drifted left.** `scroll_to_me` makes egui compute `target_offset` **once**, as an absolute content-space offset, and it never recomputes it (`scroll_area.rs`: `let target_offset = state.offset[d] + delta`). So as portraits *ahead* of the selected photo loaded, the photo slid left in content coordinates while the scroll offset stayed put. Worst at the end of a folder, where the most predecessors are still unloaded — which is exactly how it was reported.
- **Fix: `thumb_cell` allocates first and paints into the allocated rect**, so a cell's geometry is independent of whether its thumbnail has arrived. **The Library grid shares it** and additionally pins its cell with `ui.set_min_size(CELL, CELL)` — it had the same defect in its own shape, masked by `egui::Grid` aligning columns to the widest cell.
- **⚠ JPEG/PNG/TIFF were never rotated by their EXIF orientation.** `image::open` returns the *stored* pixels and ignores the tag, so a portrait JPEG lay on its side — which is why portrait RAWs looked right in the grid (libraw's `sizes.flip`, applied by `apply_flip`) while portrait JPEGs did not. `image_decode::open_oriented` now reads `ImageDecoder::orientation()` and applies it. **⚠ Applied in `decode` as well as `thumbnail`**, because the bug was never confined to the browser: the canvas and every **export** of a portrait JPEG were sideways too. A missing or unreadable tag is treated as "no transform", never an error.
- **⚠ The orientation tests build a real EXIF APP1 segment by hand** (little-endian TIFF header, one `0x0112` SHORT entry, spliced in after SOI) because **the `image` crate reads EXIF but cannot write it** — a fixture that merely *claimed* to be rotated would prove nothing. All eight orientations are covered; 5–8 transpose, 1–4 do not. Verified to fail without `apply_orientation` (`left: (40, 20), right: (20, 40)`).
- **⚠ Consequence for existing JPEG sidecars:** a crop saved against the *unrotated* version of a portrait JPEG now refers to a rotated frame and will be wrong. Accepted — the image was being displayed incorrectly before, and this is early dev; the same call the sidecar-naming change made.
- **⚠ Diagnostic trap worth remembering: `sips` reports a RAF's *sensor* dimensions, unrotated.** It called all 411 files landscape and sent the investigation down a blind alley. `extract_thumbnail` applies libraw's flip (the `apply_flip` fix), so the *thumbnails* are genuinely portrait — 7 in the first 40. **Measure through `extract_thumbnail`, never through `sips`, when asking about thumbnail geometry.**
- **⚠ `thumb_cell` allocates with `Sense::hover()`, and that is load-bearing.** The first version used `Sense::click()`, which **broke clicking a Library grid thumbnail**: there the click target is the whole cell (thumbnail *and* filename), so two overlapping click-sensing widgets both sat at distance 0 from the pointer, and egui breaks that tie by **registration order** (`hit_test.rs`: "In case of a tie, take the last one = the one on top"). The thumbnail swallowed the click and only the grey margin around it opened the photo. The rule: **`thumb_cell` reserves space and paints; interaction is the caller's to add.** The filmstrip, where the cell *is* the target, opts in with `.interact(Sense::click())`.
- **egui interaction is testable headlessly too** — three passes with `RawInput` events (`PointerMoved`, then `PointerButton` pressed, then released), asserting `Response::clicked()` on the third. `clicking_a_library_grid_thumbnail_opens_it` and `clicking_a_filmstrip_thumbnail_opens_it` reproduced the regression before it was fixed, and each was watched to fail again afterwards.
- **`main.rs` now has unit tests**, which it never had before — a binary crate can have them, and egui lays out headlessly via `Context::run_ui(RawInput::default(), ..)` with `ctx.load_texture` for a fixture texture. `the_old_cell_shrank_when_a_portrait_thumbnail_arrived` **reproduces the old collapse**, so the diagnosis is pinned rather than only the fix. This is the seam for testing any future layout invariant.
- **`ThumbLoader` is now parallel** — it was one thread in strict index order, so a photo at the end of a folder sat grey until every predecessor had loaded. **Measured 175.9 ms/thumb** (not the ~90 ms once recorded here), so 822 entries was **~145 s**. Six workers bring it to 41.0 ms/thumb, **4.3× — ~34 s**. Reproduce with `cargo run --release -p app --example bench_thumbs <folder>`.
- **⚠ `worker_count()` is deliberately `cores − 1`, capped at 6, not the core count.** The develop pipeline's stages are rayon-parallel over the *global* pool and a decode may be running, so a loader that saturated every core would make editing sluggish for as long as a folder takes to load — the same contention argument that keeps `batch_export` sequential and `DecodeWorker` at 2. **No rayon dependency was added to `app`**, precisely so this pool stays separate from the render pool.
- **Work is handed out through a shared `AtomicUsize` cursor, not split into per-thread chunks**: a folder mixes RAW and JPEG whose extraction costs differ a lot, so static chunking would leave threads idle. The load fn and thread count are **injected** (the `DecodeWorker` pattern), so `the_folder_is_loaded_in_parallel` asserts *concurrency* — peak simultaneous loads, not wall-clock — and is deterministic on any machine. It was watched to fail (`left: 1, right: 4`) with the pool forced to one thread.
- **⚠ Results now arrive out of order.** Every one carries its `index` and the caller stores by it, so nothing broke — but do not reintroduce an assumption that `drain()` is sorted.

**⚠ CI flakiness: three tests fixed 2026-08-10, and the lesson generalises.** The first push to GitHub after the texture/clarity work went **red on Linux while green on macOS every time locally** — 50 consecutive local runs of the failing test passed. Verify concurrency tests by *hunting*, not by running once: `for i in $(seq 1 20); do cargo test --all; done` found two more that a single run never would.

- **⚠ `ExportWorker::spawn` starts the thread immediately, so `worker.cancel()` right after it is a race.** `the_cancel_flag_stops_the_run_between_photos` lost that race on Linux and exported the first photo (`left: 1, right: 0`). Its own comment said "setting the flag *before the run starts*" — which is not what it did. **The only way to say that without a race is to pass a flag that is already `true`.** A separate handshake test now covers the public `cancel()`, which that test was the sole caller of.
- **⚠ A release condition on a counter that also *decreases* is not a barrier.** The rewritten `the_folder_is_loaded_in_parallel` first gated on the *live* count: the last worker to arrive satisfied it, left, and decremented below the threshold, so its peers waited out the full 2 s deadline. **The test still passed** — just two seconds slower, which is exactly how a broken barrier hides. It now gates on a monotonic *arrival* count: 0.01 s, and a sequential loader still fails it. Assert on structure, never on OS scheduling, and give any such wait a deadline so a regression **fails** instead of hanging CI for hours.
- **⚠ Never take temp-file uniqueness from the clock.** `image-decode`'s `temp_path` used `SystemTime::now()`; `cargo test` runs tests in parallel and four of them build fixtures through `tagged_jpeg` (one eight times in a loop), so two in the same tick collided and one test deleted a file another was reading — about one run in five. Uniqueness is now **structural**: process id plus a monotonic counter.
- **CI is stricter than the usual local command in two ways** worth matching before pushing: it runs `cargo clippy --all-targets --all-features` (note `--all-features`), and `rust-toolchain.toml` says `channel = "stable"` — unpinned — so CI can have a newer clippy than the local toolchain.

**Texture & Clarity done — two thirds of M2.3.** Thirteen stages. **Dehaze is deliberately NOT part of this** and is the next action; see the RESUME block for the two reasons it was split out.

- **One stage, not two — and that is the load-bearing decision.** `LocalContrastStage` (`stages/local_contrast.rs`) computes **both** bands against the *same* source luma and **sums the deltas**: `Δ = k_t·d_t + k_c·d_c·w(l)`, then one scalar RGB gain. Two sequential stages would make Clarity operate on Texture's *output*, so the sliders would interact and neither would be independently predictable. As one stage they are **exactly additive**, which `texture_and_clarity_are_exactly_additive` asserts as `out(t,c) == out(t,0) + out(0,c) − src` rather than leaving it a claim in a comment.
- Otherwise it is `SharpenStage`'s shape at two different radii: `d = luma − blur(luma)` on Rec.709 luma in linear light, re-applied as a scalar gain. Buys the same three things — no colour fringing, `r:g:b` (hence hue and saturation) preserved exactly, and **no Oklab round trip**. `LUMA_EPS`/`GAIN_MAX` are lifted verbatim; the near-black guard is load-bearing for the identical reason.
- **`k = amount/100` with no gain constant**, so the endpoints mean something: **−100 removes the band, +100 doubles it.** Same species of defensible endpoint as the vignette's "−100 is exactly black".
- **⚠ Midtone weighting on Clarity only.** `t = l/(l+0.18)` (mid-gray → exactly 0.5, no `powf`), `w = 4t(1−t)`. Without it, +Clarity at a 40 px radius clips skies and blocks up shadows — the standard complaint about the tool. Texture does not get it, and **the asymmetry is justified by amplitude, not taste**: the fine band cannot reach the clip on its own. `texture_is_not_midtone_weighted` pins that half so the asymmetry stays deliberate.
- **`spatial::wide_blur` is a *third* primitive, not a replacement.** Clarity's σ=40 makes a Gaussian unaffordable — 241 taps × 2 passes × 26 Mpx ≈ 13 G ops on **every export**. Three iterated `box_blur` passes are O(1) in σ: `r = round((√(1+4σ²)−1)/2)`, reach `3r`. The module now covers three regimes: `gaussian_blur` sub-pixel to a few px (where a direct kernel is cheap *and* where an integer box radius cannot express the blur at all), `wide_blur` tens of px, `box_blur` where a genuine box is wanted (NR's guided filter needs box means). **⚠ Deliberately no `.max(1)` on `r`** — clamping up would render σ=0.1 as an effective σ of 0.82, eight times too wide; it returns a copy instead, like `gaussian_blur`.
- **⚠ Both are high-pass, and Clarity's passband strictly *contains* Texture's.** A 40 px blur of a 6 px sine is the mean, so Clarity sees the fine band at nearly full strength too (measured: ~0.011 each). The first draft of the band test asserted "Texture beats Clarity on fine detail" and **would have failed against a correct implementation**. The real discriminator is the other direction: Texture is band-*selective* and barely sees coarse structure. `texture_selects_the_fine_band_while_clarity_reaches_the_coarse_one` says so, with the expected magnitudes written into the comment. Visible in `clarity_plus.png`, where the fine striping is amplified along with the ramp.
- **Position: tail, after `ToneCurveStage`, before `SaturationStage`.** After the tone curve is mandatory — a local contrast measured before it would then be re-mapped by it, the same argument that kept the vignette out of the prefix. It also must not join the prefix, or every Texture drag would invalidate the NR cache.
- **⚠ `REGION_MARGIN` 128 → 192, and the margin question now has one owner.** Clarity's reach is **120 px**, which *passed* against 128 — with 8 px of slack, i.e. a trap for the next person. Sharpening's `max_kernel_radius` is now joined by **`pipeline::tail_kernel_radius(&edits, scale)`** (actual reach for these edits) and **`max_tail_kernel_radius(scale)`** (worst case over every representable setting, defined *through* the first so they cannot drift). Two functions because the two call sites want different things: `view_region`'s invariant wants the worst case, `a_region_render_matches_the_whole_render_cropped`'s inset wants the actual — conflating them makes the inset 120 px in a test whose region was 40 px wide. **Texture and Clarity are summed, not composed, so their contribution is a `max`, not a sum** — unlike sharpening's two internal Gaussians, where the mask blurs `|d|` on top of the first blur and the radii genuinely add.
- **⚠ That forced the region test's buffer to grow.** Its inset jumped 9 → 120 px, so its own `w > 2*inset` guard could not hold on 64×64. Buffer and region are now **derived from `inset`**, so they track any future σ. Both guards were **watched to fail** before being restored: `REGION_MARGIN = 100` → "must exceed the tail's kernel radius 120"; `inset = 0` → interior byte mismatch.
- **Three exhaustive fixtures caught the new field at compile time** — `pipeline::all_edits()`, `edit_model::all_nonneutral()` and `app::edit_clipboard`'s payload test — which is exactly what they exist for. Group is **Tone**, not Detail: Detail is capture-specific (noise, lens, output size), Texture and Clarity are *look*, which is what a preset carries.

  | preview pipeline | ms |
  |---|---|
  | neutral (output transform only) | 21.1 |
  | vignette −60 | 24.8 |
  | **texture 70** | **27.9** |
  | sharpening 70 | 27.7 |
  | **clarity 70** | **29.9** |
  | **texture 70 + clarity 70** | **33.6** |

  Both bands together cost **+12.5 ms**, less than the 15.6 ms the two cost separately — the shared luma extraction. Clarity at +8.8 ms is the proof `wide_blur` is being reached: a σ=10.25 Gaussian at preview scale would be several times that. Region tail went 6.9 → **8.4 ms** with the wider margin, matching the ~20% predicted.

- **Accepted caveats:** (1) **judge Texture at 1:1, Clarity at fit** — at the X-T4 fit scale of 0.256, σ_t = 2.0 becomes 0.51 and the detail it acts on has already been averaged out of the preview, while σ_c = 40 becomes 10.2 and is entirely real; the two sliders sit side by side and disagree about where to look, which is inherent and is the caveat most likely to be reported as a bug. (2) **No halo suppressor on Clarity** — the midtone weight is the mitigation; a `Detail`-style suppressor is a contained follow-up. (3) σ in full-resolution pixels, like every other radius here. (4) **Negative Texture is not edge-aware**, so it softens edges within its band along with the texture — deliberate, because NR already owns edge-aware smoothing and is upstream where it belongs; a guided-filter base for the negative half is the follow-up, at the cost of the tool behaving differently either side of zero. (5) Clarity acts on the lens vignette like any other low-frequency feature, so it accentuates or flattens it. (6) Buffer-native 1:1 is still a half-size decode that skips demosaic, so Texture at 1:1 corresponds to ~2× the radius the export applies.

**Sharpening done — the "detail" pair is complete.** Twelve stages. NR without sharpening was half the story: denoising softens, and nothing put the edge definition back.

- **`spatial::gaussian_blur` is a *new* primitive alongside `box_blur`, not a replacement.** They serve opposite regimes: `box_blur` is O(1) in its radius, which is what makes NR's 6–32 px windows affordable; sharpening works at σ 0.5–3 px, where a direct kernel is cheaper (7 taps at σ=1) **and** where an integer box radius cannot express a sub-pixel blur at all. Kernel radius `ceil(3σ)`, weights normalized, **edges replicate** (so a constant plane stays exactly constant), and — unlike `box_blur`, whose vertical pass carries a running sum — *both* passes are rayon-parallel over rows, because a Gaussian carries no state between pixels.
- **`SharpenStage`** (`stages/sharpening.rs`) — `d = luma − gaussian_blur(luma, σ)` on **Rec.709 luma in linear light**, applied back as a scalar RGB gain. That one choice buys three things at once: no colour fringing on a chromatic edge, hue/saturation ratios preserved exactly, and **no Oklab round trip** — the cost that dominates HSL and NR.
- **Detail is our own model**, not Adobe's: `supp = s + (1−s)/(1 + (|d|/HALO_KNEE)²)`. At 100 it is a pure unsharp mask; at 0 it suppresses halos where local contrast is already high while leaving fine texture at nearly full strength. Genuinely distinct from **Masking**, which gates on *where* (a blurred `|d|` through a smoothstep) rather than *how strong*. Masking 0 **skips the branch entirely** — both the cheap path and what avoids `smoothstep(0, 0, ..)` being degenerate. Measured on the goldens' hard edge: Detail 0 cuts the halo from 69→0 down to 69→61 (8-bit) while the flat-band grain is essentially untouched.
- **⚠ The near-black guard is load-bearing.** `gain = 1 + Δ/max(luma, LUMA_EPS)` with `LUMA_EPS = 1e-3`; without it a dark pixel beside a bright edge divides by ~0 and the ratio explodes. `GAIN_MAX = 4.0` then bounds a halo in near-black regions to +2 stops. Both are pinned by `the_near_black_guard_bounds_the_gain`.
- **Radius is the one slider not on a 0–100 scale**, deliberately: it is σ in **full-resolution pixels**, multiplied by `RenderScale` — the same seam NR uses, and naming it in pixels is what makes "full-res radius, scaled for the render" comprehensible. `Sharpening::is_active()` is **amount-only**, the rule `NoiseReduction` and `Vignette` already follow. Defaults: amount 0, **radius 1.0**, detail 50, masking 0.
- **⚠ The margin invariant is now real, and asserted.** NR can never seam because it lives in the *prefix*, which always runs whole-buffer. Sharpening lives in the **tail**, which runs on the *cropped* region — so at the region's edge it reads neighbours that do not exist. That band is `max_kernel_radius` wide: **15 px** at Radius 3 full-res, because the two Gaussians **compose** — `ceil(3σ)` = 9 for `d`, plus the mask's `ceil(3·2)` = 6 for the blur of `|d|`. (The spec said 9; it counted only the first.) `REGION_MARGIN` is 128, so the band never reaches the screen. `view_region::the_region_margin_exceeds_every_tail_kernel_radius` fails loudly if the Radius range grows or another spatial stage joins the tail. **`REGION_MARGIN` moved from `main.rs` into `view_region`** precisely so a test could reach it — a `const` in a binary crate is unreachable.
- **⚠ The master invariant was *weakened*, and the test now says so.** `a_region_render_matches_the_whole_render_cropped` can no longer be bit-identical at the region's edge — and never can be, because the region genuinely lacks those neighbours. It would have kept passing **silently**, since its edit set had no sharpening. So sharpening was **added** to that edit set and the comparison **inset by `max_kernel_radius`**, derived rather than hard-coded so it tracks any future change; an `assert_ne!` up front stops it passing trivially. The interior is still compared bit for bit. Verified by temporarily setting `inset = 0` and watching it fail.
- **Goldens now 23** — `sharpen_basic` / `sharpen_masked` (80) / `sharpen_detail_low` on the existing `noise_chart()`, whose hard edge *and* noise are exactly what sharpening interacts with. The 20 existing references stayed **byte-identical**, which is the proof the new stage is inert at its default.
- **Measured** (X-T4 `.RAF`, 3123×2085 half-size buffer → 1600 px preview, release, best of 5):

  | preview pipeline | ms |
  |---|---|
  | neutral (output transform only) | 21.5 |
  | vignette −60 | 23.7 |
  | **sharpening 70** | **26.6** |
  | **sharpening 70 + masking 60** | **28.8** |
  | NR both 50 | 45.3 |
  | HSL only | 56.8 |

  **+5.1 ms**, and +2.2 ms more for the second Gaussian that Masking adds — the second-cheapest stage after the vignette. It lands in the cache's **tail**, so it re-runs on every slider move; that is right (its parameters change often) and affordable.
- **Accepted caveats:** (1) **judge sharpening at 1:1, not at fit** — at fit scale (0.256) a full-res σ of 1.0 becomes σ=0.256, a kernel of `[0.0005, 0.999, 0.0005]`, i.e. the identity. That is *correct*, not a bug: neither the preview nor a fit-view of the export contains that detail. This is exactly why 1:1 region rendering was built first, and why there is deliberately **no `SIGMA_MIN` clamp**. (2) ⚠ **Superseded for RAW** by the full-resolution 1:1 work: past ~1.95× fit zoom you now see the real demosaiced pixels at the export's radius. It still holds in the **NativeHalf** tier (1.0×–1.95×) and before the full decode lands, where the buffer is half-size and skips demosaic — bounded judgement, not exactness. (3) No output/print sharpening for resized exports; separate feature. (4) Detail is our own model, not Adobe's. (5) Sharpening after the vignette means darkened corners sharpen less in absolute terms — correct for a ratio-based model.

**Vignette done — the "rounded-out Develop" set is complete.** Post-crop, creative (lens-profile vignetting correction stays a `lensfun`-era feature).

- **`VignetteStage`** (`stages/vignette.rs`) — normalized frame coordinates `u,v ∈ [-1,1]`, a smoothstep falloff, and `f = clamp(amount/100, ±1) · t` applied in linear light: `f ≤ 0` scales by `(1 + f)²` (exactly **black** at −100), `f > 0` lifts by `(1 − v)·(1 − (1 − f)²)` (exactly **white** at +100).
- **⚠ The amount model was revised three times, every time from actually using it** (originally `exp2(±2 EV)`). (1) The **endpoints** were too weak — and a multiplicative gain is strictly positive, so it can *never* reach black however large `MAX_EV` grows; interpolating toward the endpoint is the only model that hits pure black/white. (2) The **mid-range** was then too weak against the new extremes, so the darkening curve was squared. (3) That left the halves **asymmetric** (at ±25, 44% toward black vs 25% toward white), so brightening was squared about its own endpoint too. Net: −25 ×0.563, **−50 ×0.25 (−2 EV)**, −75 ×0.063, −100 **black**, and equal |amount| now moves a pixel equally far each way. `the_middle_of_the_slider_is_two_stops_down` and `darkening_and_brightening_are_mirror_images` pin both properties. The response is still not symmetric in *log* space — past −50 each step is worth progressively more, inherent to reaching true black. **Lesson: this stage's feel could not be settled from the spec; each revision came from looking at a real photo.**
- **The vignette goldens are the only references that have ever legitimately changed** (twice, by 7/255 then 59/255). Both times the *other 17 stayed byte-identical*, which is what proved the change was scoped to this stage and had not leaked. Treat that check as the point of the exercise whenever a reference has to move.
- **Needs no `RenderScale`, deliberately.** Normalized coordinates make it resolution-independent, so preview and export agree *exactly* — in direct contrast to noise reduction. This is the scale seam behaving as designed: spatial stages consume the scale, normalized ones ignore it. `VignetteStage::new` takes only params.
- **Post-crop is structural, not a mode.** `GeometryStage` runs first, so the stage reads the *cropped* frame's own dimensions and aspect. Lightroom needs a separate "post-crop vignette" concept; here it falls out of stage order. Consequence: recropping reshapes the vignette.
- **`Shape` helper** (separate from the gain so it is testable on exact normalized coords, free of pixel-centre quantization). `d = (|u·wu|^p + |v·wv|^p)^(1/p)`. Roundness **> 0** stretches the *long* axis toward `max(w,h)/min(w,h)`, giving a true pixel-space circle; Roundness **< 0** raises `p` from 2 to `P_MAX = 6`. `p == 2` takes a `sqrt` fast path, so the `powf` pair is paid only when Roundness is negative.
- **⚠ Roundness −100 darkens corners *less*, not more.** Raising the exponent **lowers** `d` off the axes — at `(1,1)`, `√2 ≈ 1.414` at `p=2` versus `2^(1/6) ≈ 1.122` at `p=6` — so the untouched interior becomes a rounded rectangle and the darkening concentrates along the edges. This was written backwards in the first draft of the spec and caught in review; `roundness_minus_100_darkens_corners_less` now pins the direction.
- Constants: `R_MID` 0.2–1.4 (Midpoint), `FEATHER` **0.0**–1.0 (Feather) — starting at 0 is what makes Feather 0 a genuinely hard edge, and what makes `WIDTH_EPS = 1e-4` **load-bearing** rather than decorative: it is the only thing between Feather 0 and a division by zero in `smoothstep`.
- **`Vignette::is_active()` is amount-only** — same rule as `NoiseReduction`. Midpoint/Roundness/Feather are modifiers; dragging one alone must not insert a stage. Defaults: amount 0, midpoint 50, feather 50, **roundness 0** (its own neutral *and* the middle of its ±100 range).
- **Two structural properties, both asserted:** neither branch can produce a negative sample (`1 + f ≥ 0`, and the lift only raises), so the stage needs **no clamp** (unlike `HslStage`/`NoiseReductionStage`); and *darkening* is a scalar multiply, so it leaves `r:g:b` ratios — hence hue and saturation — exactly alone. Brightening desaturates as it approaches white, which is what "toward white" means, not a defect.
- **`core-image` gained `map_pixels_xy`** (rayon over rows, bit-identical to sequential, with an explicit zero-width guard because `par_chunks_exact_mut(0)` panics). The primitive any future graduated filter, radial filter or lens correction reuses.
- Goldens now **20** — three shapes at the same Amount on the 4:1 `chart()`, whose aspect makes them obviously different; the 17 existing references are byte-identical. Verified by eye *and* by `cmp` that the three differ, since "roundness branch never taken" would otherwise pass silently.
- **Measured**: preview 20.6 ms neutral → **23.4 ms** with vignette (+2.8 ms) — one `sqrt`, one `exp2` and three multiplies per pixel, no Oklab round trip. The cheapest stage by a wide margin; compare NR-both at 45.2 ms and HSL at 55.0 ms.
- **Accepted caveats:** the vignette follows the crop; **crop mode previews it uncropped** (`preview_edits` resets the crop, so it snaps on exit); **no highlight protection**, so a strong negative Amount pulls bright corners down with everything else (Lightroom's Highlight Priority exists for that); positive Amount lifts toward white and stops there, leaving samples already above 1.0 alone; and an extreme Midpoint/Feather pair can put `r_mid - width/2` below zero and darken the centre too — a legitimate look, deliberately not clamped, so "the centre is untouched" holds only at sane settings.

**Noise reduction done — and the pipeline is now scale-aware.** The `detail` stage finally exists.

- **`RenderScale`** (`pipeline/src/lib.rs`) — `build_pipeline(edits, scale)`. A spatial filter's result depends on the resolution it runs at, so a radius-8 filter on the 1600 px preview is *not* the same edit as radius-8 on a 6000 px file. Spatial stages multiply their pixel radii by this; per-pixel stages ignore it (asserted bit-for-bit by `per_pixel_stages_ignore_the_render_scale`). `RenderScale::new` clamps to `(0,1]` rather than panicking on the render worker.
- **Computing it needs no libraw:** `RawMetadata.width/height` reports the **processed** size, so on a `preview()` decode it already reads half-size and cannot serve as the full-res reference. But `half_size` is our own flag → `DecodeOptions::source_scale()` (0.5 / 1.0), and `render_engine::render_scale()` multiplies that by `downscale_to`'s own ratio. Both factors exact. `Decoded` carries `source_scale`; the injected decode fn now returns `(ImageBuf, String, f32)`.
- **`NoiseReductionStage`** (`stages/noise_reduction.rs`) — one Oklab round trip serves both halves. **Luminance:** self-guided filter (He et al.) on `L` — 4 box blurs, `slope = var/(var+eps)`, so `slope→1` on an edge (pass through) and `slope→0` on noise (local mean). **Color:** 2-pass box blur on `a`/`b`. The filter's coefficients are named **`slope`/`offset`**, not the paper's `a`/`b`, which would collide with the Oklab chroma channels in the same file.
- **Why guided and not bilateral:** with a scale-aware radius, an O(r²) kernel needs ~3600 taps/pixel on a 24 Mpx export (~90 G ops). The guided filter is **O(1) per pixel regardless of radius**. Measured: NR adds only ~1.1 s to a full 26 Mpx export (12.2 s → 13.3 s) at radii of 6 and 20 full-res px.
- **`spatial::box_blur`** — separable running sums. Borders clamp the *window*, not the samples (window shrinks, divided by its actual count), so a constant plane stays exactly constant. Horizontal pass is rayon-parallel over rows; the **vertical pass is deliberately sequential**, advancing all columns together over contiguous row slices — a transpose-blur-transpose would scatter-write the whole buffer 4× per blur (16× per NR render). Don't "fix" it without a profile.
- **Parameter mapping** (base radii in **full-res px**, then `max(1, round(base × scale))` — never 0, which would silently disable the filter): luminance radius fixed at **6**; `chroma_radius_full` = **8..32** from Smoothness; `eps = 1e-3 · (1e-2)^(detail/100)` from Detail — **geometric**, because it is a variance spanning two decades (50 → 1e-4, i.e. σ_L ≈ 0.01).
- **`NoiseReduction::is_active()` is `luminance > 0 || color > 0`, NOT `!= default()`** — Detail/Smoothness are modifiers (default **50**, not 0), so dragging one alone must not insert a stage that only costs an Oklab round trip. Defaults stay at 0 even though Lightroom ships RAW at Color 25; a non-zero default would break `Edits::default() == neutral`, the `neutral` golden, and the whole "add a stage only when non-neutral" rule.
- Goldens now **17**, on a new 128×**192** `noise_chart()`; the 14 existing references are byte-identical. The chart's regions are 64 px tall **on purpose**: at Smoothness 50 the chroma window reaches 41 px, so on shorter bands the reference recorded chroma *bleeding between regions* instead of noise being removed inside one (caught by actually looking at the first generated PNGs — a golden nobody has looked at is just a hash).
- **Measured** (X-T4 `.RAF`, 3123×2085 half-size buffer → 1600 px preview, release, best of 5). Reproduce with `cargo run --release -p app --example bench_preview <raw>`:

  | preview pipeline | ms |
  |---|---|
  | neutral (output transform only) | 22.4 |
  | NR color 50 only | 37.7 |
  | NR luminance 50 only | 40.2 |
  | NR both 50 | 46.6 |
  | HSL only (for comparison) | 57.7 |

  NR is **cheaper than HSL** — the Oklab round trip dominates both, and 8 box blurs cost less than per-pixel `atan2`/`cos`/`sin`.
- **Validated on a real photo** (`rustroom render --edits`, X-T4 fur at 1:1): Color-only 80 leaves individual hairs fully crisp while killing chroma speckle — the payoff of splitting the two halves. Luminance 30/Detail 70 is a natural everyday setting; Luminance 70/Detail 40 visibly smears fur, which is correct-but-aggressive on texture at the same scale as the noise.
- **Accepted caveats:** (1) the preview over-smooths relative to the export, because `downscale_to` has already averaged noise away — **judge NR at export**, since our "100%" zoom is 100% of the *half-size* buffer; (2) chroma bleeds across strong color edges at high Color/Smoothness (fix would be guiding the chroma blur with `L`); (3) single-scale, so luminance blotches larger than the radius survive — wavelets are the real fix, deferred; (4) NR runs **first**, which used to mean every slider paid for it — fixed by the preview prefix cache, see above; (5) very dark, very noisy regions read as structure (var ≫ eps) and are left alone — raise Luminance or drop Detail.

**HSL done (per-hue color), plus rayon-parallel pixel maps.**
- **`color::oklab`** — `linear_srgb_to_oklab` / `oklab_to_linear_srgb` (Ottosson matrices; `#![allow(clippy::excessive_precision)]` keeps the reference digits verbatim). Round-trips to ~5e-7, including scene-referred values above 1.0.
- **`HslStage`** (`stages/hsl.rs`) — 8 bands × Hue/Saturation/Luminance in Oklab. Per pixel: hue = `atan2(b, a)`, the **two bracketing band centers get a smoothstep blend** (weights always sum to 1 → setting all 8 bands equally equals the global adjustment, asserted by a test). Ranges: hue ±100 → ±30°, saturation ±100 → chroma ×0…×2, luminance ±100 → L ×0.5…×1.5.
- **`BAND_HUES`** = Oklab hue angles of the canonical sRGB colors — Red 29.23, Orange 52.98, Yellow 109.77, Green 142.50, Aqua 194.77, Blue 264.05, Purple 293.94, Magenta 328.36. `band_centers_match_canonical_colors` recomputes them from `#FF0000`…`#FF00FF` and fails if the table drifts: **fix the table, never the tolerance.**
- **Chroma taper (`CHROMA_FADE = 0.02`)** — adjustments fade out via smoothstep as chroma → 0. Without it, a near-neutral pixel's hue is pure sensor noise (chroma ~0.003 at ±0.6% noise vs ~0.06 for a real color), so neighbours landed in different bands and got different treatment: **measured 37.8× noise amplification** on a near-neutral patch, visible as speckle in bright hair/sky. With the taper: **1.03×**, while a genuinely colored patch keeps its full 1.58× effect and all goldens stay byte-identical. Trade-off: pastel colors respond less. Residual grain amplification on noisy files is expected until an NR stage exists — Lightroom behaves the same without NR.
- `Edits.hsl` = `Hsl { bands: [HslBand; 8] }` + `HSL_BAND_NAMES` (shared by stage and UI). Sidecar stores bands **positionally**, so that order is part of the file format. Three `CollapsingHeader` groups (Hue/Saturation/Luminance) in the right panel, which gained an `egui::ScrollArea` to fit them.
- Goldens now **14**: `hsl_red_desaturated` / `hsl_blue_hue_shift` / `hsl_green_luminance` on a new `hue_sweep_chart()` (the primaries-and-gray charts can't exercise bands).
- **`ImageBuf::map_samples` / `map_pixels` are now rayon-parallel** (`F: Fn(..) + Sync + Send`). Pixels are independent, so output is bit-identical — proven by the 14 goldens passing unchanged. Measured on the 1600×1068 preview, 8 cores (cold / warm):

  | pipeline | before rayon | after |
  |---|---|---|
  | neutral (output transform only) | 33.7 ms | 14.0 / 7.8 ms |
  | with HSL stage | 209.7 ms | 47.7 / 40.7 ms |
  | 5 stages + HSL | — | 51.6 / 55.4 ms |

  HSL is still the most expensive stage by far (Oklab round trip + `atan2`/`cos`/`sin` per pixel); a hue LUT is the obvious next optimization if it ever matters. `downscale_to` is still sequential — **re-measured at 9.0 ms, not the ~14 ms once recorded here** — and is now skipped entirely on a preview-cache hit.

**Snappy RAW switching done (photo switching never blocks the UI).** Two new `app` lib modules:
- `decode_worker::DecodeWorker` — **thread per request**, capped at `MAX_CONCURRENT_DECODES = 2`, with a one-slot queue that keeps only the newest request. Each result carries a monotonic `seq`; the app ignores stale ones. The decode fn is **injected** (`DecodeWorker::new(decode_for_edit, …)`) so its 4 unit tests run without libraw. The worker also renders the neutral **baseline frame** while it holds the buffer, keeping that off the UI thread.
- `buffer_cache::BufferCache` — LRU (`BUFFER_CACHE_CAP = 3`) of `Arc<Decoded>` keyed by path; a hit shares the buffer with the live session instead of copying. **Superseded decodes are still cached**, so skimming past a photo and returning is instant.
- `app` bin: `RustroomApp::new(ctx)` (replaces `Default`, needs the ctx for `request_repaint`); `pending: Option<PendingOpen>` holds the placeholder texture + a **180 ms debounce** deadline (`DECODE_DEBOUNCE`), so holding an arrow key starts *zero* decodes until you settle; `pump_decodes` runs once per frame. `Session` still means "fully decoded" — nothing downstream learned about the half-open state.
- UI while decoding: the target's filmstrip thumbnail fills the canvas, laid out **where the decoded preview will land** (predict long side = `PREVIEW_MAX_DIM`, then the session's `.min(1.0)` fit rule) so the swap doesn't jump; no thumbnail → previous photo dimmed. Right panel / Export / Undo / Crop are disabled (`ui.disable()` — `set_enabled` is gone in egui 0.35); arrows and filmstrip clicks stay live.
- **Measured** (X-T4 `.RAF`, release): half-size decode ~1.03 s, of which **`unpack()` is 840 ms**, `process()` 111 ms; baseline render 42 ms; `extract_thumbnail` 99 ms.
- **Abandon, don't abort.** Real cancellation is plumbable (`libraw_set_progress_handler` is in the `rsraw-sys` bindings and `rsraw` exposes `AsMut<libraw_data_t>`; nonzero return → `LIBRAW_CANCELLED_BY_CALLBACK`), but 85% of the time is inside one `unpack()` whose callback granularity is unverified for compressed RAF. So a superseded decode is left to finish on its own thread while the new one starts in parallel — same feel, no unsafe FFI. **Follow-up if ever needed:** experiment first, then a `CancelToken` param on `decode_raw`.

**Thumbnail orientation fixed (`raw-decode`).** Embedded thumbnails are stored unrotated while `decode` gets libraw's flip applied during `dcraw_process`, so portrait shots were sideways in the **grid, filmstrip and decode placeholder** (7 of 62 files in the test folder). `backend_rsraw::apply_flip` now applies `sizes.flip` (dcraw codes: 0 none / 3 180° / 5 270° / 6 90°) after the downscale; unit-tested, and validated against a real `flip=5` file (thumb 341×512 vs decode 2085×3123).

**Saturation & vibrance done (first color adjustments).** One `SaturationStage` (`crates/pipeline/src/stages/saturation.rs`) handles both: per-pixel chroma scaling around the Rec.709 luma in linear light — `out = luma + (rgb - luma) * f_sat * f_vib`, clamped at 0, where `f_sat = 1 + saturation/100` and `f_vib = 1 + (vibrance/100) * (1 - chroma)` with `chroma = (max-min)/max`. So vibrance moves muted pixels most and leaves fully saturated ones alone; a neutral pixel is untouched at any setting; `saturation = -100` collapses to luma (monochrome). `build_pipeline` inserts it **after the tone curve, before the output transform** (color follows tone), only when either param is non-zero. `Edits.saturation` / `Edits.vibrance` (serde-defaulted → old sidecars load unchanged); two sliders after Blacks in the Develop panel, which inherit undo/redo, sidecar and export for free. Goldens now 11: `saturation_plus50` on the existing chart plus `vibrance_plus50` on a **new `muted_chart()`** (the main chart is pure primaries/gray, where vibrance is a no-op by construction) — `check_golden_with(name, edits, chart)` was added for that; the 9 pre-existing references stayed byte-identical. **Caveat (MVP model):** negative vibrance uses the same `(1 - chroma)` weighting, so it desaturates muted colors *more* than saturated ones — simple and symmetric, not Adobe-identical. Validated end-to-end via `rustroom render --edits` on the X-T4 `.RAF`.

Combined with load-on-open, switching photos never loses edits — no "discard?" dialog needed (fits the non-destructive model). ⚠ It calls **`sidecar::persist`, not `save`**: neutral edits *delete* the sidecar.
