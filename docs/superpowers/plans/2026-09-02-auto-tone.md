## The maths the tasks rest on (worked out before writing anything)

`ToneRegionsStage::gain_for_luma(l)` = `1 + 0.5·(whites·max(0, 3l−2) + blacks·max(0, 1−3l))`
with the sliders as fractions. So:

- A slider moves its percentile by **at most ±50 %**, and only where its weight is non-zero
  (whites: `l > 2/3`; blacks: `l < 1/3`). The gain is **linear** in each slider, hence monotone —
  the premise bisection rests on, asserted by test 3.
- The stage multiplies RGB by a scalar, so the output **luminance** of any pixel of luminance `l`
  is exactly `l · gain(l)`. A neutral 1×1 stand-in `[l, l, l]` pushed through the real stage is
  therefore an exact model of every pixel at that luminance — which is how the solve goes
  through the stage rather than a formula.
- The exact-solve window is narrow: blacks can only land `p_lo` on 0.01 from
  `p_lo ∈ [0.0067, 0.0189]`; whites can land `p_hi` on 0.98 from `p_hi ∈ [0.653, 1.96]`. Outside
  it the honest answer is the **boundary** (levels-style: as far as the slider goes).
- ⚠ **Spec test 1 forces one guard.** A uniform grey lands every percentile at `MEDIAN_TARGET`;
  the blacks weight there is 0.52, the target is unreachable, and a bare boundary clamp returns
  −100 — dragging the whole frame down 26 %, fighting the exposure it just set. The spec's own
  wording is the rule: *"nothing to clip"*. A tail that is not distinct from the body is not a
  black or white point, so **a slider engages only when its percentile sits at least one stop
  from the median** (`p_hi > 2·median`, `p_lo < median/2`). Every real photograph passes that by
  a wide margin; only degenerate input fails it. A second, smaller guard: a percentile the
  slider has **no leverage on** (flat response) returns 0, not the boundary — a whites of +100
  that moves nothing is a lie in the panel. Both are decisions to report.

## Task 1 — `crates/pipeline/src/auto_tone.rs`

Files: new `crates/pipeline/src/auto_tone.rs`; `pub mod auto_tone;` in `lib.rs` (one line).

API:
```rust
pub const MEDIAN_TARGET: f32 = 0.16;
pub const WHITE_TARGET: f32 = 0.98;
pub const BLACK_TARGET: f32 = 0.01;
pub const EXPOSURE_LIMIT: f32 = 2.5;
pub const MAX_SAMPLES: usize = 250_000;
pub struct AutoTone { pub exposure: f32, pub whites: f32, pub blacks: f32 }
pub struct Percentiles { pub lo: f32, pub median: f32, pub hi: f32 }
pub fn percentiles(img: &ImageBuf, crop: Option<CropRect>) -> Option<Percentiles>;
pub fn solve(p: Percentiles) -> AutoTone;
pub fn analyse(img: &ImageBuf, crop: Option<CropRect>) -> AutoTone;
```
`percentiles` is public so the probe can print them; `solve` so tests can feed exact values.

Tests (spec §5, 1–6 plus monotonicity):
1. `a_uniform_grey_sets_exposure_from_the_median_and_clips_nothing`
2. `outliers_land_on_the_targets_through_the_real_stage` — ramp 0.05..0.3, 0.2 % pinned at 0.014
   and 0.2 % at 1.3; apply `ExposureStage` + `ToneRegionsStage::new(0,0,w,b)`; assert new
   `p_hi ≈ 0.98`, `p_lo ≈ 0.01`. Sabotage: swap a target, bisect against a formula.
3. `the_stage_is_monotone_in_whites_and_in_blacks`
4. `the_crop_restricts_the_analysis`
5. `degenerate_inputs_give_finite_values_inside_the_ranges` — black, 1×1, NaN
6. `exposure_clamps_at_two_and_a_half_stops` — both directions (the spec's wording has the sign
   flipped: a frame 6 EV *under* wants +6 and lands at +2.5)
7. `a_percentile_the_slider_cannot_move_leaves_it_at_zero`
8. `the_solve_reaches_the_boundary_when_the_target_is_out_of_range`

## Task 2 — `crates/app/src/auto_tone_tool.rs`

Files: new lib module; `pub mod auto_tone_tool;` in `crates/app/src/lib.rs`.

```rust
pub const ANALYSIS_DIM: usize = 512;
pub fn source_crop(crop: CropRect, o: Orientation) -> CropRect;   // oriented frame → buffer frame
pub fn analyse(buffer: &ImageBuf, geometry: &Geometry) -> (Option<Percentiles>, AutoTone);
pub fn apply(edits: &mut Edits, buffer: &ImageBuf) -> AutoTone;   // writes the three fields
```
⚠ `Session.buffer` is **pre-geometry** while `CropRect` lives in the **oriented** frame. Straighten,
lens and perspective are ignored (spec caveat 2); the quarter-turn/mirror is not, because a
portrait crop on a landscape buffer samples the wrong pixels entirely. Inverse of "mirror then
`r` turns cw" is "`4−r` turns cw then mirror".

Tests: `apply_writes_the_three_fields_and_nothing_else`; `the_crop_maps_back_through_every_orientation`
(round trip over all 8 orientations, plus a directional check that Cw90 really moves a left-edge
crop); `apply_analyses_the_cropped_region_of_the_buffer` (a bright border outside a crop under
`Cw90` must not move the result).
