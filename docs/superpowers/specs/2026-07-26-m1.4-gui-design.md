# M1.4 — Minimal GUI: Design Spec

**Milestone:** Phase 1 / M1.4 — the final M1 milestone. Turns the headless Rustroom develop engine into a genuinely usable single-image editor with a graphical interface.

**Status:** Approved design (2026-07-26). Implementation to follow in two staged plans (M1.4a, M1.4b).

---

## Goal

A desktop GUI to **open a RAW, adjust it with live feedback, crop & straighten, and export a JPEG** — reusing the existing CPU develop pipeline unchanged. Non-destructive throughout: the UI edits an `Edits` value; the pipeline renders it.

## Non-goals (explicitly out of M1.4)

- No catalog / library / filmstrip / multi-image (Phase 2).
- No GPU pipeline — the develop pipeline stays CPU; egui merely runs on the wgpu backend (GPU pipeline is Phase 5).
- No presets, no local/masked adjustments, no lens corrections.

---

## Rendering architecture

- **Framework: `eframe` (egui) on the `wgpu` backend.** Immediate-mode UI. "wgpu canvas" in this milestone means *egui is rendered by wgpu*; the develop pipeline itself is the existing CPU `pipeline` crate. Its sRGB output is uploaded as an egui texture and painted in the central panel. No hand-written wgpu render passes or shaders in M1.4.
- **Background render worker.** The UI thread never runs the pipeline. A dedicated worker thread owns the editing buffer and renders on request:
  - UI → worker: the current `Edits` (plus which preview is needed) over a channel.
  - worker → UI: a finished sRGB `ImageBuf` (or raw RGBA bytes) over a channel; the UI uploads it as a texture on receipt.
  - **Coalescing:** while a slider is dragged, only the most recent `Edits` is rendered; superseded requests are dropped. This keeps the UI at interactive frame rates even when a render takes tens of ms.
- **Zoom/pan are pure texture transforms** — they do not trigger a re-render. A render happens only when `Edits` changes (or on open/crop-mode transitions).

## Editing buffer & the half-size decision

- **On open:** decode the RAW at libraw **half-size** (linear, scene-referred — X-Trans Markesteijn demosaic is the bottleneck, so half-size is dramatically faster). Cache this as the *editing buffer*. All interactive rendering runs against it.
- **On export:** a separate **full-res** decode → `build_pipeline(current_edits).run(full)` → `export::save_jpeg`.
- **Consequence (documented tradeoff):** "100%" zoom is 100% of the *half-size* image; true full-resolution detail is only seen in the exported file. Acceptable for MVP given the snappy-open requirement.

## State

```
EditorState {
    source_path: PathBuf,
    editing_buffer: ImageBuf,     // half-size, LINEAR scene-referred (pipeline input)
    edits: Edits,                 // the single source of truth for all adjustments
    history: History<Edits>,      // undo/redo
    view: ViewState { zoom, pan, mode: View | Crop, before_after: bool },
    // caches
    baseline_render: Option<Texture>,  // render of Edits::default() for before/after
}
```

- **Undo/redo is trivial because state *is* `Edits`.** `History<Edits>` holds an undo stack and a redo stack of cloned `Edits`. A slider drag commits **one** entry on release (not per mouse-move); redo is cleared on a new edit.
- **Before/after** toggles between `baseline_render` (render of `Edits::default()`) and the current render.

## Data flow

```
Open  → rfd file dialog → half-size linear decode → editing_buffer
                        → load `<raw>.json` sidecar if present → edits
On any edit → history.push(prev) → worker renders build_pipeline(&edits).run(downscale(editing_buffer, viewport))
                                 → sRGB texture → central panel
Export → rfd save dialog → worker: full decode → pipeline(edits) → save_jpeg
                        → also write `<out>.json` sidecar
```

- **Preview downscaling:** add `ImageBuf::downscale_to(max_dim)` (area-average, in **linear** light — correct for downscaling, dependency-free, unit-testable). The worker renders at a working resolution that fits the viewport; egui magnifies for zoom > available resolution.

## UI layout & interactions

Window: top bar (Open, Export, Undo/Redo, Reset all, Before/After, zoom controls); central image canvas; **right-hand panel** (per the approved layout choice):

1. **Histogram** (top): live 256-bin RGB histogram computed from the current display render.
2. **Sliders** bound 1:1 to scalar `Edits` fields: WB temp/tint, exposure, contrast, highlights, shadows, whites, blacks. (No interactive tone-curve widget in M1.4 — see Deferred decisions; the `tone_curve` field still applies when present in a loaded sidecar.)
3. **Crop / Reset** controls.

Interactions:
- **Zoom/pan:** fit-to-window and 100%, with drag-to-pan.
- **Reset:** double-click a slider resets that field; "Reset all" sets `edits = Edits::default()`.
- **Undo/redo:** toolbar buttons + Ctrl+Z / Ctrl+Shift+Z.
- **Crop mode** (fuller version, per approved choice): entering it shows the full *straightened* frame with a draggable crop rectangle (corner/edge handles), the area outside dimmed; **aspect presets** (Free / 1:1 / 3:2 / 4:3 / 16:9) constrain the rectangle; a **rotate handle** drives `geometry.angle` live. Committing writes `geometry.crop` (normalized). While in crop mode the preview is rendered with `geometry.crop = full` (straighten still applied) so the whole frame is visible under the overlay.

## Error handling

- Decode failures / unsupported files / export IO errors surface as a non-blocking egui error banner or modal; the app stays alive.
- Missing/invalid sidecar on open → fall back to `Edits::default()` (no error shown).

## Crate structure

- **New `crates/app`** — the GUI. Binary **`rustroom-gui`**. (The existing `rustroom` CLI binary stays; the GUI can be promoted to the primary `rustroom` binary post-MVP.)
- Deps: `eframe`/`egui`, `rfd` (native file dialogs), plus existing `raw-decode`, `pipeline`, `edit-model`, `export`, `core-image`.
- **Logic lives in small, non-UI, testable units** (so the untestable egui view layer stays thin):
  - `History<Edits>` — undo/redo stack (own module, unit-tested).
  - `ImageBuf::downscale_to` — in `core-image`, unit-tested.
  - histogram computation — pure fn, unit-tested.
  - crop-rect + aspect-ratio math (constrain a rect to an aspect, map screen↔normalized) — pure fns, unit-tested.
  - the render worker's core is just `build_pipeline().run()` (already golden-tested).

## Testing strategy

- Unit tests for every logic unit above.
- `edit-model`: add `Edits::to_json_file` (sidecar write) with a round-trip test.
- The egui view code has no good unit-test story → verified by `cargo build` + a manual smoke run (open a RAW, move sliders, crop, export).
- Existing golden tests continue to guard the pipeline the GUI drives.

## Scope → two staged, independently-runnable plans

The spec covers all of M1.4; implementation splits so each plan ends in usable software:

- **M1.4a — Core interactive editor.** `crates/app` scaffold + eframe shell; half-size open via rfd; background render worker + coalescing; right panel with sliders + live histogram; zoom/pan; reset (per-slider + all); full-res export via rfd. Add `ImageBuf::downscale_to`. **Done when:** open a RAW, adjust with live preview, export a JPEG — entirely from the GUI.
- **M1.4b — Crop mode & history polish.** Crop mode (draggable rect + aspect presets + rotate handle) writing `geometry`; before/after toggle; `History<Edits>` undo/redo (+ shortcuts); sidecar load on open / save on export. **Done when:** the full-featured editor per this spec. 🎯 Milestone 1 complete.

## Open questions / deferred decisions

- **Tone-curve UI:** a proper draggable curve widget is more than a slider. Decision: defer an interactive curve editor beyond M1.4 (the `tone_curve` field still works via loaded sidecars); M1.4 exposes the scalar sliders only. Revisit when needed.
- **HiDPI / color-managed display:** the preview is shown as plain sRGB; display-ICC-aware output is a later (lcms2) concern, consistent with the pipeline's current sRGB assumption.
