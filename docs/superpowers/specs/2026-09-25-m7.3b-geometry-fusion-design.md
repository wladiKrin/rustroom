# M7.3b — one geometric resample, and a prefix reordered around it

**Date:** 2026-09-25 · **Branch:** `m7.3b-geometry-fusion` · **Status:** approved in brainstorm

## Why

Two problems in the prefix, both about resampling.

1. **Perspective and straighten each resample.** With both active the picture is interpolated
   twice. The backlog measured the second pass at **~20% of acutance** (`persp_sharpness`). It is
   the normal case for Guide Mode, whose solve writes the straighten angle as well.
2. **Noise reduction and dehaze run *after* up to three resamples** (lens, perspective,
   straighten). Interpolation low-passes and spatially correlates the noise, so NR is handed
   blotchy, correlated noise instead of the per-pixel noise it is designed to remove. Lens
   correction's fractional offset varies across the frame, so the correlation, and with it NR's
   effective strength, varies by position. It is also slow: a straighten drag re-runs NR (117 ms
   at native), dehaze and the masked capture stages on every frame, because they sit downstream
   of geometry in the prefix cache.

The code is not public and the author's sidecars were scanned (49 edit files under
`~/Pictures`, **0** with spots, **0** with active perspective), so both reorders are free of
compatibility cost now and would not be later.

## The new prefix

```
before:  lens → perspective → spots → geometry → NR → dehaze → masked NR/dehaze
after:   NR → lens → dehaze → spots → geometry(orient·perspective·straighten·crop) → masked NR/dehaze
```

The tail does not change.

- **NR first.** It sees the demosaiced source before any interpolation.
- **Lens before dehaze.** Dehaze must see the vignetting correction; a darkened corner reads as
  less haze.
- **Dehaze before spots.** A spot drag then re-runs only spots and geometry, not dehaze. The dark
  channel sees a dust spot at most as a tiny local effect.
- **Spots before geometry, now also before perspective.** See §3.
- **Masked NR/dehaze stays after geometry.** Its coverage is rasterised in frame space
  (`MaskStage::new_capture(.., &edits.geometry, ..)`), and moving it would mean mapping every mask
  kind through the homography. So a masked Luminance 50 now acts on resampled noise while a
  global one does not. That asymmetry is **recorded, not hidden**, in `capture_stages`' docs.

### The airlight

`prefix_airlight` replays the prefix up to dehaze and **skips the resampling family**, so the
airlight does not vary with a straighten drag. Its skip list becomes `LensCorrection | Geometry`
(`Perspective` no longer exists as a step). What it replays changes: today it includes spots,
after this it includes NR (both sit ahead of dehaze in their respective orders). Both are
deterministic in the edits, so invariance under geometry drags holds. The comment in
`render_engine`'s seam ("the checkpoint after geometry and noise reduction") is rewritten to say
what dehaze is actually handed.

## 2. `GeometryStage` absorbs `PerspectiveStage`

`GeometryStage::new(&Geometry, Perspective, Resampler)`. `PrefixStepKey::Geometry` carries
`(Geometry, Perspective, Resampler)`, and `PrefixStepKey::Perspective` is deleted, along with
`stages/perspective.rs`'s stage. The `Homography` type stays where it is (`pipeline::perspective`).

The geometry step is inserted when `geometry != default || perspective.is_active()`.

**Two code paths, and which runs is decided by `perspective.is_active()`:**

- **Inactive:** today's code, byte for byte. That is `orient` (exact permutation), then
  `rotate_region` if `angle != 0`, then the crop slice. `apply_region` and `input_rect_for` are
  unchanged.
- **Active:** one gather over output pixels. For output pixel `(x, y)` in the cropped frame:
  1. add the crop origin → oriented-canvas pixel;
  2. if `angle != 0`, un-rotate about the oriented canvas centre (today's inverse map, same
     association);
  3. un-orient → pre-orientation pixel, as continuous coordinates (the inverse of `orient`'s
     index permutation: `Cw90` maps `(ox, oy)` to `(oy, h-1-ox)`, and so on);
  4. inverse homography, about the pre-orientation frame's centre in half-height units, exactly
     `PerspectiveStage::render`'s normalisation;
  5. `resample::sample_region` once.

  ⚠ Step 2 is **skipped, not computed with sin = 0**, and so is step 3 on identity orientation.
  With both skipped the arithmetic is exactly `PerspectiveStage::render`'s, which is what keeps
  `perspective_vertical` and `perspective_aspect` byte-identical.

  `input_rect_for` / `apply_region` work on the fused path **including non-identity
  orientation**: all four maps (offset, rotation, permutation, homography) send lines to lines,
  so the bounding box of the four mapped corners is exact. The horizon `is_finite` guard carries
  over and declines. The inactive path keeps declining on orientation as today.

**The brush anchor space does not change.** Brushes are anchored in `GeometryStage`'s *logical*
input, meaning post-lens and post-perspective. The fused stage keeps that space as a coordinate
system (after step 3, before step 4) without ever storing it as pixels. `FrameMap` is untouched,
and so is every stored stroke.

## 3. Spots move ahead of perspective

`SpotRemovalStage` is unchanged. Its input becomes post-lens, pre-perspective, so a spot's
stored `centre`/`source` are normalised over that frame.

Gains: a spot stays on its blemish when perspective changes (today it shifts, like a brush).
The auto-pick sampler composes one inverse fewer.

**New lib type `pipeline::brush::SpotMap`**, which maps spot space to frame pixels. It is
`FrameMap` ∘ homography, in `crates/pipeline/src/brush/spot_map.rs`:

- `new(&Geometry, Perspective, frame_w, frame_h)`;
- `point([f32; 2]) -> (f32, f32)`: spot-normalised → frame px (homography forward, then
  `FrameMap::point`);
- `inverse_point(x, y) -> [f32; 2]`: frame px → spot-normalised;
- `radius_scale`: as `FrameMap`'s. On screen the outline is drawn by mapping points of the
  spot-space circle through `point`, so it is drawn exactly where it acts.

With perspective inactive it is `FrameMap` exactly. It needs the homography's **forward** map
(`Homography` today exposes `source_of`, the inverse). The forward is the matrix inverse, added
to `Homography` with a round-trip test.

App call sites that move from `FrameMap` to `SpotMap`:

- `develop/canvas/spot_overlay.rs`: drawing, hit-testing, and the sampler (which drops its
  homography step and keeps only the lens inverse);
- `develop/canvas/mod.rs`: placement click (~752) and the spot-related homography use (~1451,
  ~1595);
- `spot_tool.rs` if it maps coordinates;
- visualize-spots, if it maps coordinates.

Spot placement at the screen edge of a perspective-corrected frame may land outside `[0, 1]` in
spot space. Behaviour matches what happens today outside the frame: the stage clips.

## 4. Sidecar version

`Edits::version` goes **7 → 8**, with **no coordinate migration** (the scan above). A v7 sidecar
loads as today. The bump marks that spot coordinates changed meaning, so a later reader can tell.

## 5. Evidence, before merge

1. **Golden prediction, written before any run: ZERO existing goldens move.** No golden combines
   a reordered pair. The perspective goldens have no angle and no crop; the spot goldens have no
   perspective; the NR, dehaze and lens goldens have no second prefix stage; and the airlight
   replay for `dehaze_*` has no NR to include. If any moves, that is a finding to explain, never
   a reference to regenerate.
2. **New goldens:** `perspective_straighten` (vertical + 5° angle + crop; the fused path),
   `nr_straighten` (NR + angle; the reorder), and `spot_perspective` (a spot under active
   perspective; the new anchor).
3. **Fused-vs-chain test:** on a smooth field, the fused stage and the old two-pass chain (kept in
   the test as `PerspectiveStage`-equivalent code, not as a shipped stage) agree to within the
   error of one extra resample. **The coordinate map** agrees to ~1e-3 px, which is the stronger
   check. First assert that the two maps differ from the identity.
4. **Region = whole:** `apply_region` on the fused path equals the same rect of `apply`, bit for
   bit, including under `Cw90` orientation and mirror.
5. **`SpotMap` round trip:** `inverse_point(point(p)) ≈ p`, with perspective inactive equal to
   `FrameMap`, and agreeing with the fused `GeometryStage` (a dot painted at `p` in spot space
   lands at `point(p)` in the output).
6. **Measurements** (release build, the X-T4 frames the journal uses):
   - acutance with `persp_sharpness` (straighten + perspective), `main` vs branch;
   - `RUSTROOM_DEBUG_RENDER` per-frame time for a straighten drag and for an NR drag, `main` vs
     branch. The NR drag is expected to rise, and by how much is the number that goes in the report;
   - magnified crops of a high-ISO frame with NR and a straighten, `main` vs branch, for the
     author to judge. Photographic judgements are his.
7. The full gate: `fmt`, clippy (own target dir), `test --workspace`, each exit code read from
   its own command.

## Out of scope

- **Folding lens correction into the gather** (three passes to one). A composed map loses
  lensfun's per-row `fill_row` path, measured at 400 ms of a 1,178 ms prefix.
- **Masks' scene sliders at their global positions** (WB, exposure, contrast and tone regions
  inside a mask run after the global curve today). This is the next milestone, with its own spec.
- A GPU twin for the fused geometry stage. Geometry was never ported, and that decision stands.
