# M9.14 — Previews: instant 1:1 in Develop, Compare and Survey — design

**Done when:** an untouched RAW shows a sharp picture at 1:1 within a fraction of a second of
opening in Develop, and in a Compare pane or a zoomed Survey cell without any decode at all; an
edited photo shows Rustroom's own rendering at 1:1 the moment it opens, provided it was left once
after editing or built on demand; **nothing is built for photos that are never edited or asked
for.** The professional review's P-20 (`docs/BACKLOG.md`, "First-session reviews").

## Decisions taken in the brainstorm (the author's, 2026-09-28)

| Question | Answer |
|---|---|
| Where is the focus check done? | **Develop, Compare and Survey.** No Loupe view — Develop already plays that role. |
| What is a preview? | An 8-bit picture of the photo at up to full size, drawn instead of a decode. |
| Where does it come from? | **1** the camera's own JPEG embedded in the RAW, free; **2** Rustroom's rendering, built for an **edited** photo when it is left; **3** the same rendering built **on demand** for a selection at a tier the author chooses. |
| Declined | Automatic folder-wide builds (about an hour and 4 GB per 500 frames at the default tier); decode-ahead in memory (helps only when the dwell exceeds a decode); a GPU demosaic (a project of its own); edits applied over the camera JPEG as thumbnails do (cheap, but it lies about highlights and white balance at a size where that shows). |

## Measured (2026-09-28, this Mac: 8 cores, 16 GB; one X-T4 RAF, decode only, no render)

| Tier | One decode | Three in parallel, per frame |
|---|---|---|
| Better (the 1:1 view default) | 16.0 s | 7.4 s |
| Fast | 7.3 s | 3.0 s |
| Fastest | 3.0 s | 1.8 s |

⚠ The **7.4 s** quoted in `specs/2026-09-10-demosaic-decision.md` for Better is what three
parallel decodes achieve *per frame*; a single one is 16 s, because the X-T4 is X-Trans and its
3-pass demosaic is the cost. Rendering and encoding add a second or two per frame on top.
The X-T4 embeds a **4416×2944** JPEG (71% of 1:1 on each axis), about 4 MB, read from the file's
header offset; the backend already reaches it through libraw's thumbnail list and today shrinks it
to 512 px for the thumbnails. Extracting and decoding it takes about 0.2 s. All 899 RAWs in the
author's library are X-T4 files.

## Architecture

### Crate `raw-decode` (zero GUI)

- `extract_preview(path) -> Result<Thumbnail>`: the **largest** embedded JPEG, decoded to RGBA at
  its own size and oriented by libraw's flip code, exactly as `extract_thumbnail` orients it. The
  two share one internal function; `extract_thumbnail` is that function plus the 512-px shrink.
- `image-decode` gets the matching `preview(path)` for JPEG/PNG/TIFF: the file itself at full size,
  orientation applied. Those files are already decoded at full size for editing, so Develop never
  needs a stand-in for them; Compare and Survey do.

### App lib (`crates/app/src/`, no egui)

- **`preview_key.rs`** — `PreviewKey { thumb: ThumbKey, tier: Demosaic }` for a rendered preview:
  the thumbnail key's file identity (path, size, mtime) and edits fingerprint, plus the demosaic
  tier it was built at. One file name per key, a hash, in the store. A different tier is a
  different preview; old ones age out by the budget.
  `is_untouched(edits, fresh) -> bool` is equality with the edits a fresh open assigns
  (`Settings::initial_edits(None)`: the camera rendering and the lens decision from the settings,
  everything else default). ⚠ Not the sidecar's `is_neutral`, which compares against
  `Edits::default()` and so calls every freshly opened photo edited. Tested both ways.
- **`preview_store.rs`** — `PreviewStore::new(dir, budget)`, `user_default(budget)` at
  `<app dir>/previews` beside `thumbs`. `path_for(key)`, `has(key)`, `sweep()`, `size_bytes()`,
  `clear()`. The budget logic is `ThumbStore`'s, copied: evict oldest by mtime when over budget,
  touch mtime on a hit so a preview in use stays, sweep once at startup off the UI thread and when a
  write pushes the store a tenth over. Default budget **10 GB** (`Settings::preview_budget_mb`).
- **`preview_loader.rs`** — one worker thread, `want(&[PreviewRequest])` / `drain()` in the
  thumbnail loader's shape. `PreviewRequest { id, edits, tier }` resolves in this order: a rendered
  preview in the store for `PreviewKey(id, edits, tier)`; else, if `is_untouched`, the camera
  preview; else nothing — the caller keeps its thumbnail. The result is converted to the display
  space at load, by the same `convert_thumb` the thumbnails use, moved into a lib helper both call.
  A small in-memory LRU (three entries, `BufferCache`'s shape) so arrowing back and forth does not
  decode the same JPEG twice. A preview whose long edge exceeds the GPU's texture limit (8192 on
  this Metal device) is shrunk to it here, once, so the bin never sees an unpaintable picture.
- **`preview_build.rs`** — the queue and the job shape.
  - `LeaveQueue`: `push(id, edits, tier)` replaces an existing entry for the same photo (a photo
    edited again before its build ran is built once, with the new edits), `pop()`, `remove(id)`,
    `len()`. Pure, tested.
  - A build **is an export job**: the existing `ExportWorker` with `ExportOptions { format: Jpeg,
    quality: 90, space: Srgb, max_edge: None, demosaic: tier, dest_dir: <store> }` and the key's
    hash as the job's name and empty metadata (nothing worth embedding). Two uses of that worker:
    a **leave build**, spawned per job at width 1 from the head of `LeaveQueue` and only when no
    other build is running, so it never competes with editing; and an **on-demand build**, spawned
    per command with every selected job at the export concurrency setting. On-demand goes first
    because the leave build simply waits while one is running. ⚠ Nothing builds at quit:
    `process::exit` ends the workers, and the photo is built the next time it is left or asked for.
- **`stand_in.rs`** — the one rule Develop applies:
  `prefer_preview(wanted_long, buffer_long, preview_long) -> bool` is
  `wanted_long > buffer_long && preview_long > buffer_long`: show the preview only where the live
  buffer cannot supply the pixels the canvas asked for and the preview can supply more. The caller
  guarantees the preview is for the current edits. A table test over the fit, 50%, 71% and 1:1 cases
  before and after the full decode lands.

### App bin (egui)

- **Develop** (`develop/canvas`, `session_flow`): `PendingOpen` gains a `preview` texture beside
  the thumbnail `placeholder`; the loader is asked the moment a photo is chosen, before the decode
  debounce. While pending, the preview is drawn when it has arrived, the thumbnail until then. Once
  the session exists, `Session` holds the preview texture and its long edge; the canvas paints it in
  place of the live texture at the same rectangle, scaled by their long edges, whenever
  `prefer_preview` says so and the preview's key still matches `view_edits`. The status bar reads
  "Camera preview" or "Preview" while it is on screen. The preview is dropped when
  `buffer_is_full_res` becomes true or the edits' fingerprint changes.
  ⚠ The camera JPEG is the camera's framing and its own distortion correction; for an untouched
  photo geometry is identity, so it maps onto the frame with sub-percent differences from lensfun's
  correction — accepted, and stated in the status text's hover. A rendered preview is the exact
  post-geometry frame.
  ⚠ Declined alternative: the camera JPEG at every zoom until the full decode. The fit view would
  carry the camera's colours for up to 16 s and change under the user mid-edit.
- **Compare** (`multi/compare.rs`, new `multi/preview_pane.rs`): the panes stop decoding.
  `PreviewPane { id, zoom, pan, texture, long }` keeps `Pane`'s zoom, pan and navigation maths and
  draws the preview, or the thumbnail while one loads or builds. `pane.rs`'s `RenderEngine` path,
  and Compare's use of the decode cache and the edit decoder, are **removed** — one path, not two.
- **Survey** (`multi/survey.rs`): cells keep thumbnails at fit; a cell whose on-screen size exceeds
  the thumbnail's 512 px draws the preview instead; a scroll over a cell zooms it as a Compare pane
  does, and the same gesture zooms back out. The want-list per frame goes through the loader as the
  thumbnail window does.
- **Leaving a photo**: in the photo switch, right after `persist_current_session`, the left photo is
  pushed to `LeaveQueue` when `!is_untouched(edits)` and the store lacks its key.
- **Command**: Library → "Build previews" (`Command::BuildPreviews`) for the selection, or the open
  photo in Develop. Progress in the status bar, "Building previews 3 of 12", with Cancel in the
  export line's shape. No new bare key.
- **Settings → Display**: "Preview quality" — a combo *Same as 1:1 view · Fastest · Fast · Better ·
  Best* (`preview_demosaic: Option<Demosaic>`, `None` = follow `view_demosaic`), its hint stating
  the measured cost per frame relative to the default; "Preview cache" — size, Clear and a budget
  slider beside the thumbnail cache's, `preview_budget_mb` default 10240. The startup sweep runs
  beside the thumbnail stores'.

## Data flow

1. A photo is chosen → the previous one is persisted and, if edited and unbuilt, queued → the
   loader is asked for the new one's preview → the decode starts after the debounce as today.
2. The preview lands → a texture; drawn as the placeholder while pending, then wherever
   `prefer_preview` allows, until the full decode lands or the edits change.
3. Compare and Survey build a want-list per frame; the loader answers; panes draw preview or
   thumbnail.
4. A build job decodes at its tier, renders with the photo's edits through `export_one`, writes the
   JPEG into the store; the loader's LRU entry for that key is dropped so the next want reloads it.

## Errors and edges

- No embedded JPEG (some DNGs): no camera preview; the thumbnail stays. A JPEG/PNG/TIFF is its own
  preview.
- A store write fails: one status line, the job is dropped, no retry loop.
- A preview smaller than the frame is shown sharp to its own size and upscaled past it.
- A rebuilt photo: the old key's file ages out by the budget; nothing deletes it eagerly.
- Two instances on one profile write the same store; file names are content-keyed, so the worst
  case is the same JPEG written twice.

## Testing

- `raw-decode`: `extract_preview` on the `RAW_FIXTURE` file is larger than the thumbnail and
  oriented the same way (fixture-gated, like the backend's existing tests).
- `preview_key`: untouched is equality with `initial_edits(None)`, and a fresh photo is untouched
  while `is_neutral` would call it edited (the fixture check: prove the two disagree).
- `preview_store`: the budget and key tests copied from `ThumbStore`'s.
- `preview_loader`: resolution order (rendered beats camera beats nothing), the LRU, the texture
  cap.
- `preview_build`: `LeaveQueue` replaces a re-edited entry and keeps order; a build's export options
  are JPEG 90 sRGB full size at the given tier.
- `stand_in`: the table.
- Compare: the panes are on the preview path and no decode is requested (the existing pane tests
  rewritten against `PreviewPane`); Survey: a large cell asks for a preview, a small one does not.
- The wiring is confirmed in use: Develop's stand-in and its status text, Compare's sharpness,
  Survey's zoom, the command's progress, the Settings rows.

## Out of scope

A Loupe view; decode-ahead; a GPU demosaic; previews for Immich assets beyond what their
downloaded originals give through the same path; the `rustroom`/`Rustroom` release-binary
collision on case-insensitive disks (its own small fix).
