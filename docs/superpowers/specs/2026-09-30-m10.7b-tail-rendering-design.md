# M10.7b — Rename `ProfileRendering` → `TailRendering`

**Date:** 2026-09-30 · **Branch:** `m10.7b-tail-rendering-rename` · **Status:** design approved

`pipeline::ProfileRendering` holds what the tail's rendering needs that `Edits` cannot carry — the camera
profile's curve and baseline exposure **and** the creative look's table. Its own doc said so on
2026-09-18: *"The name is narrower than the contents — `look` is not a camera-profile field — and
`TailRendering` would be the better one"*, left for a change of its own.

## Scope (the author's call)

**The type and its bindings.** `ProfileRendering` → `TailRendering` at all 270 mentions in 41 files
(pipeline, gpu-pipeline, app, the CLI, examples), and the 25 bindings of the type named `profile` →
`rendering`: 14 function parameters (9 pipeline builders, 2 in `render_engine`, 3 in `accelerate`) and
`accelerate`'s struct field with its initialisers.

**Kept:** `decode::profile_rendering`, which really does read the camera profile; the history — the
journal, specs and plans — as written.

## Approach

Compiler-driven. The type by a whole-word `sed` (`TailRendering` appears nowhere yet but in the note
proposing it). The bindings by renaming only each **declaration**, then fixing exactly the uses the
compiler reports as unresolved — so a comment saying "camera profile" is never rewritten by the
mechanics. Comments that do mean this struct are reviewed by hand. No function holding such a parameter
has another `profile` in scope, so no old use can silently resolve to a different binding.

## Verification

A pure rename: nothing may move. All targets compile (examples included); all tests pass with the 82
goldens and the GPU parity tests unchanged; a grep finds no `ProfileRendering` and no `profile:` binding
of the type, with a positive control counting the new name.
