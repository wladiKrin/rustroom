# M10.8a — Keyword suggestions, type-to-tag, and undoable tagging

**Date:** 2026-09-30 · **Branch:** `m10.8a-keyword-suggestions` · **Status:** design approved

Phase 10's M10.8a: *"Keyword suggestions (2026-08-26)"* — the M4.2b journal's accepted caveat (6), "no
keyword suggestions — needs usage data and a heuristic". The catalog now has both: every file's capture
time (`photo_capture.taken`) and every assignment (`photo_keywords`).

## Decisions (the author's)

- **Signals:** keywords from photos taken **on the same capture day(s)** as the selection, and keywords
  that **usually go with** the ones the selection already has — Lightroom's model — **plus typing
  autocomplete.** No "recently used" (it would need assignment times the catalog does not keep).
- **Placement:** the rail's Keywords section **and** a Suggested group in the right-click Keywords
  submenu (which the filmstrip shares, so Develop gets it too).
- **Form in the rail:** up to five rows **like the tree's** (`docs/DESIGN.md` §7.6) — name, parent faint
  as meta, the same `+` action; a click on the row opens the keyword, as in the tree. §7.7 rules out
  chips: they are filters and states, never buttons.
- **Typing:** type to tag — with photos selected, the field's list offers matching keywords and Enter or
  a click tags the selection; a new name is created and tags. With nothing selected it creates only.
- **Undo:** tagging becomes an undo step on **every** route, and creating from the field too.

## Design

### Suggestions (lib `keyword_suggest`, no egui)

For the selected **files** (keywords are per file; copies share them):

- **Same day** — `day(k)` = share of the photos taken on the selection's capture day(s), the selection
  excluded, that carry `k`. A day is `date(taken, 'unixepoch')`, the Dates tree's day. Photos without a
  capture time contribute nothing.
- **Companions** — for each keyword `j` on the selection, `P(k | j)` = files carrying both / files
  carrying `j`; `comp(k)` = the best over `j`.
- **Score** = `day(k) + comp(k)`; ties by usage count (descending), then name. **Excluded:** a keyword
  already on every selected file, and every ancestor of one (the XMP path carries parents already); a
  score of zero. A keyword on *some* selected files stays — tagging makes the selection uniform.
- Up to **five**, in the rail and in the menu alike.

**Catalog** (`db/keywords.rs`): `day_keyword_counts(photos) -> DayCounts { neighbours, counts }` and
`companion_counts(keywords) -> HashMap<(j, k), usize>`. **Cached** in the app per (selected files,
`Connection::total_changes()`), so the rail's 60 Hz redraw queries nothing and every catalog write —
from any route, present or future — refreshes it without a list of call sites to keep in step.

### Autocomplete (lib `keyword_suggest::complete`)

Case-insensitive on the name: exact first, then prefix, then substring; each group by path. Up to eight
matches, each with its parent path (`Places › Europe`).

### The field (bin `keyword_field`)

The Keywords section's field reads **"Tag with a keyword"** while photos are selected and **"New
keyword"** (or "New keyword under X") otherwise. Typing opens a list under it: ↑/↓ move, Enter or a
click picks, Escape closes. **With a selection:** a pick tags it; a name with no match is created (under
the last-clicked keyword, today's rule) and tags it. **Without:** Enter creates; an exact match is shown
first, and picking it opens that keyword instead of making a duplicate.

### Suggested rows and the menu group

- **Rail:** a `Suggested` label (Caption, `text2`) and up to five §7.6 rows between the field and the
  tree, hidden when nothing is selected or nothing is suggested.
- **Right-click → Keywords:** `Suggested` at the top with the same tri-state marks, a separator, then
  the full list.
- Every route tags through `assign_keyword_to_selection` / `set_keyword_on_targets`, so the XMP write is
  `+`'s by construction.

### Undo

- **`ActionKind::KeywordTag { keyword, on, files }`** — `files` are only those whose state **changed**, so
  undo never removes a tag a photo already had. Undo reverses them and rewrites their XMP; redo reapplies.
  `assign_keyword` / `unassign_keyword` now report whether they changed a row. Every tagging route pushes
  one: the rail's `+`/`−`, the menu toggle, a suggestion's `+`, type-to-tag. Nothing changed, nothing
  pushed.
- **`ActionKind::KeywordCreate { id, name, parent }`** — only when the call actually created a row
  (`create_keyword` returns an existing keyword's id for a name already there). Undo deletes it; redo
  re-inserts it with the same id (`unmerge_keyword`'s precedent).
- **Create-and-tag is one step:** a `Batch` of the two, undone in reverse.

## Tests

- **Ranking:** a same-day keyword outranks an unrelated one; a companion is suggested; a keyword on every
  selected file and its ancestors are not; one on some is; the tie order; at most five. Positive
  controls first (the fixture must produce suggestions at all).
- **Autocomplete:** exact, prefix, substring order; paths; case.
- **Catalog:** both queries against a real catalog; `assign`/`unassign`/create report changes.
- **GUI** (through `test_ui`): the Suggested rows appear for a selection and not without one; their `+`
  tags and writes the XMP; the menu's Suggested group; typing + Enter tags; a new name + Enter creates
  and tags; the hover walk covers the new controls.
- **Undo:** undoing a tag leaves a pre-existing tag; undo and redo rewrite the XMP; one undo removes a
  created-and-tagged keyword entirely; each route pushes exactly one step.
- Sabotages, each red: the day signal off; the ancestor exclusion off; changed-files recording all files;
  the cache key without `total_changes()`.
