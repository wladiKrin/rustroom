# M10.8d — Batch rename

**Date:** 2026-10-02 · **Branch:** `m10.8d-batch-rename` · **Status:** design approved

Phase 10's M10.8d: *"Batch rename — today one photo at a time; the import filename template exists
(P-26, 2026-09-28)"*.

## Decisions (the author's)

- **The names come from the template field** Import and Export already use, with a live preview.
- **Photo → Rename… and the right-click**, on the selection.
- **`{seq}` counts in grid order from a start number** (1 unless typed); a RAW+JPEG pair takes one.

## Design

### The command and the dialog

- **Photo → Rename… ⌘R** (free; a chord here is a character, so Lightroom's F2 cannot be one) and
  the right-click's existing **Rename**, both on the selection (the right-click: its targets).
  `Command::RenamePhotos`. ⚠ Found while building: the right-click already had a single-photo
  *Rename* (in place — the caption, or a copy's label). It stays one entry: **one photo is renamed in
  place, two or more open the dialog** (`CellAction::RenameFiles`), rather than two entries that read
  alike.
- **`Modal::Rename`**: the template field (remembered — `Settings::rename_template`, default
  `{date}-{seq:3}`), **Start at** (a number, 1 each time), a **preview** of the first three as
  `DSCF1234.RAF → Berlin-001.RAF` plus *"and N more"*, the template's error in place of the preview,
  and Rename (enabled only on a valid template with something to rename) / Cancel. The field's hover is
  `filename_template::token_hover`. A note says when Immich photos will be left out.
- **Tokens** `{name} {seq} {date} {camera}`. **`{copy}` is refused** with its own message: a rename
  changes the file every virtual copy shares, so a copy number has nothing to name.

### What is renamed

- **The files behind the targets, in grid order**: the targets sorted by their row, then
  `files_of` (a collapsed stack brings its files; a copy, its file; each file once).
- **One photo = the files sharing a folder and a stem** (a RAW+JPEG pair): one `{seq}` number, one new
  stem, **each file keeps its own extension**. `{name}` is that stem; `{date}`/`{camera}` come from the
  catalog's `photo_capture` (the first file with a row), read from the file when the catalog has none.
- **Never overwrites.** A name held by a file outside the rename — on disk, by a sidecar, or by a
  catalog row of a vanished file — gets `-1`, `-2` (Move to folder's rule, for the whole photo).
- **The renamed photos do not block one another.** Their current names count as free; a photo whose
  name would not change is left alone and keeps its name reserved. When a target is another file's
  current name, the rename goes in **two passes** — every file to a temporary name in its folder, then
  to its final one — so renumbering a set or swapping two names works. A file that fails is put back
  where it was and named in the status row; the rest stay renamed.
- **Immich photos are left out and counted** — they live in the cache under the server's names (Move
  to folder brings them out first). A file that is not there is left out too.

### What follows the file — one path, shared with Move to folder

- `photo_move` moves the JSON sidecar and a RAW's XMP; the catalog re-keys **every** per-file table
  (`PER_FILE_TABLES`) in one transaction, two-pass when names chain; `after_move` re-keys the decode
  cache, forgets the old ids' in-memory history, fixes the Library and the open photo.
- **One undo step**: `ActionKind::PhotoMove`. Its replay goes through the same two-pass move, so
  undoing a swap works.
- **The selection follows** the renamed photos (`after_move` re-keys the rows before the rebuild, in a
  folder view too), and **the hand stacks are reloaded** after every move (a stacked pair renamed stays
  a stack; Move to folder had the same stale map).
- **The single rename (the caption) goes through it too.** Read from the code: `rename_file` moves the
  JSON sidecar but not a RAW's `.xmp`, and `Catalog::rename_photo` re-keys only `photos` and
  `photo_keywords` — a renamed photo would lose its description, history, capture facts and stack.
  **A test proves both first**; then `rename_file` uses `photo_move::move_file` and
  `Catalog::move_photo`, and `rename_photo` is removed.

### Placement

- **Catalog** (`db/moves.rs`): `move_photos(&[(from, to)])` — one transaction, a temporary name no
  file can have (it contains `/`) when names chain; `move_photo` calls it.
- **Lib**: `filename_template` — `Template::parse_for_rename` (refuses `{copy}`); `batch_rename.rs`
  (pure) — `photos_of(files)` groups by folder and stem in order, `plan(photos, template, start,
  taken) -> Vec<Planned>`; `photo_move::move_all(plans)` — direct or two-pass, a result per plan,
  tested on temporary directories.
- **Bin**: `rename_flow.rs` — opening the dialog (targets → photos → facts), the rename, the status;
  `modals/rename.rs` — the dialog; `menu`/`commands`/`library/cell_menu` wiring; `move_flow` —
  `after_move`'s selection and stacks, the replay through `move_all`; `copies::rename_file` on the
  shared path; `Settings::rename_template`.

## Tests

- **Catalog:** two photos' rows swap names with every table intact; a rename carries description,
  history, capture and stack (the single-rename gap, red before the fix).
- **Lib:** `{seq}` in order from the start number; a pair takes one number and keeps both extensions;
  a name taken outside gets `-1` for the whole pair; a swap and a shifted renumbering plan without
  suffixes; an unchanged photo is left out and keeps its name; `{copy}` refused, the other errors still
  reported; `move_all` swaps two files with their sidecars, and a failure puts the file back.
- **App:** ⌘R through the menu opens the dialog on the selection; Rename renames in grid order as one
  undo step; undo restores names, sidecars, XMP and catalog rows; the selection follows; a renamed hand
  stack stays a stack; Immich photos are left out and counted; the single rename keeps its XMP and
  every catalog table; the dialog's preview shows the first names and the error on a bad template.
- **Sabotages, each red:** the pair split; the batch's own names counted as taken; the direct pass on
  a swap; the catalog's single pass; `{copy}` accepted; the selection not re-keyed; the stacks not
  reloaded; `rename_file` back on `rename_photo`.
