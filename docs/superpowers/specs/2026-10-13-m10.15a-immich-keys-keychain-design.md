# M10.15a — The Immich API keys in the OS keychain

**Date:** 2026-10-13 · **Branch:** `m10.15a-immich-keychain` · **Status:** design approved (option 1)

## Why

Both Immich keys — the read-only **browse** key and the write-capable **upload** key — sit in
plaintext in `settings.json` (`-rw-r--r--`): readable by anything running as the author, and carried
into every backup or copy of the file. Rustroom has never stored a secret; the OS credential store is
the right home (`docs/BACKLOG.md`, M10.15a).

## Decisions (the author's)

- **The OS keychain, read once per launch** (option 1 of three). Both keys in **one** keychain item,
  so at most one access prompt per launch.
- ⚠ **Accepted cost:** today's builds are ad-hoc signed and the signature changes with every rebuild;
  macOS ties an item's access to the signature that wrote it, so the **first launch after a rebuild
  asks once** ("Rustroom wants to use your confidential information…"). Properly signed release
  builds (Phase 11) would not prompt. Rejected: a `0600` secrets file (any process running as the
  user can still read it); an item open to every app (defeats the purpose).

## Behaviour

- The keys live in the OS credential store: **macOS Keychain**, **Windows Credential Manager**,
  **Linux Secret Service** — one item, service `Rustroom`, account `immich`, holding both keys as JSON.
- **`settings.json` no longer contains them** whenever the keychain accepted them.
- **Existing keys move over by themselves** on the first launch: read from `settings.json`, written to
  the keychain, and only then removed from the file.
- **Where no keychain works** (a Linux box with no keyring daemon, a write the OS refused), the keys
  stay in `settings.json` as today — never lost, never silently dropped — and the Settings window's
  key fields say where they are kept.
- **A denied or failed read** leaves the keys as `settings.json` has them (empty, once migrated): Immich
  is simply not connected this session, and nothing is written or deleted.
- Nothing else changes: the Settings window edits the keys exactly as today, Test checks what is typed,
  Apply saves.

### The one rule that keeps it safe

**Plaintext keys in `settings.json` are always the newest** — they are only ever written there when the
keychain could not take them. So on load they win over a keychain item and are moved into it; on save,
the file loses them only after the keychain write succeeded. No path deletes a key before another copy
exists.

## Design

### `rustroom_app::secrets` (new lib module, no egui)

- `Keys { browse: String, upload: String }` — serde, the item's content.
- `trait SecretStore: Send + Sync` — `read() -> Result<Option<Keys>, SecretError>` (`Ok(None)`: no item
  yet), `write(&Keys) -> Result<(), SecretError>`, `name() -> &'static str` (for the hover text:
  "your keychain").
- `Keychain` — the real store, through the **`keyring`** crate (v3: apple-native, windows-native, and
  for Linux the pure-Rust `async-secret-service` over zbus, so CI needs no `libdbus`; the exact feature
  names are checked against the crate's docs when it is added).
- `Memory` — for tests; it can be told to fail, to exercise the fallback.

### `SettingsStore` (`settings/store.rs`)

- Gains `secrets: Option<Box<dyn SecretStore>>` and the keys it last wrote (so a settings save — which
  happens on many ordinary UI changes — touches the keychain **only when a key changed**), plus where
  the keys currently live (`Keychain` / `File`), for the hover text.
- **`user_default()` — the app's only constructor — uses `Keychain`.** **`new(path)` — every test's —
  uses none**, so behaves exactly as today and **no test can reach the real keychain**. A
  `with_secrets(path, store)` constructor serves the tests of this feature with `Memory`.
- `load()`: read the file; with a store, read the item; apply *the one rule* (file keys win and are
  migrated; otherwise the item's keys fill `Settings::immich_key` / `immich_upload_key`).
- `save(s)`: with a store, write the item when the keys differ from the last written; on success write
  the file with both key fields **blank**; on failure write them in plaintext (the fallback).
- `Settings` keeps its two fields as the **in-memory** keys, so `immich_source::connection`,
  `immich_upload::config` and the Settings window are unchanged.

### The Settings window

The two key fields' hover sentences say where the key is kept — "…, kept in your keychain" or "…, kept
in plain text in settings.json" — from the store's state (one sentence each, under 110 characters).

## Tests

- With `Memory`: a saved `settings.json` contains **neither key**, and a reload restores both.
- **Migration:** a file with legacy plaintext keys loads them, writes the item, and the file loses them.
- **Fallback:** a store that fails to write leaves the keys in the file, and a reload still has them.
- **A failed read** with a migrated file: keys empty, the file untouched, nothing written.
- **The file wins:** plaintext keys beside an older item replace the item.
- **No keychain churn:** saving settings with unchanged keys does not write the item (counted).
- `SettingsStore::new` stays keychain-free (no store) — the existing settings tests unchanged.
- One `#[ignore]`d test round-trips the **real** keychain under a throwaway account, run by hand.
- The hover sentences pass `every_hover_is_one_short_sentence`.

## Out of scope

Signing the builds (Phase 11, which also ends the rebuild prompt); per-server keys (one server is
configured today); any other secret (there is none).
