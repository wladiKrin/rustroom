# M10.15c — Read Immich's own rating and favourite

**Date:** 2026-10-13 · **Branch:** `m10.15c-immich-rating` · **Status:** design approved

## Why

Stars and favourites set in Immich's own apps — the phone, the web — never reach Rustroom, which shows
only its own marks. This is the **read** half of the two-way sync declined on 2026-09-24 and re-opened
as M10.15d: Rustroom reads the server's marks and **never writes** them back.

## Measured (2026-10-13, the author's server, Immich v3.2.0)

Captured replies of `POST /search/metadata` — the request behind every album and Timeline month:

| | Album, 1,022 photos | Favourites |
|---|---|---|
| `isFavorite` | in **every** reply, a plain bool | **1 photo** in the library |
| Rating | only with `withExif: true`, at `exifInfo.rating` | — |
| Ratings present | **0 of 1,000** (all `null`) | the one favourite: `null` |
| Asking for the rating | **858 KB → 1,327 KB (+55%)**; **0.60–0.65 → 0.78–0.83 s** (+~180 ms) | — |

The server's schema: a rating is **1–5**, `null` unrated (0 no longer valid since v3); **writing** allows
**−1 = rejected**, while the **reply's** schema says 1–5 only — a contradiction no real reply could settle
(no photo is rejected), so −1 is handled deliberately rather than trusted away. The author builds this
for the marks he will set in Immich, knowing there are none today.

## Decisions (the author's)

- **Fill only where Rustroom has nothing** — a mark set in Rustroom is never overridden.
- **Each mark fills at most once per photo** — a filled mark the author clears or changes stays as he
  left it; Immich never fills that mark again.
- **Immich's favourite becomes a pick** flag; **−1 (rejected) becomes a reject** flag; both on one
  photo → **pick**.
- **Stars and favourites both** (not favourites alone), accepting the larger replies.

## Behaviour

When an Immich album or Timeline month is opened — from the server or from the list cache:

- Immich's **1–5 stars** fill the photo's **rating** if it is 0 and has never been filled.
- A **favourite** fills a **pick**, a **−1** a **reject** (no stars), if the photo is unflagged and its
  flag has never been filled. Favourite and −1 together → pick.
- Anything else — `null`, 0, out-of-range values — fills nothing.
- Only the **original** (copy 0); virtual copies keep their own marks.
- A mark Rustroom already has is untouched, and a fill is not an undo step — it is not the user's act.
- **Never written to Immich.**

⚠ "Never filled" is per mark: a photo first seen unrated and rated in Immich later still fills once; one
already rated in Rustroom when Immich's rating is seen is not filled — and, if that rating is cleared
later, Immich's fills it then (Rustroom has nothing at that point, and it was never filled).

### When a mark arrives

Whenever a list is **fetched** from the server: every album and month **once** after this ships (the
list cache's format version changes), then when a list changes — an album by its photo count or last
change, a month by its count. ⚠ A rating added in Immich to a photo whose cached month has not changed
arrives only with that month's next fetch (or any album holding it that is refetched). Accepted: making
it immediate means giving up the list cache's instant opening.

## Design

### `immich` crate

- `Asset` gains **`is_favorite: bool`** (`#[serde(default)]`) and **`exif_info: Option<ExifInfo>`**
  (`#[serde(default)]`), `ExifInfo { rating: Option<i32> }` (`#[serde(default)]` on the field — the reply
  schema does not list it as required). Both default because the lists cached today lack them. Nothing
  else of `exifInfo` is modelled — GPS and the rest have no use here.
- `Filter::body` sends **`withExif: true`** for both an album and a month.
- A fixture **captured** from the author's server and **trimmed** to the fields the DTO reads (the GPS and
  the rest of `exifInfo` removed), saying so; the 3-star and −1 cases are **constructed**, and say so.

### `catalog` — schema v12 → v13

- `photos` gains **`filled_rating INTEGER NOT NULL DEFAULT 0`** and **`filled_flag INTEGER NOT NULL
  DEFAULT 0`**. On the photo's own row, so a move (`PER_FILE_TABLES` already lists `photos`) carries them.
- **`fill_from_server(&[ServerFill]) -> Result<usize>`** (`ServerFill { photo: PathBuf, rating:
  Option<u8>, flag: Option<Flag> }`), one transaction, the whole rule in SQL — e.g.
  `UPDATE photos SET rating = ?, filled_rating = 1 WHERE … AND copy = 0 AND rating = 0 AND filled_rating = 0`
  — so there is no read-then-write. Returns how many marks it filled. ⚠ A fill that changes nothing
  leaves `change_count` alone (`total_changes` counts changed rows), so no view refreshes for nothing.

### App

- `immich_catalog` (lib): **`server_marks(&Asset) -> (Option<u8>, Option<Flag>)`** — the mapping — and
  **`fill_marks(cat, root, assets)`**, which passes only assets carrying a mark.
- `open_immich_album` and `open_immich_bucket` call `fill_marks` right after `record_assets`, before the
  grid is built, so the marks show as the list opens.
- `immich_list_cache::VERSION` **1 → 2**.

## Tests

- The captured fixture parses (`isFavorite` true, rating `null`); an old cached list without the new fields
  parses (`false`, no rating); both request bodies carry `withExif: true`.
- The mapping: 1–5 → stars; favourite → pick; −1 → reject, no stars; favourite + −1 → pick; 0, 6, −2,
  `null` → nothing.
- The fill: an empty mark fills; a set one is kept; filled-then-cleared stays cleared; a never-filled photo
  rated later fills; a copy is untouched; a fill that changes nothing leaves `change_count`; v12 → v13
  keeps every row and starts both columns at 0; a moved photo keeps its filled state.
- The list cache: a version-1 file is a miss.
- Through the app: opening an album whose assets carry marks puts them in the catalog at once.

## Out of scope

Writing marks to Immich (M10.15d); following later re-ratings in Immich (the author chose fill-once);
colour labels (Immich has none); refetching lists whose validator has not moved.
