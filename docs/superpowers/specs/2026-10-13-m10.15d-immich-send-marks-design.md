# M10.15d — Send marks to Immich (two-way sync, the write half)

**Date:** 2026-10-13 · **Branch:** `m10.15d-immich-send-marks` · **Status:** design approved

## Why, and why now

Declined 2026-09-24 ("too dangerous"), re-opened by the author 2026-09-29. The decline recorded what a
reopening needs: **writes attended and reversible — per photo, confirmed, the prior value recoverable** —
and a need the additive path (uploading edits as *new* assets) cannot serve. Both now hold: the author
wants **his Rustroom marks visible on the photos already in Immich** (an upload never changes those), and
this design writes only on a deliberate, confirmed send with the replaced values kept for an undo.

M10.15c built the read half (Immich's marks fill Rustroom's once). This is the write half.

## Decisions (the author's)

- **What:** marks only — ★1–5 → `rating`; **pick → `isFavorite`**; **reject → `rating: -1`**. Colour labels
  have no Immich equivalent. Keywords and captions are out of scope.
- **When:** only on a deliberate **Send marks**, with a confirmation listing every change.
- **Undo:** **Undo last send** restores what the last send replaced.
- **Never remove:** a photo with no rating or no flag in Rustroom leaves Immich's as it is — a send never
  clears a mark in Immich.
- **The key:** the upload key, renamed **Write key**, gains `asset.update` in Immich (the author edits it;
  Immich lets a key's permissions change). Browsing stays read-only by credential.

**Mine:** a photo with **stars and a reject** in Rustroom sends **−1** (Immich cannot hold both; the reject
is the more deliberate mark) — its line says so.

## Measured / read (2026-10-13, the author's server, v3.2.0)

`PUT /assets` (`AssetBulkUpdateDto`: `ids`, `rating`, `isFavorite`, plus fields this never sends) needs
`asset.update` and answers **204**; there is **no bulk read by id**, but an album or month is one search
per 1,000 assets (~0.8 s with `withExif`). `asset.update` can also change dates, location, descriptions and
archive state — Rustroom sends only `rating` and `isFavorite`; it cannot delete. ⚠ All from the published
schema; **the first real send goes to one photo the author chooses, with his OK**, and its reply is
captured before anything else relies on it.

## Behaviour

- **Send marks** sits in the status row beside Download / Remove downloads — an Immich album or month
  with a selection. ⌘A covers the whole album or month. It acts on the selected photos' **originals**
  (a virtual copy counts as its original; Immich has one asset).
- **Check:** the album's or month's **current** list is fetched from the server (not the cache) — the
  status row says "Checking Immich…".
- **Confirm:** a dialog lists every photo that would change, one line each (`IMG_1234.jpg  ★3 → ★5`,
  `… favourite`, `… rejected (−1)`), a count line, and calls out lines that **replace** a mark Immich
  already has. Nothing to change → no dialog: "Immich already has these marks".
- **Send:** one `PUT /assets` per distinct change, with the Write key. Before writing, the prior values of
  every photo the send changes are kept; after it, **only what landed** is recorded as *the last send*.
  The album's or month's cached list is dropped, so its next opening shows the new state. Status:
  "Sent marks for 12 photos to Immich".
- **Undo last send** (in the status row's ⋯, present only while a last send exists): a confirmation, then
  the prior values written back exactly — a replaced ★3 returns, a photo that had no stars becomes
  unrated again (`rating: null`), a favourite added is removed. What landed leaves the record; it is empty
  once all has.
- **Failures:** a 401/403 → "The Write key cannot change photos — add asset.update to it in Immich";
  nothing recorded. A send that half lands records the half that landed and says how many did not.
  No Write key → "Send marks needs a Write key — set one in Settings → Immich".
- **Settings:** "Upload key" → **Write key**; its hover: "An optional Immich key that can upload and change
  marks, used only by Export and Send marks" (+ where it is kept); every message naming the upload key
  says Write key.
- Never automatic: nothing is sent except by the confirmation's button.

## Design

### `immich` crate

`Client::update_marks(ids, rating: Option<Option<i32>>, favourite: Option<bool>) -> Result<(), Error>` —
`PUT /assets`, a body with `ids` and only the fields being set (`"rating": null` for an undo to unrated);
expects 2xx. A crate-visible body builder, asserted without a server.

### `rustroom_app::immich_send` (new lib module, no egui) — every decision

- `ServerMarks { rating: Option<i32>, favourite: bool }`; `Candidate { asset_id, name, mine: Marks,
  server: ServerMarks }`; `Change { asset_id, name, before, after }`.
- `wanted(mine, server) -> ServerMarks` — the mapping under never-remove: reject → −1; else stars 1–5 →
  stars; else the server's rating. Pick → favourite true; else the server's favourite.
- `plan(&[Candidate]) -> Vec<Change>` — only photos whose `wanted` differs.
- `groups(&[Change]) -> Vec<Group { ids, rating: Option<Option<i32>>, favourite: Option<bool> }>` — one
  per distinct delta, a field present only where it changes.
- `undo_groups(&[(String, ServerMarks)]) -> Vec<Group>` — both fields, to the prior values.
- `line(&Change) -> String`, `summary(&[Change]) -> String` — the confirmation's words.

### `catalog` v14

`immich_last_send (asset_id TEXT PRIMARY KEY, rating INTEGER, favourite INTEGER NOT NULL)` — keyed by
Immich's asset id, not by file (a move does not concern it). `record_send(&[(id, rating, favourite)])`
replaces it; `last_send()`; `forget_sent(&[id])` removes what an undo restored.

### Worker

`Job::CheckMarks { source }` (album id or month; the read-only key) → `Outcome::CheckMarks`;
`Job::SendMarks { conn, groups, undo }` (its own connection: the Write key) → `Outcome::SendMarks {
landed: Vec<usize>, error: Option<String>, undo }` — groups in order, stopping at the first failure.

### App (bin)

- `send_flow.rs` (new; `immich_flow.rs` is 531 lines): `begin_send_marks`, the check's outcome → the
  plan → `Modal::SendMarks`, `confirm_send`, the send's outcome → the record, `begin_undo_send`,
  `confirm_undo`.
- `modals/send_marks.rs` (new): the confirmation (a scrolling list) and the undo confirmation.
- `status_immich.rs` (new): the Immich buttons **moved out of `status_bar.rs`** (627 lines of code and doc,
  over the 600 this project flags) with **Send marks** added; ⋯ gains **Undo last send**.
- Settings: the field's label and hover; `secrets::key_hover`'s Upload sentences.

## Tests

- **Request:** bodies for rating only, favourite only, both, and `rating: null`; method and path.
- **Mapping and plan:** nothing to send; equal values not sent; stars; pick → favourite; reject → −1 with
  the heart kept; stars + reject → −1; unrated / unflagged never sent (never remove); a replaced value
  flagged as replacing.
- **Groups:** identical deltas share one group; different deltas split; undo groups set both fields to the
  prior values, `null` included.
- **Words:** the lines and summary; every glyph in them renders in the bundled fonts (the existing
  renderable check) — or the line uses words.
- **Catalog:** record replaces; forget removes; v13 → v14 keeps every row.
- **Through the app, with a fake server:** confirm sends exactly the planned groups and records the prior
  values of what landed; a 403 records nothing and names `asset.update`; a half failure records only the
  half; undo sends the prior values and empties the record; **nothing reaches the server before the
  confirmation** (the recording fetcher holds no `SendMarks` after the check).
- **The real reply:** one send and its undo on one photo the author picks, with his OK.

## Out of scope

Keywords → tags, captions → descriptions; sends from catalog-wide views (All Photos, collections); a
history of sends beyond the last; anything automatic.
