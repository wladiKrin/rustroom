# M10.18a — Tethered capture: design

**Status:** written 2026-10-28. The author skipped the questions ("start"), so every choice below is
**my call** unless marked otherwise, and each one is open to correction once it has been tried.

## Intent

A camera on a USB cable to the computer. Each frame you take lands in Rustroom a few seconds later,
already in the catalog and selected, so you can judge focus and light on a big screen while you
shoot. That is tethering. Rustroom can also fire the shutter itself, which matters on a tripod or
copy stand.

Success is when the author plugs in the X-T4, chooses File → Tethered capture…, presses the camera's
shutter, and the shot appears in the Library, or in Develop when that is open, without touching the
mouse.

## Goals

1. **Detect** a camera on USB and name it ("Fujifilm X-T4").
2. **Receive** every shot taken on the body. Download it into the session's folder under the
   camera's own file name, then catalog it, open it and select it.
3. **Shoot from Rustroom.** A Shoot button and **F12** (bindable) fire the shutter. The result
   arrives the same way.
4. **Apply on entry** an optional develop preset, the import's preset and `ingest::entry::apply`.
5. **Show the live state** in the status row: the camera, the shot count, Shoot and Stop. A
   disconnected cable or a camera error says so in one sentence and ends the session cleanly.

## Non-goals (this milestone)

- Live view, and setting shutter, aperture or ISO from Rustroom. Both need per-model widget work.
  They are named here so they are not forgotten.
- Wi-Fi tethering. It's a different protocol per vendor.
- Watching a folder that another program writes to. It's cheap to add later, and it isn't needed
  while libgphoto2 talks to the camera directly.
- Deleting anything on the camera. The card is only ever read, the import's rule.
- More than one camera at a time.

## Anti-goals

- **A lost or half-written frame.** The download goes to `<name>.part` and is renamed only when
  complete. A name already taken gets `-2`, `-3`, … and is never overwritten.
- **A UI that stalls.** libgphoto2 blocks for seconds and isn't thread-safe. One background thread
  owns the camera for its whole life, and the app only talks to it through channels.
- **A build that needs a camera library to compile everything else.** The libgphoto2 backend sits
  behind a cargo feature. The rest of the crate builds and tests without it.

## How it is built (my calls)

### Crate `tether` (no GUI)

- `Camera` trait: `name()`, `wait(timeout) -> Result<Option<CameraFile>>`, `fetch(&CameraFile, &Path)`,
  `shoot() -> Result<Vec<CameraFile>>`. `CameraFile` is `{ folder, name }`.
- The `gphoto2` feature, on by default in the app, is backed by the `gphoto2` crate (3.4,
  LGPL-2.1, which GPL-3 can link). It provides `detect()`, the first camera found.
  - `wait` maps `CameraEvent::NewFile` to a file and every other event to `None`.
  - `shoot` is `capture_image`.
  - `fetch` is `fs().download_to`.
- A `Fake` camera behind a `testing` feature, the way `photo-merge` exposes `synth_pano`. It
  hands out scripted files and errors, so both the crate's tests and the app's can drive a whole
  session.
- `Session`, the worker thread. It is given a `Box<dyn FnOnce() -> Result<Box<dyn Camera>>>`
  (the opener runs on the thread) and a destination folder. Its loop:
  1. Take commands: `Shoot` or `Stop`.
  2. Wait 200 ms for an event.
  3. For each file: pick a free name, fetch it to `.part`, rename it, then send
     `Landed { path }`.

  The events are `Connected { name }`, `Landed { path }`, `Failed(String)` (a sentence, the
  session goes on) and `Ended(Option<String>)` (why, if not a Stop). A thread that dies without
  a last word reads as `Ended`, the merge queue's lesson.
- `free_name(dir, name, taken)` uses the import's collision rule: `-2` before the extension.
  `DSCF0001.RAF` and `DSCF0001.JPG` are a pair and never collide with each other.

### The app

- **Lib `tether_options`**, remembered in `Settings.tether` (container `#[serde(default)]`, a compat
  fixture test):
  - `destination: PathBuf`, default `~/Pictures/Rustroom/Tethered`;
  - `session: String`, default empty, which means today's date `YYYY-MM-DD`;
  - `preset: Option<String>`;
  - `folder()` is `destination / safe_name::folder_name(session or date)`.
- **Bin `tether_flow`** holds `RustroomApp::{open_tether, start_tether, shoot, stop_tether,
  pump_tether}`. On Start:
  1. Create the folder.
  2. Open it in the Library (`open_folder_at`), so every shot is a row of the view.
  3. Start the session.

  On each `Landed`:
  1. `scan_and_relink(folder)`, then `entry::apply` with the preset.
  2. `write_xmp_for`, then add the row and select it.
  3. In Develop, open the shot there. That's auto-advance: the newest frame is always what's on
     screen.
- **Dialog `modals/tether`**, a Narrow dialog:
  - the camera line, either "Looking for a camera" or the name;
  - Destination with Choose…;
  - Session name, with the date as its placeholder;
  - Preset ("None" or one from the list);
  - Start, disabled until a camera is found.

  Detection runs on its own short-lived thread while the dialog is open. Start hands the camera
  over to the session.
- **The status row** holds "Tethered · X-T4 · 12 shots", Shoot and Stop, in the job slot after
  export, merges, preview builds and Immich downloads. It falls back to the status line when one
  of those is running; F12 and the menu still shoot then.
- **Menu:** File → Tethered capture… ⇧⌘T, then **Shoot** (F12) and **Stop tethering** under
  it, both enabled only while a session runs.

### What a real camera needs (goes in the dialog's hover text and the journal)

- The X-T4 must be set to **USB TETHER SHOOTING AUTO** (Set up → Connection setting →
  PC Connection Mode). In card-reader mode it shows its files but sends no events.
- On Linux, GNOME's gvfs can claim the camera first. libgphoto2's "Could not claim the USB device"
  becomes "Another program is using the camera".
- On macOS, `PTPCamera` does the same. It's noted, and handled only by that sentence.

## Testing

- **Crate:** the fake drives the session.
  - Two shots land under their names.
  - A taken name gets `-2`, and no `.part` is left behind.
  - Shoot reaches the camera.
  - A fetch error is `Failed` and the session goes on.
  - A `wait` error ends it with the sentence.
  - Stop ends it.
  - A camera that never opens ends at once.
  - Every wait on an event has a 120 s ceiling.
- **App, headless end to end** (the import's e2e shape):
  1. Start a session on a fake that yields `A.JPG`, then `B.JPG`.
  2. Both files are in the session folder and catalogued.
  3. The Library shows both and selects B.
  4. The preset's sidecar is written.
  5. The status count reads 2.
  6. Stop clears the row.
- **Options:** defaults, the date fallback, and a hostile session name kept inside the
  destination.
- **Real camera:** only the author can run it. It's left to the GUI check before merge.
