# M10.18e Print — design

**Status:** the author said "just start" (2026-11-03) and skipped the questions, so every choice below is
mine, made from Lightroom's Print module and what Rustroom already has. Each is marked *(my call)* where
another answer was reasonable.

## Intent

Get the selected photos onto paper, either at home or by sending a PDF to a lab, without leaving Rustroom.
The page must show exactly what Develop shows: the same render export makes, at the printer's resolution,
with print sharpening.

## Goals

- **File → Print… ⌘P** opens a Print dialog on the Library's selection, or on the open photo in Develop.
  With nothing selected the entry is disabled.
- **Two layouts** *(my call: Lightroom's Single Image and Contact Sheet; its Picture Package and Custom
  Package are left out)*:
  - **Single**: one photo per page, either **Fit** (the whole photo, inside the margins) or **Fill** (the
    page area covered, with the excess cropped evenly around the centre).
  - **Contact sheet**: a grid of **Columns × Rows** cells with a **Gap** between them, each photo fitted
    in its cell. **Captions** can be on, showing the file name (or the copy's name) under each photo.
- **Paper**: A3, A4, A5, Letter, 4×6 in, 5×7 in and 8×10 in; **Portrait · Landscape**; one **Margin**
  for all four sides, 0–50 mm.
- **Rotate to fit** (on by default): a photo turns 90° on the page when that makes it larger.
- **Resolution** 150 · 240 · 300 · 360 PPI (default 300), and **Print sharpening** Off · Low · Standard ·
  High. These map to export's `OutputSharpening` amounts 0 · 25 · 50 · 75 (default Standard).
- **Where it goes**:
  - **PDF**: a save dialog, then the file.
  - **Printer**: one of the system's printers, with a number of **Copies**. It goes to the printer
    through CUPS's `lp`, which Linux and macOS both have. The printer list comes from `lpstat`. When
    there is no `lpstat`, or it lists no printer, the dialog offers PDF only, and a hover says why.
- **A preview** of the current page in the dialog, with ‹ › to step through the pages: the paper, the
  margins, each cell, the photo's thumbnail placed as it will print, and the captions. It updates live
  as settings change.
- **In the background**: the dialog closes on Print or Save. The status line shows "Preparing print 3 of
  12", then the outcome: "Printed 12 photos on 3 pages to Canon_G620" or "Saved 3 pages to
  contact.pdf". Failures are named, as export names them. One print runs at a time.
- **The last settings are remembered** in Settings, like the export dialog's.

## Non-goals

- Picture Package and Custom Package layouts, page backgrounds, identity plates, cut guides.
- Soft-proofing or printer ICC profiles. Pages are sRGB and the printer's driver converts them; colour
  management belongs to M10.13.
- The printer driver's own settings (paper type, quality, borderless). `lp` gets the paper size, the
  copies and the file. Anything more is done in the system's printer settings.
- Windows printing. A PDF works there; sending to a printer is M11.2's.
- A Print module (a third view beside Library and Develop) *(my call: a dialog, the shape HDR,
  Panorama and Export already have)*.

## Anti-goals

- A page that differs from the export of the same photo. Each photo is rendered by the export worker
  (`batch_export::ExportWorker`), never by a second path.
- A blocked UI thread during rendering or printing.
- Upsampling done quietly. When a photo's pixels cannot reach the chosen PPI at its printed size, it
  prints at the size asked, and the outcome says "2 photos print below 300 PPI" (the export's
  `below_ppi` idea).

## How

- **Rendering**: an `ExportWorker` run with `Destination::Files` into a staging folder under the cache
  directory, deleted when the print is done. Settings are JPEG quality 95, sRGB, no watermark, no
  metadata beyond the default, and the print's sharpening. Each photo's size is the pixels it needs:
  **its printed size × PPI**. That size comes from the layout for the photo's cropped aspect ratio,
  predicted from its edits the same way export's sizing predicts it (`batch_export::sizing`). Fill asks
  for the size that covers its cell.
- **The PDF** is written by hand, the way `immich::multipart` hand-rolls multipart, with no new crate.
  Each rendered JPEG is embedded as-is as a `DCTDecode` image XObject, so it is not re-encoded. The
  colour space is `ICCBased`, using the sRGB profile export already ships (`export::icc_for`). A Fill
  crop is a clipping rectangle, so no pixel work is needed. Captions use the built-in Helvetica with
  WinAnsi encoding, and a character outside it prints as `?` *(my call)*. Page size is in points.
- **Printing**: `lp -d <printer> -n <copies> -o media=<A4|Letter|…> <file.pdf>`. It is run through an
  injected command runner, so tests never touch a real printer. On this Linux machine CUPS is not
  installed, so the printer path is proven by tests only and by the author on the Mac.
- **Placement** in code, by the repo's rule:
  - lib modules with no egui: `print/{layout,pdf,printer,job}.rs`, holding the page geometry and
    pagination, the PDF writer, `lpstat` and `lp`, and the job's sizes and outcome;
  - bin modules: `print_flow.rs` (the background run, pumped each frame) and `modals/print.rs` (the
    dialog and its preview).

## Left to the builder

The exact widget order in the dialog, within `docs/DESIGN.md`. The caption's font size (one of the
four text sizes, as points on paper). How the preview finds thumbnails (the existing thumbnail cache).
