# `v0.1` piece 3c — the AppImage: design

> Brainstormed with the author on the Arch machine, 2026-11-18, from the brief
> `2026-11-17-v0.1-packaging-linux-brief.md` (read it — this design does not repeat what it settled) and the Mac's
> hand-off `2026-11-18-handoff-from-mac.md`. Calls marked **(author)** were his; **(builder's call)** were made in the
> brainstorm without him and may be revisited; anything unmarked is left to the builder.

## Intent

Photographers on Linux download one file, make it executable, run it — on any distribution, without installing a
package or opening a terminal. **"I don't care which Linux they are on"** (author): the AppImage must reach as far
back as is practical, and a photographer should never have to know what glibc is.

Success: `Rustroom-0.1.0-linux-x86_64.AppImage`, built by the release workflow into the `v0.1.0` draft release beside
the Windows installer and the Mac disk image, starts on Arch (X11 and Wayland), decodes RAW and HEIC, renders on the
system's GPU, tethers the author's X-T4, and keeps the Immich keys in the desktop's keyring.

## Goals

1. **`packaging/linux/build.sh`** — one script makes the AppImage; the release workflow only calls it (3a's rule).
2. **Built on Ubuntu 22.04** (glibc 2.35), so it runs on Ubuntu 22.04+, Mint 21+, Debian 12+, Fedora 36+ and newer
   (author). The floor is **measured** from the bundle (the highest `GLIBC_x.y` symbol version any bundled ELF needs) and
   the build **fails** above a `--floor` the release passes as 2.35 — the Mac's `--floor` idea.
3. **libheif compiled from source for the AppImage** (author): Rustroom binds libheif ≥ 1.17 (`image-decode`'s
   `v1_17`), Ubuntu 22.04 ships 1.12. Use `libheif-sys`'s `embedded-libheif` feature (its bundled 1.23 source, cmake,
   static, plugin loading OFF), with Ubuntu 22.04's `libde265-dev` present so the HEVC decoder is built in. Expose it
   as a cargo feature through `image-decode` and `app` that **only** the AppImage build turns on; Mac, Windows, CI and
   development builds keep the system libheif. ⚠ Verify the result actually decodes a HEIC (the build finds libde265
   by cmake probing — absent, it builds a libheif that decodes nothing, silently). Install no other codec's `-dev`
   package in the build image, so nothing else is picked up by accident.
   **CI's `clippy --all-targets --all-features`** would turn the feature on too (builder's call): make it a no-op off
   Linux — `tether`'s `gphoto2` pattern on Windows — and give CI's Linux job `cmake` and `libde265-dev`, so CI compiles
   the AppImage's own HEIC path on every push (slower clippy, accepted). The `test` job keeps the system libheif.
4. **The bundle** — modelled on `packaging/macos/build.sh`:
   - a walk of the binary's and libgphoto2's drivers' shared libraries (`ldd` / `readelf -d`, NEEDED + RPATH/RUNPATH),
     copying each non-system library in and pointing everything at the bundle (`patchelf --set-rpath '$ORIGIN/…'`);
   - libgphoto2's **camlibs and iolibs**, the same four non-camera drivers left out (`ax203`, `st2205`, `tp6801`,
     `docupen` — they alone link libgd);
   - ⚠⚠ **never the GPU stack or the base system**: no `libvulkan`, `libGL*`, `libEGL`, Mesa, `libdrm`, `libgbm`,
     `libwayland-*`, `libX*`/`libxcb*`, `libxkbcommon`, `libc`/`libm`/`libpthread`/`libdl`/`librt`/`ld-linux`,
     use a written exclude list (AppImage's community `excludelist` is the reference; whether `libstdc++` and
     `libgcc_s` are bundled follows it, the builder's call) and fail the walk on a library in neither list (bundle or
     exclude), so a new dependency is a decision, not an accident;
   - **a check that nothing points outside the bundle** except the excluded system libraries (every bundled ELF's
     resolved NEEDED, run with an empty `LD_LIBRARY_PATH`);
   - **the licences**: the GPL, `cargo about generate --manifest-path crates/app/Cargo.toml packaging/about.hbs`, and a
     **map from each bundled native library to its own licence text that fails on an unknown library** (the Mac's
     lesson: a package's `COPYING` was not always its library's licence). Texts from the Ubuntu packages'
     `/usr/share/doc/<pkg>/copyright` or the upstream source, the builder's choice per library;
   - `AppRun` + the AppImage layout, made by `appimagetool` (a pinned release, its checksum checked) — `linuxdeploy`
     only if it earns its place over the hand walk; the builder's call, the Mac script proved the hand walk.
5. **Desktop integration**: `io.github.wladikrin.Rustroom.desktop` (Name Rustroom, `Categories=Graphics;Photography;`,
   `Icon=io.github.wladikrin.Rustroom`), the aperture icon from `packaging/icons/png/` (256 and 512 into `hicolor`),
   and AppStream metadata `io.github.wladikrin.Rustroom.metainfo.xml` validated with `appstreamcli validate` — the
   groundwork Flathub will want (builder's call). ⚠ Check what app id **winit** sets on Wayland (the `xdg_toplevel`
   app id) and make it `io.github.wladikrin.Rustroom` (eframe's `ViewportBuilder::with_app_id`), or the compositor
   cannot match the window to its icon. Changing it changes nothing on macOS/Windows; confirm.
   **A bare AppImage on Wayland shows a generic icon, and that is accepted for `v0.1`** (author): the compositor matches
   the app id only against an INSTALLED desktop file, which exists once AppImageLauncher or Gear Lever integrates the
   file — the README says so. Rustroom never writes its own desktop file or icon into `~/.local/share`. (If winit
   turns out to support `xdg_toplevel_icon_v1` and setting the icon through it is trivial, it may be used; no more.)
6. **Self-update information** (builder's call, author agreed): the AppImage carries
   `gh-releases-zsync|wladiKrin|rustroom|latest|Rustroom-*-linux-x86_64.AppImage.zsync` and the build writes the
   `.zsync` beside it, so Gear Lever / AppImageUpdate update it in place. It does nothing until the releases are
   public, and no harm before. **Updating through a package manager — the author's ideal — is Flathub, piece 4**
   (needs the public repo); record it in `docs/BACKLOG.md` beside signing and the stores.
7. **`rustroom_app::app_bundle` learns the AppImage**: inside one (`$APPIMAGE` and `$APPDIR` set, and the running
   executable under `$APPDIR`), point `CAMLIBS`, `IOLIBS` and `LIBHEIF_PLUGIN_PATH` at the bundle's folders, never over
   a value the user set — the existing `to_set` rule. Keep the module a lib no-op elsewhere (no `cfg` at its call in
   `main`); the path logic stays pure and tested like `runtime_dirs`. Whether `AppRun` (a shell script) sets them
   instead is the builder's call — but one place, not both, and the "user's value wins" rule holds either way.
   ⚠ libgphoto2 also reads its own compiled-in paths; check that the bundle's drivers are the ones loaded (`lsof` on
   the running AppImage with the X-T4 attached, as on the Mac).
8. **Tethering without USB permission says why** (author): on Linux a camera's `/dev/bus/usb/BBB/DDD` is writable only
   through udev rules, which some distributions install with their libgphoto2 and an AppImage cannot. When that is the
   cause, the status row names it — a new `tether::trouble::Trouble` variant with one sentence in the house style (no
   full stop), e.g. *"Linux does not allow Rustroom to use this camera — install libgphoto2's udev rules"*. Detect it
   from the **device node's permissions**, not from libgphoto2's error text (builder's call): a camera seen on USB
   whose node cannot be opened read-write. Cover the case where libgphoto2 does not even list the camera without
   permission (then "no camera found" must not be the whole answer). ⚠ **Capture libgphoto2's real behaviour first**
   on this machine — Arch's udev rule moved aside, the X-T4 plugged in — and record it in the journal as captured; a
   test fixture built from a guess is not evidence (`AGENTS.md`). Rustroom installs nothing and asks for no password.
9. **The release job**: a `linux` job in `.github/workflows/release.yml` on `ubuntu-22.04` beside `windows` and
   `macos`, calling `packaging/linux/build.sh --floor 2.35`, uploading the `.AppImage` and its `.zsync`; added to the
   `release` job's `needs`. The top comment's "Piece 3c adds its job" line updated.
10. **Built locally too** (builder's call): a small wrapper runs the same `build.sh` inside an `ubuntu:22.04` Docker
    container on the Arch machine (docker is installed there), so the AppImage can be built and tried without CI. The
    container installs the same packages the CI job does — one list, read by both, if practical.
11. **The README's Linux section**: download, `chmod +x`, run; tethering's udev rules (where the file comes from, one
    line per common distribution family); a running keyring (GNOME Keyring / KWallet) for the Immich keys; desktop
    integration through AppImageLauncher or Gear Lever. `CONTRIBUTING.md` says how to build the AppImage.

## Non-goals

- **aarch64** — x86_64 only for `v0.1` (builder's call, unchallenged).
- **Flathub, `.deb`, `.rpm`, AUR** — piece 4 / after *Going public*.
- **Signing the AppImage** — piece 4.
- **Installing udev rules or anything else** on the user's system.
- **Bundling the GPU stack** — wgpu uses the system's Vulkan/GL drivers, always.

## Anti-goals (a failure even if it builds)

- An AppImage that starts on Arch but not on Ubuntu 22.04 / Debian 12 — the floor is the point.
- A bundled `libvulkan`/Mesa that makes the GPU path fall back to the CPU, or crash, on another machine's driver.
- HEIC silently undecodable (libde265 not linked in) — a green build is not proof; decode a real `.heic`.
- A camera that "cannot be found" with no reason when the reason is a missing udev rule.
- A second recipe in the workflow that drifts from the script.

## Constraints

- `AGENTS.md` throughout: the crate boundary (`app_bundle` and the tether detection logic in libs, testable without a
  window), the hover/status-sentence style, no platform words that are wrong elsewhere, the gate on the tip.
- The Mac's `build.sh` lessons carry over: every tool's failure loud (capture its whole output into a variable, never
  lose an exit status inside `< <(…)` or a pipeline), the floor compared as numbers, nothing silently empty passing a
  check. Diff the shell against those lessons.
- Ubuntu 22.04's libgphoto2 is 2.5.27 and its lcms2 2.12 — confirm the `gphoto2` (3.4) and `lcms2` crates build
  against them; if one does not, that is a question for the author before working around it.
- ⚠ **Building is not tethering:** the confirmed Mac and Arch sessions ran a much newer libgphoto2. Tether the X-T4
  through the AppImage's 2.5.27 early. If it cannot, libgphoto2 (and its drivers) is compiled from source for the
  AppImage too, as libheif is — the same "any Linux" reason (builder's call); its licence map and the left-out libgd
  drivers follow the source build.
- The bundle id `io.github.wladikrin.Rustroom` is fixed forever.
