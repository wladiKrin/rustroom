# M11.4 `v0.1` — piece 3b: the Mac app (design)

> **Decisions taken with the author 2026-11-18** on his Mac (macOS 26.6, Apple Silicon), from the brief
> `2026-11-17-v0.1-packaging-mac-brief.md`. Piece 3 is split by machine: 3a ✅ on Windows (the icon, the installer, the
> release workflow), **3b here** — `Rustroom.app` in a `.dmg` — and 3c on Arch (an AppImage). Developer ID signing,
> notarisation and the stores stay piece 4.

## Why

`v0.1` is a download people install the way their system expects. On a Mac that is an app in a disk image, dragged
into Applications. Today Rustroom on a Mac exists only as `cargo run`.

## What 3b found (2026-11-18; measured unless marked)

- **The binary needs no files beside it** — 3a's finding holds: the fonts and the window icon are `include_bytes!`,
  the lens database is the `lensfun` crate's bundled one, the AI models download on first use.
- **The release binary's own floor is macOS 11.0** (`otool -l`, `LC_BUILD_VERSION`). It links four Homebrew
  libraries — `libgphoto2.6`, `libgphoto2_port.12`, `libheif.1`, `liblcms2.2` — which pull in `libltdl`, `libexif`,
  `libintl`, `libusb` (through libgphoto2's USB port driver), `libx265`, `libde265`, `libaom` (and its `libvmaf`) and
  `libsharpyuv`: about 17 MB beside a 63 MB binary.
- **Every Homebrew library on this Mac is built for macOS 26.0** — Homebrew builds for the system it runs on — so a
  bundle made here opens only on macOS 26.
- **Homebrew's bottles** (formulae.brew.sh, 2026-11-18): Apple Silicon builds for macOS 27, 26 and **15**; none for
  macOS 14 of libheif, little-cms2, x265 or aom — so the brief's `macos-14` runner would build them from source — and
  no Intel macOS build of libheif and the others. ⚠ *Expected, not measured:* a macOS 15 bottle's floor is 15.0. The
  build measures it (*What* 1e) on its first CI run.
- **Homebrew's libheif has its decoders built in** — no plugin folder to carry — and links two **encoders**, x265 and
  aom (~11 MB), which the Windows build leaves out.
- **libgphoto2 loads its drivers at run time** — 21 camera drivers (`camlibs`) and 4 port drivers (`iolibs`: disk,
  ptpip, serial, usb1) — from folders compiled into it (`/opt/homebrew/Cellar/libgphoto2/…`), or from the folders the
  `CAMLIBS` and `IOLIBS` environment variables name. Nothing in Rustroom sets them.
- **No CI job builds on macOS**; the release workflow's will be the first.
- ⚠ *Apple's announced change, not tried here:* since macOS 15, Control-click → Open no longer opens an unnotarised
  app — the first launch goes through System Settings → Privacy & Security → **Open Anyway**.
- Development builds stay as they are: `scripts/macos-run.sh` signs `cargo run`'s binary as "Rustroom Dev"
  (identifier `com.rustroom.dev`).

## Decisions (the author's)

- **The floor: macOS 15 and later.** The release is built on CI's `macos-15` runner, from Homebrew's macOS 15
  libraries. A bundle built on this Mac is for trying things out, and needs macOS 26.
- **The bundle identifier `io.github.wladikrin.Rustroom`** — ⚠ fixed forever, like Windows' `AppId`. The form
  Flathub requires for a GitHub project without its own domain, so 3c can use the same id.
- **Our own script**, not packaging tools (*Approaches*).
- Mine, stated in the conversation and not objected to: **Apple Silicon only**; Homebrew's libheif **as it is**, the
  encoders included; a **plain** `.dmg`.

## What

1. **`packaging/macos/build.sh`** — the one recipe; the release workflow only calls it, like `build.ps1`. It needs
   Homebrew's `little-cms2`, `libheif`, `libgphoto2` and `pkgconf`, and `cargo-about`. Every step that fails stops it.
   - a. The version from `cargo metadata` (the `app` crate), as `build.ps1` reads it.
   - b. `cargo build --release -p app` (with Homebrew's `PKG_CONFIG_PATH`, `CONTRIBUTING.md`).
   - c. **The bundle**, `target/macos/Rustroom.app`: `Contents/MacOS/Rustroom`, `Contents/Info.plist`,
     `Contents/Resources/rustroom.icns` (from the committed PNGs through an `.iconset` and `iconutil -c icns`),
     `Contents/Frameworks/` for the libraries, and libgphoto2's two driver folders in a place `codesign` accepts for
     nested code (under `Contents/Frameworks` or `Contents/PlugIns` — never `Resources`).
   - d. **The libraries:** starting from the binary, follow `otool -L` through every library outside `/System` and
     `/usr/lib` — and through every driver — copying each once, and rewrite each reference to `@rpath/<name>`, with
     the binary's rpath `@executable_path/../Frameworks` and each driver's reaching the same folder. ⚠ The script
     **fails if any Mach-O in the bundle still names a path outside the bundle and the system** (`/opt/homebrew`,
     `/usr/local`, a Cellar path).
   - e. **The floor, measured:** the highest minimum macOS of every Mach-O in the bundle becomes
     `LSMinimumSystemVersion`. Given a required floor (the release job gives `15.0`), the script **fails if the
     measured one is higher** — so the day Homebrew stops building for macOS 15, the release stops instead of
     shipping an app that will not open.
   - f. **`Info.plist`:** the identifier above; name and display name `Rustroom`; executable `Rustroom`; the crate's
     version as `CFBundleShortVersionString` and `CFBundleVersion`; the icon; `APPL`; the floor; high-resolution
     capable; category `public.app-category.photography`; the copyright line with GPL-3.0-or-later. And the
     **purpose strings** macOS shows the first time Rustroom reaches a protected place — the Desktop, Documents and
     Downloads folders, a removable volume (a card), a network volume, and the **local network** (an Immich server
     at home, macOS 15's prompt) — each one sentence in `docs/DESIGN.md`'s voice.
   - g. **The licences**, in `Contents/Resources`: `LICENSE`, `THIRD-PARTY-LICENSES.html` (`cargo about generate`,
     `about.toml` already names the Mac target) and a `licenses/` folder — LibRaw's three texts, LensFun's notice,
     Inter's and Phosphor's, from the same sources `build.ps1` copies, and **every bundled Homebrew library's own
     text** from its keg (`COPYING`, `LICENSE`); the script fails on a bundled library it has no text for.
   - h. **Signing, ad hoc** (`codesign --sign -`): every nested Mach-O first, then the app; then
     `codesign --verify --deep --strict` must pass. Apple Silicon runs no unsigned code.
   - i. **The disk image** `target/macos/Rustroom-<version>-macos-arm64.dmg` — plain: the app and an `Applications`
     link, `hdiutil` compressed — and its `.sha256` beside it, printed like the Windows script's.
2. **Tethering inside the bundle** — a **lib** module (no egui) whose one call is the first line of `main`, a no-op
   off macOS and outside a bundle — `rustroom_app::console`'s pattern, so `main` needs no `cfg`. When the executable
   sits in `<name>.app/Contents/MacOS/` and the bundle carries the driver folders, it sets `CAMLIBS` and `IOLIBS` to
   them — never over a value already set — before any thread starts. Deriving the folders from the executable's
   path is a pure function, tested on constructed paths.
3. **The release workflow:** a `macos` job on `macos-15` — `brew install` the four, install `cargo-about`, run
   `build.sh` with the floor `15.0`, upload the `.dmg` and its `.sha256` — and the `release` job's `needs` gains it.
4. **Docs:** the README's macOS row (the file; "macOS 15 or later, Apple Silicon"; the Open Anyway paragraph beside
   the Windows one); `CONTRIBUTING.md` (building the `.dmg` locally, its floor following the machine's Homebrew); the
   journal, `CLAUDE.local.md` and the vault; `AGENTS.md` only for a rule that outlives the piece.

## How it is tried

- **By the script itself:** no outside path left, the signature verifies, the floor checked.
- **On this Mac, by the author:** the `.dmg` opens; drag into Applications; launch — the Dock's icon and name, the menu
  bar's "Rustroom"; open a folder, a RAW and a HEIC; Develop and export; the Immich keys (one keychain prompt); the
  map's tiles; **tethering with his X-T4 from the installed app** (the drivers loaded from inside the bundle, not from
  Homebrew — read from the running process's open files, `lsof`); and a **quarantined** copy
  (`xattr -w com.apple.quarantine …`) to see the first-launch path the README describes.
- **On CI:** a manual run of the release workflow builds the `.dmg` on `macos-15` and **measures** the floor.
- ⚠ **Not seeable here:** the app on a macOS 15 machine. The floor is a measurement of the libraries, not a run.

## Known costs

- **Ad hoc signing:** the first launch needs Open Anyway, and every update is a new identity to the keychain — the
  Immich keys ask for the login password once after each (as development builds do today, M10.15a).
- **The floor follows Homebrew,** whose bottles today cover the three newest macOS (27, 26, 15): when macOS 28 ships,
  the macOS 15 bottles likely go, and the release fails its floor check (*What* 1e). Then: accept macOS 26, or build the libraries from source.
- About 80 MB unpacked (the binary 63 MB, the libraries 17 MB, x265 and aom among them).
- Still no macOS CI on ordinary pushes — the macOS-only modules can rot unseen between releases.

## Approaches

1. **Our own script** — ✅ the author's pick. `otool`, `install_name_tool`, `codesign`, `iconutil` and `hdiutil` are
   on every Mac; about 200 lines of shell we own, the same shape as `build.ps1`; the driver folders, the licence
   texts and the floor check are just more steps.
2. **Packaging tools** — `cargo-packager` (or `cargo-bundle`) for the bundle, `Info.plist`, icon and `.dmg`, and
   `dylibbundler` for the libraries. Less shell, but two more tools to install on CI and keep compatible;
   `dylibbundler` still needs the drivers named by hand, and their styled `.dmg` scripts Finder, which often fails on
   CI's headless machines.
3. *Dropped:* LittleCMS from its bundled source on the Mac too (as on Windows) — one library fewer, at the cost of a
   Mac-only difference in how the code is built.

## Not in this piece

Developer ID signing, notarisation, the hardened runtime and a Homebrew cask (piece 4); Intel Macs or a universal
app; a macOS job in CI for every push; opening photos from Finder (file associations — later, as on Windows); a
styled `.dmg`; automatic updates.

## Left to the builder

The driver folders' exact place and the script's structure; the purpose strings' wording (within `DESIGN.md`); how
the floor is passed to the script; whether to strip the binary; how the workflow caches Homebrew; the volume name.
