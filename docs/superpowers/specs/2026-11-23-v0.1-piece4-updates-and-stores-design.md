# `v0.1` piece 4 — updates and stores, free routes only: design

> Brainstormed with the author on the Arch machine, 2026-11-23, after `v0.1.0` went public. Calls marked **(author)**
> were his; **(builder's call)** were made in the brainstorm without him and may be revisited; anything unmarked is left
> to the builder. The research behind the routes (dated 2026-11-23) is summarised in *Background*; re-check any price or
> policy before acting on it.

## Intent

**Installing Rustroom should be easy, and updates should arrive on their own** (author). **Nothing may cost money**
(author: "I don't want to pay, let's only do the free stuff") — no code-signing certificate, no Apple Developer
Programme, no paid signing service.

Success: on Windows a photographer installs Rustroom from the Microsoft Store with no SmartScreen warning and is
updated by Windows; `winget upgrade` and `choco upgrade` bring a new release; on every download that cannot update
itself (the AppImage, the Mac disk image, the Windows installer) Rustroom says when a newer version exists. Flathub,
written and submitted by the author, does for Linux what the Store does for Windows.

## Background (research, 2026-11-23)

- **Microsoft Store:** an individual developer account is free (since 2025-09-10). An **MSIX** package is re-signed by
  the Store — no SmartScreen warning — and updated by Windows. A classic Win32 app runs as `runFullTrust`, a restricted
  capability justified in the submission. (The Store's EXE/MSI route needs our own certificate from a trusted CA: not
  free, so not taken.)
- **winget:** free; a release is a pull request to `microsoft/winget-pkgs` with a manifest pointing at the installer on
  GitHub. **Chocolatey:** free; a package is pushed to community.chocolatey.org with an API key and moderated before it
  is listed (moderation's details unverified).
- **Flathub:** source builds only. ⚠⚠ Its requirements forbid AI-generated or AI-assisted content in a manifest and ask
  submitters to disclose AI-generated code. **The author writes and submits the manifest himself (author).** An
  AI-written reference he asked for, marked not for submission, is outside the repository
  (`~/rustroom-flatpak-reference/`) and must never enter it.
- **macOS:** no free route removes Gatekeeper's warning; Homebrew's main cask repository stopped accepting casks that
  fail Gatekeeper (September 2026). The Mac stays as it is.

## Goals, in build order (builder's call)

### 1. The "new version available" notice — every platform

- **On from the first launch, with a switch to turn it off (author).** The switch is **"Check for new versions"** in
  Settings → Behaviour (builder's call), with the other choice about going online, the map tile server, nearby.
- **When:** once at startup, in the background, **at most once a day** — the time of the last check is kept in the
  settings. No network, a timeout, a GitHub error or an unparsable reply: **silent**, never an error dialog, never a
  status message (builder's call).
- **Where it asks:** `GET https://api.github.com/repos/wladiKrin/rustroom/releases/latest` (the newest published,
  non-draft, non-prerelease release), through `ureq`, already a dependency. Unauthenticated; 60 requests an hour per
  address is far above one a day. Its `tag_name` (`v0.2.0`) is compared with the running `CARGO_PKG_VERSION` as a
  version, never as a string (`0.10.0` > `0.9.0`).
- **What it shows:** one quiet line in the status bar, "Rustroom 0.2.0 is available", following `docs/DESIGN.md` (its
  §12 checklist; a one-sentence hover without a full stop). A click opens the release's `html_url` in the browser
  (egui's `open_url` — verify eframe opens it natively). **Rustroom downloads and installs nothing itself.** Beside it,
  **Hide** hides it until Rustroom next starts (nothing saved) and **Don't show again** turns the switch below off — the
  author's change of 2026-11-24, replacing a Hide that kept one version quiet across starts.
- **Silent where something else updates it** (builder's call): in the **Store** build (packaged identity —
  `GetCurrentPackageFullName` succeeds) and the **Flatpak** (`/.flatpak-info` exists or `FLATPAK_ID` is set) it never
  asks. A **build-time opt-out** too (builder's call): built with the environment variable
  `RUSTROOM_NO_UPDATE_CHECK=1` (read through `option_env!`), the check is compiled off and the switch hidden — for a
  distribution's own package (AUR, Nix) and the author's Flatpak, whichever way it is built. ⚠ winget and Chocolatey install the very same `setup.exe`, so the installed program cannot tell them from a
  download: there the notice shows, and its link is still right. (This narrows what the brainstorm said — "silent in
  winget and Chocolatey" — and is the builder's call.)
- **Shape:** the logic in a **lib** module with no egui (`crates/app/src/update_check.rs`, say): the version
  comparison, "is a check due", "should this be shown", reading the release JSON, the "updated elsewhere" detection —
  all tested headless; a small background worker; the status-bar line in the bin. The new settings fields — the switch,
  the last check's time, the newest version found (so a second launch the same day still shows it) — are appended to `Settings` (container-level `#[serde(default)]` — the file's rule) with a `compat_tests.rs` test that an
  older settings file still loads with the check **on**.
- ⚠ **Tests never touch the network** — the HTTP call is behind a function handed in, like `people_tool::Finders`.
- ⚠ `modals/settings.rs` and `status_bar.rs` are large (1,152 and 767 lines on disk): measure with
  `code_and_doc_lines` before adding, and split by responsibility if the switch would push either too far.

### 2. The Microsoft Store — an MSIX package

- **`packaging/windows/msix.ps1`** (or a mode of `build.ps1`) makes `Rustroom-<version>-windows-x64.msix` from the same
  staged folder the installer uses (`Rustroom.exe`, the licences), with `makeappx.exe` from the runner's Windows SDK,
  as a **workflow artifact only** (builder's call): it is never a release asset nor in `SHA256SUMS`, since an
  unsigned MSIX cannot be installed by double-click and a sideloaded one would be a copy nothing updates. The author
  downloads it from the run and uploads it to Partner Center. The identity values come from **repository variables**
  the author sets after reserving the name; while they are unset the job skips the package and says so. The package is **unsigned** for the Store
  (the Store signs it); for a local test install the script can sign it with a throwaway self-made certificate, never
  committed.
- **`AppxManifest.xml`:** a `windows.fullTrustProcess`-style desktop app (`EntryPoint="Windows.FullTrustApplication"`,
  `runFullTrust`); `Identity Name`, `Publisher` and `PublisherDisplayName` are the values **Partner Center assigns when
  the author reserves the name** — the repository variables above, never invented; the version is `<x.y.z>.0`; the logos rendered from
  `rustroom.svg` by `render.py` (the Store wants several sizes — 44, 50, 150, 310 and their scales; check its list).
- ⚠⚠ **The catalog and settings must be the SAME for the Store build and the installer build** (builder's call). An
  MSIX app's writes into `%APPDATA%` and `%LOCALAPPDATA%` are redirected to a private per-package folder by default, so
  the Store version would start with an empty catalog and lose everything on uninstall. Rustroom keeps its settings in
  `%APPDATA%\rustroom` (`dirs::config_dir()`, many call sites) and its catalog, previews and caches in
  `%LOCALAPPDATA%\rustroom` (`Catalog::library_dir`, `user_cache`). The builder **finds the mechanism the Store
  accepts** for writing those real folders — Windows' flexible virtualization (`virtualization:FileSystemWriteVirtualization`
  with excluded directories) or `unvirtualizedResources` — and **proves it on the Windows PC**: install the installer
  build, make a catalog, install the Store build (sideloaded), see the same catalog; uninstall the Store build and the
  catalog stays. If no accepted mechanism exists, stop and bring it to the author before choosing another.
  ⚠ The OS version that mechanism needs becomes the package's `MinVersion`; say what it excludes.
- **Submission is the author's:** registering the account (with its identity check), reserving the name, writing the
  listing, the `runFullTrust` justification, the age rating, uploading each release's package. Automating the upload
  (the Store submission API) is a later option, not this piece. The builder writes the author a short checklist for the
  first submission in `CONTRIBUTING.md`'s release section, and a draft of the `runFullTrust` justification for him to
  edit.
- **A privacy policy** — the Store asks for one when an app goes online or handles personal data, and Rustroom holds
  Immich keys. The builder drafts `PRIVACY.md` (plain words: what Rustroom sends where — Immich, the tile server,
  Nominatim, model downloads, the update check — and that it collects nothing itself); ⚠ **the author approves its
  text before it is committed**, since it is a public statement made in his name.
- The installer stays beside the Store package, its `AppId` unchanged — with one addition for Chocolatey (below).

### 3. winget and Chocolatey — published from each release

- Both run in a **new workflow on `release: published`** — the release workflow only drafts; the author publishes by
  hand, and only then do the files have their final URLs. Each reads the installer's URL and SHA-256 from the
  published release (`SHA256SUMS` is already attached).
- **winget:** the first submission is by hand (`wingetcreate new`, package id `wladiKrin.Rustroom` — builder's call —
  installer type `inno`, user scope); later releases by the workflow (`wingetcreate update --submit`, or an
  established action that does the same). It needs a GitHub token able to open a pull request from a fork of
  `microsoft/winget-pkgs` under the author's account, stored as a repository secret **by the author**.
- **Chocolatey:** `packaging/chocolatey/` — the `.nuspec` and `tools/chocolateyinstall.ps1` (download the installer
  from the GitHub release, check its SHA-256, run it silently: Inno's `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /ALLUSERS`), and
  an uninstall script. ⚠ Chocolatey runs elevated, often as another account, so a per-user install would land in the
  wrong profile: the installer gains `PrivilegesRequiredOverridesAllowed=commandline` (builder's call), which lets
  Chocolatey pass `/ALLUSERS` and install into Program Files; a double-clicked installer still asks no admin and
  installs per user, as now; the catalog and settings stay per user either way. winget stays user scope. Package id `rustroom`, if free. The workflow fills in the version, URL and checksum, packs and
  pushes with the author's API key, a repository secret **set by the author**. The first push may wait for moderation.
- ⚠ Both publish under the author's name to public registries: **nothing is submitted or pushed during development** —
  the builder tests by packing locally (`choco pack`, a local `choco install` on the Windows PC; `winget validate` and a
  local manifest install) and the author runs the first real submission.
- The README's Windows section gains the Store, `winget install wladiKrin.Rustroom` and `choco install rustroom` once
  each exists — not before.

### 4. What Flathub needs on Rustroom's side — when the author starts his submission

Only on the author's request, and only in Rustroom's own files (never the manifest):

- the AppStream metadata (`packaging/linux/io.github.wladikrin.Rustroom.metainfo.xml`): screenshots by URL, a
  `<releases>` entry per version, content rating — whatever Flathub's linter asks for;
- renaming the cargo feature `appimage` to what it means (`bundled-libheif`, say), since a Flatpak build would use it
  too; the release workflow, `build.sh`, `AGENTS.md` and CI's clippy follow;
- anything else his build turns up. ⚠ Printing to a printer cannot work inside the Flatpak (no `lp`); saving a PDF does.

## Non-goals

- Anything that costs money (author) — certificates, Apple's programme, SignPath's paid tiers, Azure signing.
- Rustroom downloading or installing updates itself (builder's call: no self-updater — it is the riskiest code an app
  can carry, and the stores do it better).
- The Mac (no free route). The AppImage's own zsync update information stays as it is (Gear Lever and AppImageUpdate
  already use it); the notice adds to it.
- A Flathub manifest in the repository, or any AI-written text in the author's submission.
- Automating the Store upload.

## Anti-goals

- An update check that nags, shows an error offline, or contacts anything but GitHub's release endpoint.
- A Store build with its own empty catalog, or one whose uninstall takes the user's catalog with it.
- Anything published to a registry or store in the author's name without him.

## Where it is built (builder's call)

Goal 1 on the Arch machine, as one branch. Goals 2 and 3 need the Windows PC — the shared-catalog proof, a local
`choco install`, `winget validate` — so goal 1's close writes a hand-off spec for them
(`docs/superpowers/specs/<date>-handoff-from-arch.md`), the way the earlier machines handed over. Goal 4 waits for the
author's Flathub build.

## Left to the builder

The module and worker shapes, the MSIX script's structure, the exact manifest fields beyond those above, the
Chocolatey script details, the wording of the status line and the hover within `docs/DESIGN.md`, and the order of
commits inside each goal. Each goal is its own branch, merged when the author has seen it (his way of closing a
milestone).
